# Changelog

All notable changes to this project are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [1.4.0] — Unreleased

> **Legal text can now be changed without a deploy.** The platform owner can
> publish new versions of any of the ten legal documents from inside the product.
> The version number is the safety mechanism, and it is enforced on the server:
> **a save must carry a strictly greater `MAJOR.MINOR.PATCH` version**, so a
> published version is never rewritten and the text an acceptance record points
> at can always be produced. This is not a preference — `legal_documents` is keyed
> by `(slug, version)` and a published row is immutable, so reusing a version
> would make the catalogue disagree with the consent records and, once hash
> enforcement is switched on at launch, refuse to boot.
>
> **One consequence deserves calling out.** Publishing a new version of the
> **Organizer Agreement** withholds fifteen capabilities from every organizer
> until each accepts it again, because acceptance is matched on `(slug, version)`.
> That is correct — the agreement is what those capabilities are granted against —
> and the editor now warns before saving that particular document. Publishing any
> of the other nine changes nothing for existing users; there is still no
> re-consent flow for signup documents.

### Added

- **Optional Upstash Redis, for two things and deliberately not for five.**
  The account lockout that bounds password guessing — ten failed passwords per
  account across every device — now shares a Redis-backed counter, along with
  the mail, re-authentication, appeal and certificate-check limiters. A restart
  no longer clears a lockout in progress: a deploy during a password spray used
  to hand the attempt a fresh budget. The weather and address caches
  gained a second tier behind their in-process one, so a deploy no longer
  re-warms them against Nominatim's limit of one request per second *for this
  application in total*, and the pacing reservation that honours that limit is
  now application-wide rather than process-wide.

  Entirely optional: with `UPSTASH_REDIS_REST_URL` and
  `UPSTASH_REDIS_REST_TOKEN` unset, every limiter counts in process memory and
  every cache lives in this process, exactly as before. Redis is never required
  to serve a request, and when it is unreachable each caller falls back to a
  counter it has been incrementing all along — so an outage is the previous
  behaviour resuming, not a reset, and never a lockout.

  This is also the first of the three prerequisites the Supabase/Vercel
  assessment names for running more than one application instance.

- **Three sign-in limiters were deliberately left in process memory, on a
  measurement.** `authLimiter`, `loginLimiter` and `loginIpCeilingLimiter` were
  the obvious things to share and were the first version of this change. They
  sit on the busiest authentication paths and each sets
  `skipSuccessfulRequests`, which bills a counter increment on every request and
  a decrement on every success — so the expensive case is somebody signing in
  *correctly*. Modelled against the free plan's 500,000 commands a month, that
  version cost **107% of the monthly allowance at a thousand users**, before
  anything else spent a command; the shipped scoping costs about a fifth of it.
  What is given up is the per-device layer, which one instance already enforces
  correctly, while the per-account layer that actually bounds guessing is the
  one that became shared. `docs/operations/upstash.md` §7.3 shows both columns.

- **What was measured and then NOT built, which is most of it.** Caching
  database queries, Redis-backed sessions, chat in Redis, and a leaderboard
  sorted set were each evaluated and rejected on evidence rather than taste. The
  deciding number is in `docs/operations/postgres-scale-measurements.md`: the
  hot queries answer in 0.3–0.5 ms at fifty times pilot scale, and an Upstash
  round trip is far slower than that, so moving them would have made the
  application slower while spending a metered allowance to do it. Sessions
  already have per-session revocation in SQL; durable messages belong in the
  relational database, where retention, deletion, export and moderation are
  built; and a leaderboard sorted set would be a derived index able to drift
  from the hours ledger, against INV-001, to fix a table scan that an index
  fixes for free. `docs/operations/upstash.md` records each rejection with the
  measurement behind it.

- **The travel-time route is excluded from the shared cache on purpose**, and a
  test fails the build if that ever changes. Its origin is a volunteer's
  location — usually a minor's — and that module promises the coordinate is
  "never persisted. No column, no row, nowhere." Hashing the cache key does not
  rescue that promise, because the promise is about where the data goes rather
  than how it is encoded. That cache stays process-local and dies with the
  process, and every deploy paying for its first few lookups again is the price
  of the invariant.

- **`bin/upstash-redis.mjs`** — `status`, `ping`, `keys`, `validate` and
  `purge`, with `npm run redis:status | redis:ping | redis:keys |
  redis:validate`. `ping` prints the measured round trip beside the database
  timings it is being compared against, so the reason no query is cached in
  Redis is visible on the deployment rather than only in a document. `validate`
  exercises set/get/TTL/expiry/counter/script/pipeline against a handful of keys
  and deletes every one of them before it exits, including after a failure.

- **A Redis section on the administrator system-status panel** — configured,
  degraded, this process's command and latency counters, the plan limits, and
  per-cache hit rates. Counts and configuration only: no key names, no key
  contents, no identifiers, and never the token. Deliberately not on `/health`,
  which is unauthenticated — "the shared rate-limit store is down" is knowledge
  that the limits have fallen back to per-process.

- **A Legal Center editor, for the platform owner only** (Settings → Help &
  Support → Edit Legal Center). One document at a time, its name above it, a
  preview beside it, and a version field that explains the forward-only rule in
  place rather than only in an error. Every save keeps the version before it:
  revisions are append-only, so no publication destroys the one it replaced.
  Access is gated by a new `legal.edit` capability in `SUPER_ONLY`, which makes
  it owner-only **and ungrantable** — "let the person handling our compliance
  paperwork fix the Terms" is a reasonable-sounding grant that would hand the
  contract to an account nobody vetted, so that conversation has to happen as a
  role change instead.
- **Publishing requires a fresh proof of identity** (`legal.publish`, bound to
  the document and the version, so one verification publishes one document at one
  version). The write was already audited and attributable; what a step-up adds
  is the moment of deliberation between typing in a textarea and replacing the
  document every account on the platform is held to. Changes are recorded in the
  administrative audit trail as `LEGAL_DOCUMENT_PUBLISHED`.
- **An About Us page** at `/about`, public and readable without an account —
  what WeVolunteer is for, who it serves, and what it is trying to do. Reachable
  from Settings → Help & Support. It closes on a concrete, checkable decision
  rather than on the motto alone: hours are never stored as an editable total, and
  a running number would have been simpler to build. A page that asserts "because
  we care" without showing anything it cost is a slogan; this one names the
  tradeoff. It also answers the questions a parent or teacher arrives with, which
  the first draft did not address at all.

### Changed

- **The Settings entry for the legal documents is now called "Legal Center".** It
  read "Terms, privacy and safety policies" — a list of contents standing in for
  a place. The page it opens has been a hub of ten documents with its own search
  and grouping since v1.2, so naming it after three of them made the other seven
  invisible from the only durable route to them: the signup links are behind an
  account the reader has already made. The examples moved to a description line
  underneath, which is where an example belongs.
- Help links to pages inside the app are now client-side navigations rather than
  full page reloads.
- The Legal Center, the document pages and the consent records now report the
  version, effective date and content fingerprint of **what is actually being
  served**, resolving through the new revision layer rather than reading the
  registry constant.

### Fixed

- **A lower version number could compare as higher, permanently.** The version
  comparator was `(major - major) || (minor - minor) || (patch - patch)` over
  components produced by `Number()` with no bound on length. Both halves were
  needed and both were present: `Number('9'.repeat(400))` is `Infinity`, so two
  long versions gave `Infinity - Infinity`, which is `NaN` — and `NaN` is falsy,
  so the `||` cascade fell straight through it and the major number stopped
  participating in the comparison at all. Because revisions are append-only, a
  single publish at an absurd version would have made every later publication of
  that document compare as not-greater for ever, recoverable only by editing
  production SQL. Components are now length-bounded so they stay exactly
  representable, and the comparison is key-by-key equality so no arithmetic
  result can be falsy.
- **Keyboard focus was dropped to the page body after a successful save.**
  `useModal` restores focus to whatever opened a dialog *synchronously* on
  unmount, and a save resolves after that unmount — so the editor's focus moves
  were immediately undone, and the following Tab restarted from the top of the
  page. It also left `aria-invalid` set on a control the user was not on. Every
  focus move on the editor now routes through one piece of state consumed by an
  effect, which commits strictly later than any dialog's restore.
- **A refused save did not say which field it was about.** The server has always
  returned the offending `field` on a 400; the editor ignored it. It now marks
  that input with `aria-invalid` / `aria-errormessage` and moves focus to it.
- **The "last updated" date was collected and never shown.** A document page now
  reports "last revised", and only when it differs from the effective date —
  they are the same day for almost every save, and printing both makes a reader
  work out whether two dates disagree for a reason.
- **The sign-in page still used the old wording**, linking to the Legal Center as
  "Terms, privacy and safety policies" — a stale reference the rename missed, on
  the one page every returning user sees.
- **A policy link could specify any URL scheme, including `javascript:`.** The
  renderer put a parsed link target straight into an anchor's `href`. That was
  safe by provenance while policy text could only come from this repository, and
  stopped being safe the moment an account could write it — `/legal/:slug` is
  unauthenticated and is where the signup form sends fourteen-year-olds. Two
  layers now refuse it: the save is rejected with a message naming the offending
  link, and the renderer degrades an unsafe target to plain text rather than
  dropping it, so a clause never silently disappears.

## [1.3.1] — Unreleased

> **Two-factor authentication changed who can complete it.** Once an account has
> any second factor, a **confirmed email address is now accepted as one** — even
> for an account that enrolled an authenticator and never switched email codes
> on. This is deliberate: email is what somebody reaches for when their
> authenticator is gone, and requiring them to have pre-enabled it demands
> foresight exactly where they have none left. It does not widen who can sign in
> — delivery goes to the address that could already reset the password — but it
> does mean that **for an authenticator-only account, 2FA no longer resists a
> compromised school mailbox.** An account that wants a factor independent of
> its mailbox should rely on its recovery codes, which are unchanged.

### Fixed

#### Security and privacy — found by the pre-push audit

- **The 2FA guessing budget was bypassable by not waiting for the answer.** Both
  ceilings — five guesses per grant, twenty per account per fifteen minutes —
  were read-only `SELECT`s, and the counter was incremented only *after* the code
  had been checked, with `await bcrypt.compare` sitting in the gap. Requests
  bearing the same pre-auth cookie all read `attempts = 0` before any of them
  wrote, so all of them were allowed. Reproduced: **ten of twelve** concurrent
  recovery-code guesses reached the verifier instead of five. The attempt is now
  CLAIMED atomically before verification and rolled back if it exceeds the
  ceiling — rolled back rather than kept, because a 429 that still counted would
  refresh the rolling window on every rejected request and let anybody holding
  the password keep the account's own owner locked out. The claim sits below
  every 400 and above every verification: a malformed code, an omitted code and
  a method the account does not hold each still cost nothing.
- **Blocking did not withdraw the friendship, so it did not close the profile.**
  Restricting — the gentler control — removed the friendship row; Block, the one
  immediate safety control a student holds, did not. An accepted friendship is
  what unlocks the friends-only tier, so a student who blocked somebody harassing
  them went on publishing their school, grade and bio to that person, and both
  stayed in each other's friend lists. Blocking now withdraws the friendship, and
  `areFriends` independently refuses a blocked pair — the second half repairs
  rows an earlier version already wrote.
- **A block was announced to the person blocked.** `viewer.blocked` was symmetric
  while `GET /api/blocks` returns outbound blocks only, so seeing the flag and
  finding the subject absent from your own list identified, in two requests,
  somebody who had blocked you. The same disclosure `restrictedBy` is stripped to
  prevent, through the other flag in the same object. The wire value is now the
  viewer's OWN block; the friend request still meets the same generic 409.
- **Search could be paged out to the whole membership.** The 25-result ceiling
  bounded one request and `offset` was unbounded, so `?offset=0,25,50,…` walked
  every minor's name, handle and general area out in pages. Paging is now capped,
  and the test that claimed to cover this was vacuous — its one-character query
  never reached the query it was asserting about.
- **A partner could read student profiles through the route that predates the
  directory.** `directory.read` is withheld from `partner` deliberately, every
  v1.3 route enforced it, and `GET /api/users/:id/profile` — name, avatar,
  skills, credited hours, milestones, service counts — had no gate at all.
  Neither did `GET /api/users/:userId/badges`, whose recorded posture is
  explicitly matched to it. Both now check the capability. This also closes the
  same route to an organizer who has not accepted the Organizer Agreement, which
  v1.3 withheld `directory.read` for and this route ignored.
- **A pre-auth grant completed more than one sign-in.** Success cleared the
  cookie and nothing else, leaving the token itself valid for its full fifteen
  minutes — replayable to mint another session, and each replay also cleared the
  failed-attempt rows and so handed the next one a fresh budget. Nothing on that
  path read `token_version` either, so "sign out all other devices" and a
  password reset could not reach a sign-in already standing at the second-factor
  step. The grant is now spent once, and refused once the account's version moves.
- **One verification covered enrolling a factor and destroying every recovery
  code.** Replacing recovery codes was gated on `2fa.enable`, so the grant from a
  dialog reading "enable two-factor authentication" was spendable on the handler
  whose first statement is `DELETE FROM recovery_codes` — and enrolment
  deliberately holds an unspent `2fa.enable` grant for minutes while a QR code is
  scanned. It has its own action now, `2fa.recovery.regenerate`, with its own
  sentence.
- **An archived organization stayed fully readable, roster included.** Browsing,
  search and joining all excluded archived organizations; the page that lists up
  to a hundred members did not, and slugs are derived from the name rather than
  random. Archiving is the only withdrawal a manager is offered, so a club
  archived to take its roster out of view had not been.
- **The email-code cooldown failed open.** An unparseable `created_at` made
  `elapsed` `NaN`, and `NaN < 60000` is false — so the one comparison guarding
  the send route would have stopped guarding it silently. It now holds shut.
- **Two second-factor tables were never swept.** `tfa_email_codes` retained a
  bcrypt hash of every code ever mailed and `tfa_login_attempts` a row per
  abandoned sign-in, indefinitely — credential material with no remaining
  purpose, which is exactly what `reauth_challenges` is swept to avoid keeping.

#### Correctness, mobile and records

- **The Dashboard scrolled sideways on a phone, and that is what made it render
  zoomed out.** The mobile rule stacked `.nextshift` but used
  `align-items: flex-start`, which in a column flex container sizes each child to
  its own max-content width rather than the container's — so the line holding an
  event title laid out at 356px inside a 320px viewport and pushed the document
  past the screen. `.truncate` could not help, because ellipsis needs a box that
  has already been constrained. The fix is `stretch`; the viewport meta tag is
  untouched and pinch-zoom stays available, because the overflow was the bug and
  the scaling was only the report of it.
- **The discovery live region was ungrammatical.** `role="status"` announced
  "1 people and organizations found" — the single result that typing a name
  usually produces — and "0 people and organizations found" for none. It is the
  only signal a screen-reader user gets that the search finished. Each kind is
  now pluralised on its own count and the empty case reads as a negative.
- **Turning email codes off did not turn them off**, for an account that also has
  an authenticator: `tfa_email_enabled = 0` demotes email from the default and
  changes nothing the sign-in step reads. The button said "Turn off". It now says
  what it does and confirms before it does it, naming recovery codes as the
  factor a mailbox cannot reach. The v1.3.1 behaviour itself is unchanged — it is
  deliberate, and documented at the head of this release.
- **Migration 032's pragma guard failed open**, passing whenever the read
  returned anything other than a confirmed `1` — the wrong direction for the one
  assertion standing between a table rebuild and a cascade delete. It now matches
  `001_authz_roles.js` and refuses anything that is not a confirmed `0`, and
  restores the connection's prior foreign-key state rather than forcing it on.
  **Editing 032 changes its checksum**, so a DEVELOPMENT database that already
  applied it will refuse to boot until the recorded value is backfilled — the
  error names the exact `UPDATE`, and `bin/migration-checksums.mjs` prints it.
  No released database is affected: 032 is not on `main`, and on any database
  without an `external_hours` table the migration early-returns. It was worth
  doing now precisely because this is the last moment it is cheap — after the
  release, editing a migration that has run against real data is a different and
  much worse problem.
- **The v1.3 participation-count index could have been lost permanently.**
  `applications(user_id, status)` was created by migration 031 only, and the
  `applications` rebuild in `db.js` recreates no indexes; the two it does lose are
  recreated on every boot and this one was not. Not reachable today, which is why
  nothing would have noticed.
- **The volunteer-record policy no longer matched its pinned hash.** The v1.3
  Auto Select section was written into the file and the constant was not moved
  with it, so every boot warned about drift and an enforcing boot would have
  refused to serve it.
- **The release checklist never asked for a backup before a table rebuild.**
  §8.3 makes that the first of six guards and the only one no code enforces —
  the other five are assertions inside the migration. v1.3 contains a rebuild.


- **Authenticator 2FA answered 500 on a CORRECT code** — and a clean 401 on a wrong one, which is the most confusing shape a sign-in failure can take, because every instinct says the code is the problem. The accepted TOTP time step is written to `users.tfa_last_counter` so a code cannot be replayed, and that write was the only statement in the whole TOTP login path: on a database behind migration 029 the column did not exist, the write threw, and the handler's outer catch turned it into a generic 500. A wrong code returns before reaching it. The write is now guarded, and a code that cannot be recorded as spent **refuses the sign-in** — with a named 503 pointing at recovery codes — rather than completing one the platform cannot make single-use. Silently accepting it would have turned off the replay protection on exactly the databases least likely to be watched.
- **Two more 500s in the same handler** — `code.trim()` ran on the raw request body, so a non-string `code` threw a TypeError, and it did so *before* the failure counter was bumped, so it was not rate-limited either. Both submitted values are normalised once and a wrong type is now a 400. An empty string is a 400 too, rather than a 401 that spends one of the twenty attempts on a request that supplied no code.
- **`/api/auth/login-2fa/email/send` had no error handling at all** despite awaiting a bcrypt hash, a dynamic import and several writes. Under Express 4 a throw there was an unhandled rejection that left the request hanging — a Send button that never came back.
- **Email codes were offered to accounts that could not receive them.** `enabledSecondFactors` tested `tfa_email_enabled` alone while the send route also required `email_verified`, so an unconfirmed address was shown the radio and met a 400 on pressing send. One derivation now answers both for the screen that offers a method and for the route that honours it.
- **A restriction told its subject it existed.** Restriction is invisible to the restricted party by design — that is the whole difference between it and blocking. `GET /api/users/:id/public-profile` stripped the flag, but every *other* handler returning a relationship state sent it raw, so muting somebody who had restricted you made your own Add-friend button disappear. `viewerRelationshipState` is now the only shape a handler may send; `relationshipState` remains for the internal gates that must see the truth.
- **A profile headline escaped the privacy setting.** `profile_headline` and `profile_highlights` shipped on the public baseline while `bio` sat behind `profile_visibility` — and they are the same kind of thing, free text under the account holder's own name. So a student with a private profile still published one line to every member. They are now furniture of a *distinguished* account: refused outright for an ordinary one, and gated by the privacy setting even if a value reaches the column another way.

### Changed

- **External volunteer hours are tracking only.** The verification apparatus 1.3.0 introduced — a `status` column, an admin review queue, and the `service.verify.external` capability — is removed by migration 032, which rebuilds the table under the six guards ENGINEERING_GUIDE §8.3 requires. It was inferred from the existence of that capability rather than asked for, and the inference was wrong: these are a student's own notes about their own afternoons, and a review queue turns a notebook into an application form. Entries can now be **edited** at any time, because nobody else's judgement is stored on one. Self-reported totals are shown to the account itself and to nobody else, and `lastVolunteeredAt` no longer counts them — a figure nobody checked is not evidence that somebody is still active.
- **Recovery codes can be saved as a `.txt` or a `.png`**, both generated entirely in the browser from values already on screen. No request is made, no code reaches a URL, and the object URL is revoked after the download starts. The image carries its own white background rather than reading the theme: it is opened later in a photo viewer that knows nothing about `data-theme`, and a dark-mode export would be unreadable exactly when it is needed.
- **Discovery moved into Opportunities.** "Find people" is gone as a navigation entry; one field with a scope control now searches people, organizations and opportunities together, and `/directory` redirects so existing links still land. The two searches used to live on separate pages and answered the same question.
- **A Logged hours page**, reached from the Dashboard, showing confirmed WeVolunteer service and self-reported external entries as two clearly separated lists. No navigation entry was added for it.
- **The account menu is Profile / Notifications / Settings / Sign Out.** Edit profile moved onto the profile page it edits, and is now reachable from a student's own public profile too. On mobile, Profile lives in the existing account sheet rather than a fifth tab.
- **Owner and partner accounts get a distinguished profile**, derived from `users.role` alone — no username is special-cased, and the leakage suite asserts the name and username are ignored entirely. The treatment is **additive**: the platform's owner is a high-school student who volunteers, so their hours, skills and hobbies render exactly as anybody else's do.
- **One mark everywhere.** `--brand-mark-bg` / `--brand-mark-ink` are declared once and deliberately not overridden under dark mode, so the in-app badge matches `favicon.svg`, the new web manifest, the Safari mask icon and the header of every transactional email — none of which has a theme this application can read.

## [1.3.0] — Unreleased

> **The member directory.** Every profile is now discoverable by any signed-in
> member at `/users/@username`, and `users.profile_visibility` — a column that
> existed since v1.2 and gated nothing — finally does. What it protects has
> changed: a private profile is no longer an invisible one. See "Public profiles"
> below for the field-by-field split, and read it before assuming the old
> setting means what it used to.

### Added

- **Public profiles, at `/users/@username`** — a volunteer profile that another member can actually open: name, general area, hobbies, skills, organizations, and the participation counts. Deliberately not a social network — no followers, no feed, no likes — for the same reason `VolunteerProfile` has never had them. The routing is an authenticated app route rather than a `PUBLIC_ROUTE`: "public" here means visible to the school community somebody volunteers alongside, not to the open internet, and a signed-out crawlable index of minors by name and area is not something the word should be allowed to smuggle in. Every field goes through one allowlist serializer (`server/profileSerializer.js`), so a new column on `users` is invisible until somebody edits that file to say otherwise — a denylist is wrong by default the moment the schema grows, and `date_of_birth`, `graduation_year` and `tfa_secret` all arrived on that table after the old handlers were written.
- **Privacy redesigned rather than removed** — the old setting hid the whole profile, which made the directory useless and forced a student to choose between being findable by the people they volunteer with and exposing their school and grade to everybody. Now the profile is always discoverable and the SENSITIVE fields are what privacy withholds: school, grade, graduation year and bio go behind it; name, general area, hobbies, skills, joined date, last-volunteered date, participation counts and credited hours are the public baseline. An email address is never shown to another student at any setting — choosing a public profile is not consenting to publish an address. Organizers are not exempt; the same fields are withheld from them, and only `user.contact.read` (administrators) sees through it.
- **Signups versus attendance, as counts** — "Events signed up" and "Events attended", and deliberately **never** a percentage. "1 of 2 — 50%" reads as a verdict on a person when the evidence behind it is one missed shift, and a reader cannot un-see the number. The definitions are drawn against the real lifecycle and documented in `server/volunteerStats.js`: signed up counts an *accepted* application to a non-cancelled event whose shift has ended, so being turned down never appears on a student's record and withdrawing in time — which the API already refuses to allow late — is not penalised. `eventsAwaitingRecord` is published alongside them, so a gap between the two reads as "the organizer has not confirmed yet" rather than as absence. Missing attendance is never counted as absence, anywhere.
- **A people and organization directory** — one search box over both, because a student typing "NHS" does not know whether they are looking for a club or a person. Results are badged so the two are never ambiguous. Debounced, aborted on a newer keystroke (the debounce is the performance fix, the abort is the correctness one), bounded at 25 results however large a `limit` is requested, and with `%` and `_` escaped so the search box cannot be turned into an enumeration endpoint.
- **Friend, mute, restrict, block and report, from a profile** — four different jobs, not a severity slider, each documented in `server/relationships.js`. Friending is a *request* that the other person accepts, and that is a safety decision rather than a social one: an accepted friendship is what unlocks knowing when somebody signs up for things, so a unilateral follow would let any account subscribe to a minor's schedule without them agreeing. Muting is silent and one-sided. Restricting withdraws the friendship, stops future requests, and is invisible to its subject — otherwise it is just a quieter block. Blocking keeps its existing home and its existing asymmetry (students block; organizers do not).
- **Friends are told when you sign up — if you allow it** — the privacy decision is made in one query *before any notification row exists*, so a notification that should not be sent is never written, and there is nothing for a later endpoint to leak by forgetting to re-apply a filter. Four conditions each independently empty the recipient list: the setting is on, the friendship is accepted, the recipient has not muted you, and neither of you has restricted or blocked the other. An organizer's private attendee visibility also suppresses it entirely. The notification names the opportunity and never the time or the place.
- **Organizations** — a club, chapter or programme that runs volunteering; "Example Valley Volunteering Club", "NHS". Only organizers and administrators may create one. Membership is scoped and is never compared against `users.role`: a `manager` may edit the organization and publish its events, and *which* organization is an ownership question answered against the membership table, exactly the way `event.edit.own` is paired with an `organizer_id` check. Students search, view, join and leave. The last manager cannot leave or demote themselves, because an organization nobody can manage is recoverable only by an administrator and only if somebody notices.
- **Events can belong to an organization, and its members are told** — one query for the roster and one transaction for the whole fan-out, never a query per member. Attaching an event is a membership question, not a capability one: `event.create` says this account may create events, not that it may publish under the National Honor Society's name and notify three hundred people.
- **Events that credit no hours** — a donation drive, a supply sort, a participation activity. A boolean on the event, **not** an hours value of zero: `credits_hours = 0` says "this event does not measure service in hours", where a stored 0 would say "this volunteer earned nothing", which is both false and demoralising. Attendance is still recorded and still counts toward events attended.
- **Organizers can credit the hours actually completed** — a volunteer rostered for four hours who leaves after two and a half did two and a half. The scheduled duration is now a default rather than the only possible value. There is deliberately no "left early" checkbox on its own — a boolean cannot say *how* early — so the number is the source of truth. An hours-only change is a correction: it requires a reason and lands in `hours_ledger` as `adjusted` rather than as a second `credited`, which is the difference between a trail that reads as two awards and one that reads as what happened.
- **External volunteer hours** — service done somewhere WeVolunteer does not run, logged by the student against their own record. Emphatically **not** an event: it has no slots, no applications and no roster, so there is no code path by which one can be listed as an opportunity, applied to, or attended — the guarantee is structural rather than a rule somebody has to remember. Self-attested, labelled as such on every surface, verifiable by an administrator holding the `service.verify.external` capability the platform already had, and never summed into credited hours.

### Changed

- **Auto Select weighs attendance reliability, as a deliberately small second factor** — a raw show-up percentage is a terrible instrument in both directions: 1 of 1 is 100% and is also one data point, while 1 of 2 is 50% and is also one missed shift, which for a fifteen-year-old is a bus or a bad week. Both are the same statistical mistake, so both get the same fix — the rate is smoothed toward a prior with a pseudo-count of five. A volunteer with no recorded history gets a multiplier of exactly 1.0 and is neither helped nor harmed, which is what made the term safe to add on the day it shipped. The bounds are `[0.95, 1.03]`, derived against the hours curve rather than chosen by feel, and the tested guarantee is stated for its real domain: **below 200 credited hours — eight times this district's Silver threshold — a 50-hour difference in hours outweighs any possible difference in attendance.** Shifts whose attendance was never confirmed are excluded from the denominator, so an organizer who forgets to close out an event cannot make their volunteers look unreliable.
- **`profile_visibility` is writable** — the column shipped in v1.2 with no API that could set it, no code that read it, and a default of `private` on every row.

### Fixed

- **Auto Select's hours weighting was inert, and had been since it shipped** — `computeDraw` aliased its column `total_hours` while `performWeightedSelection` read `totalHours`, so every applicant arrived at the curve with `Number(undefined) || 0` and was handed the identical maximum weight of 10.0. The draw was a uniform lottery. The organizer UI described weighting, and `docs/legal/policies/07-volunteer-record-policy.md` published the formula as policy, for the whole time it was not happening. Nothing failed, because no test asserted that a lower-hours volunteer actually wins more often — `weighting.test.js` now does, over the real curve.
- **A student's itemised service history was returned to every authenticated caller** — `GET /api/users/:id/profile` included each past event's title, its **location** and its exact start and end times, with nothing gating it. For a minor that is a week-by-week record of where they have been, assembled by the platform and handed to anybody with a login. It is now behind the same gate as their contact details, and the counts replace it publicly.
- **A friend-signup email disclosed a named minor's date and location** — the in-app copy was written to name no time and no place; the email builder appended its event-details card to anything whose payload carried an event id, which undid that into an inbox that may be shared, forwarded or retained indefinitely. The card is now an explicit per-kind allowlist.
- **The Settings privacy screen described a protection that no longer existed** — and had no control on it at all.

### Added

- **The owner can see the application as another role** (`/admin/persona-preview`) — the platform owner sees a version of this product almost nobody else does, which makes them the worst-placed person to notice that a student's view is broken. A preview renders it as a plain member of another role. It is server state — two nullable columns on the owner's own row, resolved on every request — because a client flag would be a lie and a hazard at once: the server would go on answering with the owner's real capabilities, so the preview would show a student's navigation over an administrator's data, and a role held in client-controlled storage is the shape of a privilege-escalation bug even when today's implementation happens to be safe. It **cannot escalate, for any value, from any writer**, and not because the routes validate their input: `can()` now intersects the effective role with the real one, which is re-read from the database every request, so a `preview_persona` of `super_admin` written onto a student's row by a bug, by SQL injection or by a mistake in this repository grants that student exactly nothing. That rule lives in the kernel rather than at the places that set the field, because there are several such places and a rule enforced at each is one that will eventually be missed silently. Per-user grants are ignored while previewing — a grant extends what *this* account may do, and answering "what does a plain student see" with this account's extras defeats the only job the feature has. Starting one needs `persona.preview`, which is SUPER_ONLY and therefore ungrantable; leaving one needs `persona.preview.exit`, which **every** role holds, because a preview narrows the caller and an owner-only exit would be lost the instant the owner previewed as a student. The banner carrying that exit renders on every page for the same reason, and a preview expires after thirty minutes so a browser closed mid-preview repairs itself. Authentication is untouched: whether a second factor is required is decided from the real role at sign-in, before a principal exists.
- **The platform owner has a profile** — `/profile` said "No service record for this account", which was accurate and a dead end. Both existing profile endpoints filter by role in SQL, so the owner matched neither and an honest empty state was chosen over a 404 dressed as a profile; the result was that the one account which cannot be deleted, cannot be demoted and holds every capability had the emptiest page in the application. The new page is built entirely from `/api/auth/me`, so it needs no endpoint and no widening of the two that exist. It shows no service hours deliberately — a "0.0 hours" tile would not be an achievement missing but a category error, since this account administers the programme rather than participating in it.

- **Two-factor authentication** — TOTP or emailed codes, with single-use recovery codes, and mandatory for administrators. A correct password no longer produces a session for an enrolled account: it produces a short-lived pre-authentication grant that is worthless on its own (`authenticateToken` refuses any token carrying `preauth`), and the session exists only after the second factor is accepted. TOTP secrets are stored AES-256-GCM encrypted under `TFA_ENCRYPTION_KEY`, never in plaintext, behind a versioned `v1:` envelope; production refuses to boot without the key and development falls back to a known insecure one with a warning. Enrolment, disabling and recovery-code regeneration all sit behind step-up re-authentication. An administrator without a second factor is refused by every capability gate and shown a wall explaining why — the enrolment routes deliberately use only `authenticateToken`, so the wall is never a trap. An administrator may not remove their last factor, and `bin/reset-2fa.mjs` exists for the case where the device is genuinely gone: it clears the enrolment, deletes the recovery codes, ends every session for the account, and writes a `TFA_RESET_CLI` audit row against the reserved `system-cli` actor. It is a shell command rather than an endpoint because the check it cannot perform is "is this really you", and requiring filesystem access to the database is the strongest authentication this application has — whoever can run it already controls the data the account protects.


- **Event tags** — organizers describe an opportunity in their own words: `#AnimalShelter`, `#SATPrep`, `#CommunityGarden`, whatever is true of the event. No fixed vocabulary, which is the owner's recorded answer to Q-2 — one category per event cannot express that a food drive run by the honour society is Food AND School AND NHS, and an enum forces the organizer to pick one and lose the rest. `events.category` is kept and untouched: it is CHECK-constrained so every event has one, the Auto Select draw reads it, and tags are optional. Stored twice — a normalised key for finding and the typed label for reading — so `#NHS`, `#nhs` and `# NHS` are one concept that still renders the way its author wrote it, while `AnimalShelter` does not come back as `animalshelter`. Bounded at eight per event and thirty characters, letters/numbers/spaces/hyphens in any script, with the count checked on the raw list so ten thousand tags that collapse to one concept are refused on the request's shape rather than after normalising all of them. Filtering is server-side in the existing browse query as an `EXISTS` semi-join — not a JOIN, which would multiply rows and inflate the `COUNT(*)` behind pagination — and selecting several tags widens **within** the facet while still narrowing against every other filter, which is the faceted-search convention and the only usable choice given free text: requiring all of three organizer-typed tags returns nothing almost every time. Existing tags are offered as suggestions so reuse is the easy path, and nothing is ever restricted to them; there is deliberately no tag-administration surface, because that is the taxonomy-management product Q-2 answered against.
- **The Impact Dashboard reports what organizers tagged** — the improvement Q-2 was actually about. `events.category` is five fixed values and cannot answer "where did the effort go": `5K` is a format, `Fundraiser` is a mechanism, and `Other` is a shrug a large share of real events land in. The tag breakdown sits beside the category one rather than replacing it, because tags are optional and a tag-only view would silently omit every untagged event. It carries the same five-volunteer suppression floor as every other breakdown — and that floor matters more here, since an organizer-typed tag can name a room where a category names a sector, which is the privacy hazard Q-2 flagged before tags were built. The section declares that its hours **overlap**: an event counts under each of its tags, so the column sums to more than the platform total, and that is said above the bars rather than left for a reader to discover by adding them up.
- **One date picker, used everywhere** — five screens each rendered a bare `<input type="date">`: signup's date of birth, the calendar, the audit-log range, event creation and the suspension form. A native date input is a different widget in every browser engine and accepts none of the application's design tokens, so in dark mode its calendar chrome stayed light. There is now a single `DatePicker` with no new dependency (`Intl` and `Date` are enough), and both themes fall out of the existing tokens with no second code path. Signup gets month **and year** selects and opens on the latest permitted date, because a month-by-month calendar for a date of birth is hostile — a 1979 birthday was roughly 560 arrow presses. No `Date` is ever constructed from an ISO string in the component: that parses as UTC midnight and is the off-by-one-day bug the suspension form already documents. `1979-02-30` is refused rather than silently rolled forward to 2 March, because on a date of birth a silent misread has a legal consequence. Real `role="grid"` with the full date as each cell's accessible name, a single tab stop per the ARIA grid pattern, arrows/PageUp-Down/Home-End, Escape closing and returning focus to the trigger, and 44px touch targets. The audit-log range stays two independent pickers on purpose: the common query there is open-ended, and pinning the second picker's minimum to the first makes correcting a mistyped start date impossible without clearing both.

- **Platform Impact** (`/admin/impact`, `GET /api/admin/impact`) — the platform-wide figures, as an internal view for the platform owner. This **replaces the public community page** described further down this section; see *Changed* below for why that page is gone and what happened to its data. Two charts, each plotting one quantity against one axis: hours credited by month, and hours by category. Suppressed buckets are drawn and explained rather than dropped, so a gap reads as "too few people to describe safely" instead of "none". Snapshot export builds a self-contained SVG from the same data the page rendered, reading the resolved design tokens out of the live document — so a dark-theme export is dark because it was told the colour, not because a screenshot caught it. It touches no CSS at all, which matters on a platform that already prints certificates and transcripts.
- **The Moderation Center is a way in, not a second dashboard** — an index of every administrative area this account can open, each with a sentence saying what it is for, filtered by capability and re-checked at the destination. It fetches nothing, so it is instant and cannot be stale. An administrator sees three areas; the owner sees seven, and that difference is the authority boundary drawn honestly. The name moved here from `/`, which is now called Dashboard for every persona: the page there was mostly not moderation, and `/` meaning something different in the rail for one persona than for the other two made "open your dashboard" unanswerable without first asking what kind of account somebody had. Nothing on that page changed.

- **Public community figures** (`/community`, `GET /api/public/impact`) — *(superseded — see Platform Impact above and Changed below. Kept for the record.)* three of the four reasons the impact figures exist (marketing, grant applications, community trust) are about people who do not have an account and are not going to make one. A grant reviewer will not sign up, and a link that asks them to is a link they close. The page publishes four totals — volunteers, hours, events completed, organizations supported — plus the share who came back for a second, *different* event, each carrying the sentence that says what it counts. The definitions travel in the payload rather than living in the client, so a definition cannot drift from the query that produced the number. It is a separate handler rather than a relaxed gate on `/api/impact`: that endpoint answers to somebody the platform can name, this one answers to anybody at all, and `buildPublicImpact` names the fields it emits rather than filtering the private payload — so a breakdown added to the dashboard later cannot arrive here by inheritance. No category, month, place or per-volunteer statistic is published, and the endpoint takes no parameters, because a date range is a way of asking about smaller and smaller groups until a figure describes one person. The same five-volunteer floor every other breakdown uses is applied to the totals themselves: a total over a whole population identifies nobody, and that stops being quite true when the population is four people at a named school. Below the floor the page says so instead of showing zeros — "0 volunteers" is a different claim from "not published yet", and a false one. Linked from the sign-in page beside the policies, because a public page nobody can find from the front door is a private page with extra steps.


- **Administrator invitations** (§4.3) — an owner can invite somebody to become an administrator, and the invitation is worth nothing until it is accepted from the address it was sent to. The token is stored as a SHA-256 hash and never returned to the inviter: an inviter who keeps it can accept from an address they control, which defeats the binding the whole feature rests on. Authority comes from the **verified** address rather than the token, so a forwarded or intercepted mail confers nothing. Every failure to redeem answers identically — never existed, expired, used, revoked, replaced, wrong address, unverified address — because a live invitation is administrator authority awaiting collection and distinguishing the cases is a probe for one; the real cause goes to the server log so an operator can still diagnose it. One pending invitation per address, enforced by a partial unique index rather than by application logic, because "check then insert" is a race whose failure mode is two live tokens after which revoking one leaves the other working. Creation is owner-only and step-up gated; revocation deliberately is not, because it only ever removes authority.
- **Community impact figures** (`/impact`) — what this community has actually done, counted from confirmed attendance and never from sign-ups. Four totals, how people take part, where the effort went and a month-by-month view. Every figure carries the sentence saying what it counts, because "318 hours" invites "hours of what, claimed by whom" and a page that leaves that unanswered is one somebody checks once and then stops quoting. `totalVolunteers` counts people who turned up; `returningRate` counts a second DISTINCT event, since two shifts at one event is one commitment; a median sits beside every mean so a reader can tell a broad programme from a narrow one with a star. Derived on every read and never stored, the same rule as credited hours and for the same reason. **Every breakdown is suppressed below five volunteers** — the population is mostly minors and an aggregate over a small group is not anonymous, so "one volunteer, Healthcare, March" is a specific child to anybody who knows the school. Suppressed rows read *Withheld* rather than disappearing: a reader who sees a gap knows something was held back, while a reader who sees no gap believes they have the whole picture. Platform-wide totals are never suppressed, because a total over everybody identifies nobody. Geography is a count of places and nothing else, since `events.location` is free text that routinely names a building. The endpoint takes no filters, deliberately — a date range is a way to ask about smaller and smaller groups until a bucket describes one person.


- **A suspended person can read the decision, appeal it, and sign out** — a suspended account was refused a session outright, so the whole product answer to "why can I not get in" was one sentence on the login form pointing at an email address. Everything they had actually been told lived in a single notice sent at the moment of suspension: lose it, never receive it, or read it a week later on a borrowed phone, and there was nowhere to look. Most of the people this happens to are minors. Signing in now succeeds and lands on a screen carrying the reason verbatim, when it started, whether it ends and when — and an appeal form, because the Community Guidelines promise one and an appeal the suspended person cannot reach is a promise made to nobody. The session reaches four routes and nothing else, matched by exact method and exact path with no prefixes, so a suspended administrator is a suspended account first. The refusal moved below the password check, which it had to — a session must never be issued to someone who has not proved who they are — and that closed the enumeration oracle the previous entry under Security describes.
- **The Audit Explorer reads like a record instead of a table dump** — actions were rendered as stored, so a page of `ACCOUNT_SUSPENDED` and `REPORT_EVIDENCE_VIEWED` in caps made every row look like every other row and put "somebody read a student's private messages" at the same weight as a routine approval. They read as sentences now, with a tone ladder marking the few things this platform can do to a person that they cannot undo. The timestamp shows a time as well as a date — a busy afternoon was five rows reading the same date, and the ordering, which is the entire point of an append-only log, was invisible. The `details` sentence somebody wrote at the time is on the row rather than hidden behind a View button.


- **A moderator can read the evidence a report preserved** — `report_evidence` froze the message bodies at filing, database triggers made them immutable, `report.evidence.read` gated the read and the endpoint logged every access. No client code called it: the Moderation Center rendered the evidence *count* ("1 message preserved as evidence") with no way to open it. So a moderator deciding whether to suspend a student could see that evidence existed and could not read it, and the Youth Safety Guidelines' printed promise — "this is the one situation in which an administrator reads private messages, and it is logged" — described something the product could not do. The report detail view now shows the record, the preserved messages read-only, and the append-only action history. Evidence is fetched only when asked for, never on open, because the server logs a disclosure on every call and prefetching would manufacture records of reads nobody performed. The bodies are deliberately absent from the report-detail response: `report.resolve` and `report.evidence.read` are separate capabilities so a per-user grant can create a triage-only helper who works the queue without reading a student's private messages, and folding the bodies in would have collapsed that split silently.
- **The moderation action history is readable** — `moderation_actions` had been written on every status change, reprioritisation, assignment, resolution, self-review and evidence read since v1.2, and read back by nothing; the only way to see any of it was to open the database by hand. `GET /api/admin/reports/:id` returns it as a timeline, so a moderator picking up a report can tell that it has already been decided once and reopened — which is precisely the context that changes what they do next.
- **Warnings reach the person they are about** — `warning_issued` has been in `REPORT_RESOLUTIONS` since v1.2 and "Warning issued to the person reported" has been in the resolution dropdown for just as long. Choosing it wrote a word on a closed report and told nobody, so the platform's own record said a warning had been issued while the only party it concerned had no idea — worse than no warning at all, because the label is what justifies the next escalation. A warning is now a mandatory notice delivered whatever the account's email preference says, with the moderator's words shown verbatim, an audit row naming who issued it, and no change to the account: the notice promises "nothing has been removed", and that has to be true. A second warning is allowed rather than refused, because the repeat *is* the escalation. New `user.warn` capability, split from `user.suspend` so a triage helper can tell somebody to stop without being able to lock them out.
- **Suspensions can have an end date** — every suspension the platform could express was permanent until an administrator remembered to lift it, so a week-long suspension for something a student did once had to be recorded as indefinite, and the only thing between "one week" and "for ever" was somebody's memory. `suspended_until` is now stored (NULL still means indefinite, which is what every existing row has always meant — no backfill, because inventing an expiry would silently convert a safety suspension into one that lapses). The deadline is authoritative in the **data**, not in a scheduled job: the predicate derives "suspended right now" on every read, so access returns the instant the clock passes it whether or not any background work ran. A process that was down over the weekend cannot leave somebody locked out past their own end date. An unreadable deadline fails **closed**. The person is told when it ends, in the notice sent to them.
- **An administrator can message a student or an organizer** — `eligibleRelationship` has had an admin branch since private messaging shipped, which is what made this look built. It was not: `resolveConversation` always wrote the row between `student_id` and `organizer_id`, so an admin who opened a conversation was not a participant and got 404 on both read and send. Granting `message.send` had been tried and reverted, correctly — it replaced a permission error with an empty inbox, because the shape of `conversations` was the real problem. The table now carries a `kind` (`student_organizer` | `admin_student` | `admin_organizer`), the three columns an admin thread cannot fill no longer require a value, and membership comes from `conversation_participants`, which already existed and which the authorisation check already read. Nobody is put in the `organizer_id` slot: that would state in the data that an administrator is the event's organizer, and would inherit the rule that turns a thread read-only 30 days after the event ends — which would silently close the one channel a student has for reaching an administrator, including about an appeal.
- **An administrator can undo a suspension they imposed** — `unsuspendUser` existed and was reachable from exactly one place: the appeals queue, when an appeal is upheld. So the only route to reversing a suspension ran through the suspended person formally contesting it, and somebody who suspended the wrong account had to wait for a student to appeal something the administrator already knew was wrong.

- **Conversation reports are readable for the first time** — `conversation_reports` had been write-only since it was created: two INSERTs and no reader anywhere in `server/`, so the most safety-critical report type on the platform, the one the Youth Safety Guidelines point every student at, landed in a table nobody could open. Three routes now exist — the queue (`GET /api/admin/reports/conversation`), the preserved evidence (`GET /api/admin/reports/conversation/:id/evidence`, behind a new `report.evidence.read` capability and audit-logged on every read), and resolution (`PATCH /api/admin/reports/conversation/:id`). Deliberately minimal: assignment, notes, categories and the fold into the main queue belong to the moderation-queue release. Resolution had to ship now regardless, because the evidence holds added in this release are scoped to open reports and nothing in the product could close one. Reading a student's private messages is now the logged act the Youth Safety Guidelines already described in print — until this release that sentence described something that could not happen, and so was not logged either.
- **The moderation queue distinguishes live content from a preserved copy** — a report now renders the target's live text, or the snapshot taken when it was filed with a note saying so, or an explicit "no copy of this was kept" for reports filed before snapshots existed. The previous behaviour showed the same words, `Deleted Comment`, for the last two, which reads to a moderator as "nothing to see here".

- **Error monitoring** — The application now records its own failures, end to end: server-side capture in the Express error handler, an unauthenticated intake endpoint for browsers, background-job capture, deduplication by fingerprint, a retention sweep, and a triage API. Until now a crash on somebody else's phone left no trace anywhere — the only diagnostic was a console line nobody could retrieve, and the only report was a user saying "it didn't work". Failures are grouped by a fingerprint over the source, kind, normalised message and route, so the same bug reported a thousand times is one row with a counter rather than a thousand rows. What is stored, and the reasoning behind each exclusion, is documented in `docs/ENGINEERING_GUIDE.md` §6.10.
- **Error dashboard** — `/errors`, for the platform owner only. Lists problems newest-first with their occurrence count and how many distinct people hit them, filters by status and source, charts occurrences over the retained 30-day window, and opens each problem for its redacted stack traces. Resolve, ignore and reopen are recorded with who did it. Operational guidance is in `docs/operations/error-triage.md`.
- **Client crash reporting** — React error boundaries and the global `error` / `unhandledrejection` listeners report to the intake endpoint. Deliberately bounded rather than best-effort: at most five reports per page load, deduplicated by message and first stack frame, never re-entrant (a failing report is never itself reported), and network errors are never sent at all. A reporter without those bounds turns one bad afternoon into a much worse one — a re-rendering broken component produces thousands of reports a second, and a whole school losing signal in the same place every afternoon would bury every real defect.
- **Error Experience** — 404, 403, 500, crash, chunk-load-failure, offline, expired-session and maintenance each get a designed page instead of a blank screen or a silent redirect. Six illustrated themes rotate per browsing session from a stored seed, so the personality is consistent while every individual screen still tells the truth about what happened; a theme is only offered for a failure it can honestly explain. Every one of them takes the viewport. A permission refusal was the exception — a contained panel inside a shell that still worked, on the argument that "ask your administrator" is advice you act on using the navigation a takeover removes — and that was reversed: a refusal shown as a card inside the running app reads as a page that failed to load rather than as a decision, and it leaves the nav pointing at a section the reader has just been told they cannot open. Serious failures are written flat, lead with whether your data is safe, and are enforced that way by a test rather than by taste.

### Fixed

- **Refreshing the page bought five more password guesses.** The step-up verification dialog counted down from five, said "locked out" at zero, and a browser refresh gave five more. Not a rendering bug, and hiding the counter would have left it exactly where it was: `attemptsRemaining` described one *challenge row*, a refresh opens a new row whose counter starts at zero, and the account ceiling was fifteen against a per-challenge limit of five — so the account really did have ten guesses left and the refresh really did work. The interface promised a limit three times stricter than the server enforced, and a lockout somebody clears by pressing F5 teaches that this application's limits are decorative. The two budgets are now one, summed across every challenge the account opened in the window, and a new challenge inherits the spent count rather than resetting it. Not a tightening in practice — the per-IP limiter already allowed five failures per fifteen minutes — what changed is that the account budget no longer exceeds the one the interface promises. An exhausted budget now says "wait a few minutes" instead of "please start again", because starting again is precisely what no longer helps.
- **A two-factor code that failed to send was reported as sent.** The mailer returns false when the relay is unreachable, and the sign-in code endpoint discarded that and answered `{ sent: true }` regardless. By then it had already retired every previous code and armed the sixty-second cooldown — so a user whose only second factor is email was told a code was on its way, had none, had lost the one they had, and waited a minute to be told the same thing again. A complete sign-in lockout reported as a success. It now answers 502 and names the two methods that still work.


- **The second factor accepted any six digits.** otplib v13's `verifySync` returns an object, not a boolean — `{ valid: false }` for a wrong code, which is truthy — and all three call sites assigned it straight to `isValid`. So `POST /api/auth/login-2fa` accepted any six-digit string: an attacker holding a stolen password met no obstacle, while the account holder believed they were protected. That is worse than having no second factor, because believing you have one is why somebody reuses a password. The same defect let anyone holding a session turn 2FA off, and confirm enrolment with a code the authenticator never showed. Now behind one helper that returns a real boolean and cannot be misread.
- **The brute-force cap on the second factor was bypassable, and it locked out honest users.** The pre-authentication token carried no `jti`, so HS256 produced byte-identical tokens for two sign-ins in the same second — and the attempt counter is keyed on the token's hash. An attacker could reset the counter by re-posting `/api/auth/login`, making five-guesses-per-grant into unlimited guesses; two legitimate sign-ins could lock each other out. Separately, the counter was written before the code was checked, so successful sign-ins counted as failures — twenty sign-ins in fifteen minutes locked an administrator out of their own platform. The token now carries a `jti`, only failures are counted, success clears the account's recent failures, and a per-account ceiling in a rolling window is what actually bounds the search.
- **Several ways to be locked out of your own account**: re-running enrolment overwrote a working secret while leaving 2FA switched on; an administrator could remove both factors in one call; and every QR code enrolled as an account literally named "undefined" (the option is `label`, not `accountName`, and the wrong key is silently ignored).
- **Password sign-in was unreachable** — the "Sign in with email" button set a URL mode that the mode resolver did not recognise, so it fell through to the picker and the entire email sign-in form was dead code. Signing in with a provider then hitting 2FA was a dead end for the same class of reason: the callback passed the state and the login screen never read it.
- **Five synchronous bcrypt calls in request handlers**, one of them comparing up to ten hashes per attempt — a build-failing guard whose message records a measured p95 of 3.8s on unrelated endpoints under load.
- **`config.js` called `process.exit(1)` from module scope** when `TFA_ENCRYPTION_KEY` was unset, killing the test runner rather than failing an assertion and taking out ~100 tests in files with nothing to do with 2FA. It now throws in production and warns in development, matching how `JWT_SECRET` has always behaved. Deciding to end the process belongs to the entry point, not to a module somebody imported for a constant.


- **A source comment was rendering as visible text on the Moderation Center** — `AdminDashboard.jsx` carried a thirteen-line block comment explaining why the reports queue sits above the analytics, written as a bare block comment in JSX **children** position. That is not a syntax error: in children position a comment is TEXT. So every administrator and owner opened the most important administrative page on the platform and read a paragraph of engineering prose about 720px viewports, above the safety queue. It survived the build, the linter, and 3,400 tests, and was found by looking at a screenshot. Two things now catch it: the client test teardown fails any test whose rendered output contains a comment marker, and — because a global check over rendered output is worth exactly as much as the render coverage beneath it — `AdminDashboard` now has a render test at all. It had none: it is stubbed in every test that would have mounted it, and the existing `AdminDashboard.order.test.js` reads the file as text rather than rendering it. The new file also covers a non-empty organizer queue, which is the exact condition that once threw `ReferenceError: UserX is not defined` and made the page unusable.


- **Two cross-feature escalation tests were passing because their URLs did not exist** — a new suite covering capability *combinations* originally probed `/api/admin/users/:id/promote-admin` and `/revoke-admin`. The real routes are `/promote` and `/revoke`, so Express answered 404, `status >= 400` was satisfied, and both tests reported that the platform owner was protected from an administrator while proving nothing whatsoever. The suite now asserts `not.toBe(404)` before asserting the refusal, and every owner-protection case checks the resulting database row rather than only the status — a refusal that still changed the row would satisfy a status check and lose the platform. The tripwire immediately caught a third case the same author added minutes later (`DELETE /api/admin/users/:id`), which turned out not to exist either; that absence is now asserted positively, because "no administrator can delete anybody" is the security property.
- **`server/email.reliability.test.js` could time out under full-suite load** — its per-IP limiter test makes twelve *sequential* HTTP round trips (sequential because a per-IP counter is what it measures, so they cannot be parallelised). Isolated the file runs in ~1.3s; under parallel load that one test was measured at 5133ms against vitest's 5000ms default and timed out, then passed on the next run. Nothing was hung and its assertion never failed — it ran out of clock. Given a measured 20s file budget, the same remedy and reasoning as `tooling.dbPath.test.js`. Flakiness on the gate every other gate depends on is a defect in its own right.

- **The privileged command-line scripts were changing a different database than the server** — `bin/grant-ownership.mjs`, `bin/revoke-ownership.mjs`, `bin/make-admin.mjs` and `bin/bootstrap-owners.mjs` each resolved their own path as `process.env.WEV_DB_PATH || server/wevolunteer.db`, and were invoked as plain `node bin/x.mjs`. Plain `node` does not read `.env` — only `--env-file-if-exists` does, and every other entry point in the repository has it — so the one variable that says which database is live was simply absent and the fallback won. Worse, `.env` sets a *relative* path (`../pilot.db`), which resolves against the working directory: from the server's cwd that is the live database, from a `bin/` script's cwd it is one level higher, outside the repository. Both files exist on the machine where this was found — 23 migrations and 18 users against 15 and 14 — because `new DatabaseSync` **creates** an absent file, so a privileged script wrote a fresh empty database and reported success about it. This matters more than a wrong path usually would: `bin/grant-ownership.mjs` is the only sanctioned way to create an owner, so the failure mode was an operator reading "Successfully granted ownership", signing in, and not being an owner — with the grant and its audit row sitting in a stale file nobody opens. It was caught only because an unrelated guard added days earlier (`assertSystemActor`) refused on a database that predated its migration; against a stale file that had run that migration the write would have committed silently. Path resolution now lives in one place, `bin/resolveDb.mjs`: it reads `.env` itself, anchors a relative value at `server/` so both callers mean the same file, refuses a path that does not exist rather than creating one, refuses a SQLite file with no `users` table, and prints the resolved path on every run including the successful ones — the whole failure was invisibility. A guard asserts no privileged script resolves or opens a database itself, because four private copies of one expression is why fixing `verifyHours.js` for the same bug in v1.2 did not fix these. Full analysis in `docs/audits/04-PRIVILEGED-CLI-DATABASE-TARGET.md`.
- **`bin/grant-ownership.mjs` told operators that ownership was "irrevocable"** while `bin/revoke-ownership.mjs` sits in the same directory and demotes an owner in one command. Overstating a consequence is not a harmless scare: an operator either avoids a grant they should make, or discovers the warning was wrong and reads the next one less carefully. It now says what is true — an owner holds every capability, cannot be suspended or demoted by an administrator, and can be revoked only by somebody with shell access to the database.
- **Three audit actions had no readable label** — `ADMIN_INVITED`, `ADMIN_INVITE_ACCEPTED` and `ADMIN_INVITE_REVOKED` were being written by the invitation routes and were absent from the Audit Explorer's label table, so they fell through to a title-cased fallback: the most consequential rows on the platform, somebody being handed administrator authority, rendered as the least legible. The filter derives its options from the trail itself, which is what let the gap open — a new action appears in the dropdown with no client change, so nothing failed. A static guard now scans every audit action the server can write and fails the build on any that reaches the client unnamed.
- **The nav called the Audit Explorer "Audit Log"** while the page heading and the permission-denied message both named it "Audit Explorer" — and the nav is exactly where somebody looks after being told which feature they lack.

- **The action filter offered actions nobody writes** — the Audit Explorer carried a hand-written list that had drifted from the code: it offered `ORGANIZER_APPROVED` and `ORGANIZER_DENIED` when the real actions are `APPROVE_ORGANIZER` and `DENY_ORGANIZER`, so those two filters could only ever return nothing, and it omitted `ADMIN_PROMOTED`, `ADMIN_REVOKED`, `REPORT_EVIDENCE_VIEWED`, `MODERATE_REPORT` and `ADMIN_CONVERSATION_OPENED` — between them most of what the table contains. On an accountability surface that is the worst class of bug: a filter that silently returns nothing says "this never happened" when the truth is "you searched for a string nobody writes". The options are derived from the trail itself now, so they cannot drift.
- **The permission-refusal screen sat in the corner of an empty viewport** — `App.jsx` had promoted the 403 to a takeover without `WEIGHTS` being updated to agree, so it rendered at the top level wearing the sizing written for a card inside a shell: the whole composition in the top-left above roughly 55% dead space, with a visible seam where the clipped background wash ended. Every test passed throughout, including one that asserted both halves of the contradiction in a single block.
- **The error screens pushed the only way out below the fold on a phone held sideways** — the stacked layout keyed on width alone, and 812×375 is narrow enough to stack but nowhere near tall enough to hold the result. All eight kinds were affected.
- **The "New message" dialog told three of its four audiences the wrong thing** — one sentence was shown to everybody: "You can message the organizer of an event you have applied to." True of a student and of nobody else. An organizer and an administrator message in the opposite direction, and a partner cannot message anyone at all. The administrator is now pointed at the Moderation Center, which is where contacting somebody about a report actually happens and what records the audit row.
- **The calendar gave the whole application a horizontal scrollbar** — two sections with `flex: 1` inside a `nowrap` row could not shrink below their own content, because a flex item's `min-width` defaults to `auto`. 85px of overflow on a phone, and because it landed on the document rather than any single element, every element measured as fitting.
- **The Administrator Roster was built on class names no stylesheet defines** — `.view`, `.view-head`, `.title-block`, `.view-title`, `.view-body`. The page rendered with no padding and no rhythm between its title, its primary action and its table. The guard that exists to catch this could not: it matched only the generated `s-xxxxxx` names from one historical migration, so 24 hand-written dead classes had accumulated behind that blind spot. The check now covers every static class name, closed against new ones.

### Security

- **OAuth no longer invents a user, and the mock transport is off unless asked for** — a developer holding working Google credentials pressed "Continue with Google", authenticated with Google for real, and landed on the signup form prefilled with a placeholder name and address. Two defects had to line up. `OAUTH_ALLOW_MOCK` defaulted to `!IS_PRODUCTION` — on in *every* process that was not production — and `verifyCallback` tests that flag **before** attempting the code exchange, so the mock shadowed the real credentials and the real integration could not be exercised at all. And the mock branch ended in a `catch` that fabricated an identity whenever the `code` was not JSON, which is exactly what a genuine opaque authorization code is. The default is now off unless the variable is literally `"true"`; the fabrication is gone and a `code` the transport cannot read is an error naming the remedy; and the transport lives in one module instead of being copy-pasted into each provider. The same shape of mistake had been fixed once before — the mock used to switch itself on whenever the client id was absent — and came back as a default, so the guard is now a source scan for the placeholder strings plus a subprocess boot of every value the flag can take. Production still refuses to boot with it enabled.
- **PKCE (S256) on both providers** — `OAUTH_REDIRECT_URI` points at the SPA, so the provider hands the authorization code to the **browser**, which posts it to the API afterwards. The code therefore exists briefly in a URL, in history, and in anything that can read the address bar, and the client secret alone does not bind it to the flow that requested it. The verifier is generated server-side, stored on the same single-use `oauth_states` row the replay check already consumes, and never sent to the browser — carrying it in the signed `state` would have handed it to exactly the party PKCE defends against. `plain` is not expressible.
- **An OIDC nonce binds each ID token to the sign-in that requested it** — audience validation proves a token was minted for this application; it says nothing about *which* authorization produced it, so without this a token captured from one of our own flows could be presented against a different one in flight. The existing CSRF nonce is reused: it is already 32 bytes of CSPRNG output, already stored server-side, and already single-use, which is every property the OIDC nonce needs.
- **Microsoft sign-in takes its identity from the ID token instead of a Graph lookup** — it exchanged the code for an access token and then called `graph.microsoft.com/v1.0/me`, which cost a second network round-trip inside a sign-in, required the `User.Read` consent scope purely to learn an address, and took the identity from a directory lookup rather than from the signed assertion issued for that specific authorization — so there was nothing to compare a nonce against. The ID token's `aud`, `iss`, `tid`, `exp` and `nonce` are all checked; the scope is now `openid profile email` and nothing more. The signature is deliberately not verified, which OpenID Connect Core §3.1.3.7 permits for a token obtained directly from the token endpoint over TLS with client authentication — the comment says so, and says what would have to change first if that ever stops being true. `MICROSOFT_TENANT_ID` restricts sign-in to one directory, enforced both in the authority URL and again on the `tid` claim, so a stale or hand-assembled `common` URL cannot silently widen sign-in to every Microsoft account on the internet.

- **A correct authenticator code is no longer rejected, and a used one is no longer accepted** — the two halves of one change. `verifyTotp` allowed no clock skew at all: only the current 30-second step. Typing time, network latency and the server's own work before the check all push a submitted code into the past, so a code entered in the last second of a step was routinely verified in the next one and the user was told their correct code was invalid — measured, at roughly one enrolment test run in three. A second factor that refuses a correct code is not strict, it is broken, and it teaches people to turn 2FA off. One PREVIOUS step is now accepted, and deliberately not one in the future: every cause of a late code makes it older than now, while a future code means a clock genuinely running ahead, so `[30, 0]` fixes the real cases and halves the widening — the form otplib's own documentation calls RFC-compliant. On its own that would double the window in which an intercepted code can be replayed, and RFC 6238 §5.2 requires a verifier to refuse a second use of a code, which nothing here did. So the tolerance ships with a per-account high-water mark (`users.tfa_last_counter`, migration 029): a code that has signed somebody in cannot sign anybody in again, and neither can any earlier code. The window is wider and the guarantee is stronger than either previous state. Single use is enforced on the SIGN-IN path only — the enrolment and disable routes already require a live session and a spent, action-bound step-up grant, so anybody able to replay a code there controls the account already, while a shared mark would have meant not being able to sign in and change your 2FA settings inside the same thirty seconds. Guessing is unaffected: the bound is the attempt counters, not the window.

- **Ten bcrypt hashes no longer precede a rejected 2FA code** — `POST /api/2fa/enable` generated and hashed ten recovery codes at cost 10, roughly a second of CPU, and only then opened the transaction that checks the code — throwing all of it away when the code was wrong. The attempt counters bound how many guesses somebody gets, not what the server spends on each, so five wrong codes bought fifty bcrypt operations. The code is now checked before that work is done. The authoritative verification is still the one inside the transaction beside `spendChallenge`, because only there is it atomic with the enrolment; this is a cheap gate in front of it. It also narrows a real race: `verifyTotp` runs with zero clock tolerance, so hashing first meant a code generated near a 30-second boundary was verified in the *next* step and a correct code was refused — which is what made an enrolment test fail roughly one run in three.

- **A student's achievement history is no longer readable by the whole internet** — `GET /api/badges` and `GET /api/users/:userId/badges` carried no `authenticateToken`, no capability gate and no ownership check, so anyone with a user id could read that person's badges and the timestamp of each. The population here is mostly minors. It was invisible to `authz.completeness.test.js` Guard 2 by construction: the guard walks routes whose middleware *includes* `authenticateToken`, so a route with none was outside the set it examines. Both are authenticated now and both are declared in the route registry, so the guard sees them.
- **Deleting an account deletes the profile photograph** — the anonymising update nulled `avatar`, `bio` and `school` and left `profile_picture_url` pointing at a file it never unlinked. So a deleted student's photograph stayed on disk and stayed publicly served at a URL that had already been handed out, while the Data Deletion Policy promised in writing that it was gone. The column is cleared and the file removed; the unlink runs after the transaction commits, deliberately, because an unlink cannot be rolled back and doing it inside would let a later failure destroy a live account's photo.
- **The second factor is rate limited** — `app.use('/api/auth/login', authLimiter)` matches at path-segment boundaries, so it never applied to `/api/auth/login-2fa`, a sibling rather than a child. The two endpoints that actually verify the second factor were carrying only the blanket 600-per-15-minutes API limiter while the password step in front of them carried ten. The in-handler counters (five per pre-auth token, twenty per account per rolling quarter hour) are still what bounds guessing; this is the network floor underneath them, which matters because those counters are per *account* and without it one device could work through many accounts while each account's counter looked calm. Sending an emailed code additionally carries the per-IP mail ceiling, since `skipSuccessfulRequests` means a successful send — the request being abused — costs nothing.
- **Enrolling a second factor replaces the recovery codes instead of adding to them** — enabling TOTP inserted ten codes unconditionally, so an account that had already enrolled email 2FA came out holding twenty live codes and was shown ten. The other ten stayed valid, unseen, on a printout from the earlier enrolment, indefinitely — which is the wrong direction for a recovery credential: the set somebody believes they hold has to be the set that works, or "I destroyed my old codes" is not something they can make true.
- **Profile-picture uploads answer their own refusals** — multer's size and type rejections were uncaught, so a 6 MB photo or a PDF returned 500 "Internal server error", was logged as a server defect and was filed into the error dashboard. Users got a wrong message and the triage tool used to find real faults filled with ordinary mistakes. They answer 413 and 400 now, with the bytes checked by decoding them rather than by trusting the client's declared MIME type. Replacing a picture unlinks the previous file, which used to accumulate on disk and stay reachable at its old URL for ever; and the delete path, which built a filesystem path from a database column and was guarded only by `startsWith('/uploads/')` — satisfied by `/uploads/../../../etc/passwd` — now resolves the path and requires it to stay inside the uploads directory.

- **Reading a student's preserved private messages now requires a fresh verification** — it was the cheapest consequential action on the platform. Every action in the step-up registry was about the actor's *own* account: deleting it, changing its password, exporting its data. Downloading your own data archive required re-verifying; reading a child's messages required a session. The read was already logged twice, to two trails, in the same transaction as itself — so the accountability was in place and the deliberation was not. The grant binds the specific report, so one verification opens one report rather than becoming a five-minute key to every child's messages. Deliberately not made owner-only: on a small team the administrator *is* the moderator, and the capability is already split from `report.resolve` so a per-user grant can create a triage helper who never reads a body. Full review in `docs/trust-safety/03-EVIDENCE-ACCESS-REVIEW.md`.
- **Suspension no longer signs anybody out** — it bumped `token_version`, which invalidates every session, so a suspended student's next click was "Session expired, please sign in again" and they re-entered a password to discover they were locked out. That is the silent ejection the suspension screen exists to replace. It bought nothing: enforcement is decided per request from the database, so a live cookie for a suspended account reaches exactly what a fresh one does — the notice, an appeal, and sign-out. Every device is refused on its next request either way, which is what makes keeping them alive safe.
- **Privileged command-line actions have one audit mechanism and a real actor** — `admin_audit_logs.admin_id` is a foreign key to `users`, so the ownership scripts had been recording the *subject* as the actor: a bootstrap row read "this person granted themselves ownership", and since `admin_id` is what a report groups by, every CLI action was attributed to its own subject. Migration 022 seeds a reserved `system-cli` account that cannot be signed into and cannot be purged. `bin/make-admin.mjs` wrote nothing at all before this — administrator promotion was the only privilege change on the platform that left no trace — and now writes in the same transaction as the promotion.
- **Ownership can no longer be created by anything the application runs** — `seedSuperAdmin()` inserted a `super_admin` with a known password whenever DEMO_MODE was set. It was gated and convenient, and it was the only code in the repository capable of creating an owner. That is why it went: the platform's strongest defence against privilege escalation is not a permission check but the absence of a mechanism, and an invariant with an exception is a convention. Deleting it only protects new databases, so `db.js` also refuses to boot a demo database containing the seeded owner — the dangerous artefact is the row that already exists, whose password is a string in this repository's git history. A build-failing guard now fails on any server module that assigns the role, and is mutation-tested.
- **Owner accounts hold a password nobody knows** — the two bootstrap owners were created with a bcrypt hash of 32 random bytes generated in memory and discarded. No preimage exists anywhere: not in the repository, not in a terminal scrollback, not in a shell history. Each owner sets their own credential through the reset flow, which proves control of the mailbox — a stronger claim than a password handed over in a terminal. Addresses are script arguments and never written down; a test asserts the script hardcodes none.
- **Command-line ownership changes are on the record** — `OWNER_GRANTED` and `OWNER_REVOKED`, with `method=CLI` leading the details and the operator's login and host recorded. There is no product path to ownership, so "where did this come from" has exactly one answer and the audit row was not giving it. The row also states that the subject is recorded as the actor because a shell operator has no account, rather than leaving that to be misread years later.


- **A sign-in attempt discloses nothing about a suspension until the password is right** — the refusal named the end date, and that branch ran before the password was checked, so anyone who could guess an email address reached it. The date was removed first, which fixed the worst of it and left the weaker disclosure — that the account exists and is suspended — standing as an accepted product decision that `GENERIC_LOGIN_ERRORS` did not actually cover. The branch has since moved below `bcrypt.compare` entirely (see "A suspended person can read the decision" above), so account state is no longer observable without the password at all, and the date became sayable again to the one caller entitled to it: the person themselves, holding a session. The test that asserted the date was present is how the original disclosure was found.
- **A provider-only account could be locked out permanently by a suspension that had already expired** — both sign-in branches of the OAuth callback compared `account_status === 'suspended'`, and that column stays `'suspended'` until something normalises the row, which nothing on the OAuth path ever did. A student suspended for a week and signing in with Google was still refused after their week was up, and an account with no password has no other door — so not a delay but a permanent lockout, from an account whose sanction had expired, with nothing on screen to explain it. Both branches now ask the shared predicate and normalise the row on the way past. The guard meant to prevent exactly this had missed it because it *named* the two enforcement points its author knew about; it now scans every server module, and a stale exemption fails the build too, so one cannot outlive the code it was written for.
- **The OAuth credential guard is inherited rather than remembered** — refusing to mint an authorization URL without credentials was fixed at the point the URL is built, which is the right place, but it left the refusal a convention each provider had to remember. Both existing providers shipped without it once, and Google's absence was masked for months purely by having real credentials in `.env` — the defect is invisible in exactly the environment its author works in. The provider state matrix had the mirror-image hole: it looped over a hand-written list, so a fourth provider would have received none of the six state cases while the suite stayed green. Both now derive from the provider directory.
- **Permission refusals no longer send people to somebody powerless** — three of the six error themes told a refused reader that "your school administrator" could add them or change their badge. WeVolunteer is an independent platform and not a school district service, so a school administrator has no access to it, cannot see the refusal, and cannot act on it — the same correction already made to the suspension notice, which the 403 had kept. Refusals now also name the feature attempted, the reason, and who can actually grant it, with two cases where the obvious answer would be wrong handled explicitly: an organizer awaiting approval *holds* `event.create`, and `error.read` can be held by nobody but the platform owner, so promising a grant would be false.

- **A reported person can no longer destroy the evidence against themselves** — three foreign keys chained together (`conversations.event_id` → `events`, `conversation_reports.conversation_id` → `conversations`, `conversation_report_messages.report_id` → `conversation_reports`, all `ON DELETE CASCADE`), so deleting an event removed every conversation held under it, every safety report about those conversations, and the message snapshots written specifically to survive message deletion. Measured on a real database, not inferred: one report and one snapshot before, zero and zero after. The two existing guards on `DELETE /api/events/:id` refused only an event with attendance recorded or one already completed — and **grooming happens before the event runs, when attendance is zero by definition**, so the window in which the evidence was destructible was exactly the window in which the harm occurs. The organizer needed no privilege beyond owning their own event. Migration 011 severs the cascades and the route now refuses with `409 report_evidence_held` while any report naming the event, its comments or its conversations is still open. The hold applies to administrators too: it is about the evidence, not about who is asking.
- **A student who reported an adult no longer destroys their own report by deleting their account** — `reporter_id` was `ON DELETE CASCADE` on both report tables, and the retention sweep hard-deletes anonymised account shells at three years, so a victim's own privacy right silently erased the record of what had been done to them. The cascade is now `SET NULL` alongside a name snapshot taken at report time, which keeps the report *and* keeps the published three-year shell period true — holding the shell instead would have been the easier patch and would have made a published retention period false with no stated end.
- **Reports and evidence snapshots are now immutable at the database, not by convention** — SQLite triggers refuse any `DELETE` of a report or a snapshot, and any `UPDATE` of what a report says; only `status` may change, because a report that cannot be closed is a permanent hold on everything keyed to it. A test asserts that the code path somebody wrote behaves; a trigger asserts it for every path anybody ever writes, including a `bin/` script and a `sqlite3` session. `reporter_id` is deliberately excluded from the immutable column list — an FK `SET NULL` performs a real `UPDATE` and does fire `BEFORE UPDATE OF` triggers, verified by running it, so naming that column would have aborted the nightly sweep instead of the tampering.
- **A deleted comment no longer takes the report about it** — `reports` stored `target_id` with no foreign key and no copy of the thing reported, so the author of a reported comment could delete it, needing no privilege at all, and leave the moderation queue rendering the literal string `Deleted Comment` where the evidence should be. `DELETE /api/comments/:id` now refuses with `409 under_review` while a report is live, and the report additionally snapshots the body, author and author's name at the moment it is filed — the hold covers the investigation, the snapshot covers the decision after the hold lifts.
- **The retention sweep's own safety assertion ran after `COMMIT`** — so a sweep that destroyed certificates, credited hours or safety evidence would throw, issue a `ROLLBACK` against an already-committed transaction, have that error swallowed, and log one line reading `sweep failed` over a database that had permanently lost the one class of data the file promises to keep for ever. Detection without rollback is not a guard. It now runs inside the transaction, and `reports`, `conversation_reports` and `conversation_report_messages` were added to the tables it protects.
- **Purging an organizer's account shell would have cascaded into other people's credited hours** — `events.organizer_id` is `ON DELETE CASCADE`, so removing an organizer shell deletes every event they ever ran and cascades onward into `attendance`, `conversations`, comments and announcements. The purge exemption checked only the purged account's own attendance and certificate rows, and `attendance.user_id` is always the volunteer and never the organizer, so an organizer shell was never exempt however many students' service records hung off their events. Time-armed rather than live — nothing purges until three years after the first deletion — which is why it had to be found by reading the schema rather than by waiting for it.
- **Message retention no longer sweeps out from under an open investigation** — the exemption named only *snapshotted* message ids, and the snapshot is capped at twenty caller-named ids or the last ten messages, so message eleven of a reported conversation was deleted while the report was still open. The predicate now covers the whole live thread and has one definition, in `server/evidenceHolds.js`, because a second copy of it is a second way to lose evidence.

- **Error capture redacts before it stores, not on the way out** — the population using this application is mostly minors, and an error table is filled by exactly the code paths most likely to be holding somebody's data at the moment they broke. Messages are rewritten before the row is written: email addresses, JWTs, bearer tokens, step-up challenge ids, long hex runs and long digit runs are replaced, most-specific rule first so a JWT is recognised before the generic token rule eats its segments, and truncation happens last so a secret near the end of a long message is redacted before the cut rather than preserved by it. The user is stored as a one-way hash, never an id. The route is stored as a *pattern* — `/users/:id/profile`, never `/users/user-student-2/profile` — with query strings and fragments dropped before matching, which is what keeps a password-reset token or an OAuth `code` out of the table entirely. There is no request-body column at all: not "we don't populate it", but nowhere to put one, so a later change that seemed harmless cannot start filling it in. `context` is an allowlist rather than a denylist, because a denylist fails on the first thing nobody thought of.
- **The unauthenticated error intake is bounded in four independent ways** — it accepts a write with no session, deliberately, because the failures worth hearing about most are the ones that happen before a session exists: the login screen, a failed session check, a bundle that will not boot. Requiring authentication would hide exactly the class of bug the release exists to see. In its place: a dedicated rate limiter (20 per IP per fifteen minutes), an 8 kB body cap mounted path-scoped *before* the global 100 kB parser (mounted after it, the global parser wins and the cap does nothing — this was measured, not assumed), a ceiling of 500 distinct client-created groups after which the overflow is counted in a single row, and server-side route normalisation so no client-supplied string reaches the table. The limiter bounds requests from one address and does nothing about a thousand; the ceiling bounds rows and does nothing about request volume. Neither subsumes the other. Every response is `202` whichever of those applied — a distinct answer for "ceiling reached" would be a progress meter for an attack, and a failure status invites the retry that amplifies the flood.
- **Downloading your data export now requires re-verifying your identity, not just requesting it** — gating the request and not the download protected an archive that did not exist yet and left the finished one open. A completed export is kept for seven days, and `GET /api/privacy/export/status` tells any signed-in caller its id, so for a week after any legitimate export the whole archive could be collected by someone holding a borrowed session, having proved nothing — which is the very thing gating the request was meant to stop. Collecting it is now behind `requireAAL2('data.download')`, a separate action from `data.export` and bound to the job id, so one verification releases one archive and the dialog says "download your data archive" rather than "export all of your data". Every refusal — an archive that is not ready, has expired, or whose file is gone — is answered before the verification is spent, so a download that delivers nothing never costs you one. The download button now fetches the file rather than navigating to it, because a browser navigation cannot carry the verification header; that is why this endpoint could not simply be gated where it stood.

- **Disconnecting a sign-in provider now requires re-verifying your identity** — connecting one has required it since earlier in this release, and disconnecting is the same change to the same table in the opposite direction. The existing guard that refuses to remove an account's last remaining way to sign in prevents you locking yourself out; it does nothing about someone with a borrowed session removing a provider from an account that still has a password, which costs you the sign-in route you actually use and one of the two ways you could have proved yourself afterwards. It is now behind `requireAAL2('oauth.unlink')` with the provider bound, so a verification collected to remove one provider cannot remove another. The last-credential guard is unchanged and is still checked before the verification is spent — a refusal there does not cost a provider-only account the re-consent round trip it just completed.

- **Requesting a data export now requires re-verifying your identity** — `POST /api/privacy/export` was the only sensitive endpoint with no step-up at all: an authenticated request plus a rate limit, and a complete copy of everything the account holds became a downloadable file. Deleting the account, changing the password and changing the email address each demanded a credential; the one action that copies every record out — for a population that is mostly minors — demanded nothing, which made it the quietest thing a borrowed or stolen session could do, in a single request, without altering anything the account holder would later notice. It is now behind `requireAAL2('data.export')`, satisfied by the account password **or** by re-authenticating at a linked sign-in provider, and the grant is single-use. The gate is checked before the rate limiter so that an unverified first attempt does not spend the three-per-fifteen-minutes allowance, and the "an export is already in progress" refusal is answered before the verification is consumed, so a user is never asked to verify twice for an export that never started.

- **Connecting a sign-in provider now requires re-verifying your identity, whichever way you reach it** — gating `POST /api/oauth/link` covered only half the flow. That endpoint handles the case where you are *not* already signed in as the account being linked; when you are — the ordinary case, and what the Settings button does — the link was made inside the OAuth callback instead, on the strength of a live session and nothing else. Both halves require the provider's address to match the account's; what differs between them is the session. The row it writes is a new way to sign in: from then on the callback logs in anyone presenting that provider identity, long after the session that added it has expired. Gating one door and not the other would have made this release's own rule — adding a credential requires proving identity — true only of the door nobody walks through. The verification is now opened before the redirect to the provider and carried across it in the signed state, because a callback arriving mid-redirect cannot be interrupted to ask for one; it is bound to the provider actually being written, and spent in the same transaction. Signing in through an already-linked provider and signing up for a new account are untouched: neither adds a credential to an existing account.

- **Signing in from the "an account already uses that address" screen now connects the provider for you** — that screen offered to connect the account for a password, and once `POST /api/oauth/link` required a session it could not: a signed-out attempt is refused before the handler runs, so it reported *"Incorrect password."* whatever was typed. It now signs you in, asks you to confirm it is you once, and completes the link before handing you into the app — which is one verification, where the alternative of sending you to Settings to press the provider button again is the same verification plus a second round trip through Google or Microsoft to reach exactly the same result. Declining the verification still leaves you signed in, and says where to finish.
- **Correcting a mistyped email address from the confirmation wall works again** — the same defect, in the place it mattered most: that screen is the only way out for an account whose address has a typo in it, which is why `/api/auth/change-email` is on the server's email-verification allowlist at all. It asked for a password the endpoint no longer checks, and failed. It now uses the verification dialog, which also fixes a case the old form could never serve — a Microsoft account arrives unconfirmed and with no password, so re-consenting at the provider is its only way to prove anything.
- **Charts now describe what they actually show to screen-reader users** — the accessible table behind every bar chart had its caption and value column hardcoded to "Hours", while the visible chart is hidden from assistive technology. So the platform dashboard's *volunteers active by month* chart announced a count of people as hours, and any future chart of anything else would have done the same.
- **Retention was never enforced on a frequently restarted server** — `startRetentionWorker` armed a 24-hour interval and never ran the first sweep, so the earliest enforcement was a full day after boot. Any deployment restarted more often than daily — a pilot being configured, a nightly redeploy, a crash loop — enforced the published retention periods *never*, while `/health` reported ok and the Privacy Policy kept promising them. This is the gap the retention worker was written to close, reintroduced one layer above the code that closed it: publishing a period you do not enforce turns an absence into a representation about data handling. It now runs one sweep at startup before arming the interval, the same startup-recovery behaviour the Auto Select scheduler already had and documents. Safe at boot for the same reason it is safe at all — the sweep is idempotent, deletes only by age, and asserts its preserved tables before committing. The scheduler had no test coverage at all; the sweep it drives was thoroughly covered, which is why a correct sweep that nothing called looked green.
- **A failing retention sweep reached no dashboard and no alert** — the error handler was a bare `console.error`, so unlike every other background job (notifications, exports, Auto Select) a retention failure produced no `error_groups` row and was never eligible for the alert email. That matters most for the one thing the file exists to guarantee: retention holds `assertPreservedTablesUntouched`, the guard that fires when a sweep has touched certificates, credited hours or safety evidence. Detecting the most consequential event in the system and telling nobody is not a guard. Failures are now recorded against `retentionWorker`, so "the retention sweep is broken" is one line on a dashboard rather than a journal entry nobody reads.
- **A reinstated appellant was told they had been suspended for nothing** — the appeal token route falls back from the live `users` columns to the frozen snapshots on the appeal, but its query never selected `suspension_reason_snapshot`, so the fallback read `undefined` and collapsed to null; `suspendedAt` had no fallback at all. Because lifting a suspension NULLs the live columns, the moment an appeal **succeeded** — or a suspension was lifted while the appeal was still open — the student opening their emailed link saw no reason and no date. That is precisely the reader those columns were frozen for, and the one question the record exists to settle years later. Migration 015 and its tests were right the whole time and the row always held the value; the defect was entirely in the reading, which is why the existing test passed while asserting the column directly against the table.
- **Deleting your account manufactured false alerts** — deletion is a soft delete and does not clear `notification_jobs`, which has no `user_id` column to clear it by, so any queued mail was posted to the anonymised `deleted_<id>@system.local` address. That domain is reserved and resolves nowhere, so each such notification cost five delivery attempts across roughly an hour of backoff, then a permanent-failure row on the error dashboard and an alert email, plus a hard bounce per attempt against the district's sending domain. The damage is to the alert channel rather than the mail: a channel that cries wolf gets filtered, and then the next real outage is missed. The worker now drops a job whose recipient account is deleted, checked at send time so it also covers a job enqueued by a request that lost the race with the deletion. Deliberately narrow — `deleted` only, never "not active" — because a *suspended* account is the one the platform most needs to reach: the suspension notice carries the appeal link and appeal outcome notices are mandatory.

### Changed

- **The Moderation Center is the only administrative entry in the navigation.** Community impact, Appeals, Admin Roster, Audit Explorer, Errors and Platform Impact left the rail — **none of them was deleted**: every route is still registered, every page still exists, every capability is unchanged, and every one is reached through the hub, which already listed five of the six and now lists Community impact too. Grouping the rail got eleven entries down to something readable and could not fix what was underneath: the rail is the same list on every page, so seven administrative rows sat permanently in front of an audience that is mostly students, and the pages are related to each other in ways a flat list cannot show — an appeal is about a suspension that came out of a report. Nothing about who may open what changed; the four SUPER_ONLY pages are still SUPER_ONLY, asserted from the kernel's own table rather than by naming roles.


- **The community impact figures are administrative** — `/impact`, its nav entry and `GET /api/impact` were open to every signed-in account, students included, because `analytics.impact` was held by every role; its own comment described it as "a gate whose answer is currently yes for everyone signed in". They are now `admin` and `super_admin` only. The fix is the HOLDER SET, not the gate: the rail, the client route, the API handler and the refusal copy all already name that one capability, so narrowing who holds it narrowed all four at once with no route edits — which is what the capability was written to allow. `analytics.school` was rejected as a target because it gates two unrelated admin surfaces and repointing would make one word authorize three things; `analytics.platform` was rejected because it is SUPER_ONLY and would have excluded ordinary admins. `partner` is deliberately denied: a partner is an external organization, and handing one the full breakdown — categories, month-by-month participation, a cohort of minors at a named school — is the disclosure the deleted public endpoint made, with a login on top. `analytics.public` stays registered and reads nothing; it is where a figure chosen *for* an outside reader would go.

- **The community figures are private, and `/community` is gone** — "Public Community Metrics" was read as a page for strangers. It was not: the figures were wanted as an internal view of how the programme is doing. So the public surface is **removed rather than re-gated** — `GET /api/public/impact` is deleted and a test asserts it 404s, because a route that still exists is a route somebody can still call — and the figures moved to `/admin/impact` behind `analytics.platform`, which is SUPER_ONLY. The sign-in page no longer advertises them. A working revision of this change had the client route in `PUBLIC_ROUTES` carrying a `requiredCap` that nothing in that table reads, which would have rendered the administrator's dashboard shell for an anonymous visitor; it is an `APP_ROUTES` entry, gated by the same word the API names. **Corrected 2026-08-09:** that revision was never committed — `git log --all -S "admin/impact" -- src/routes/index.jsx` returns only the commit that added the route, already to `APP_ROUTES` — so no release ever carried the defect, and the server side was gated by `analytics.platform` throughout. The hazard the paragraph describes is real and still unguarded (nothing asserts which table a `requiredCap` route lives in), but it is a hazard, not an incident. What the same commit *did* fix, silently, was a dangling `React.lazy` import of the deleted `PublicImpact.jsx` left behind by the previous commit, which made the entire client bundle fail to resolve for six commits. The payload grew rather than shrank, and that is not a relaxed gate: `/api/impact` has always served the full figures to `analytics.impact`, which every signed-in role holds, so the owner could already read all of it — while the withholding cost them the month series, the one figure that answers "is participation rising". The five-volunteer floor on individual buckets is untouched; the floor that refused to publish *anything* below five volunteers is gone, because telling the owner of a four-volunteer programme "not published yet" about their own platform was a bug wearing a privacy argument.

- **The navigation rail's group headings are gone; the grouping is not** — two uppercase heading bars cost more vertical space than the three entries under one of them, on the one surface with no room to spare: on a phone the rail collapses to four buttons and a sheet, and the sheet had no scroll container, so the headings were pushing Sign Out off the bottom of the screen. They also named nothing a reader could go to — every heading was a row that looked like a destination, was not one, and had to be visually skipped. The sections survive as `role="group"` carrying the label as an accessible name, so a screen-reader user hears "Administration, group" exactly as before; sighted readers get a hair rule instead, which also survives the tablet icon rail that used to hide the headings outright and leave the groups indistinguishable.

- **Administrator 2FA enforcement defaults to ON** — `REQUIRE_ADMIN_2FA` was introduced defaulting to *off*, guarded by a production boot check. That made production safe and left staging, CI, a pilot deployment and a demo in front of a district silently running with administrator 2FA disabled, on a variable no env template mentioned — so a real deployment would also have hard-failed at boot on an undocumented name. Unset now means enabled, switching it off is an explicit `REQUIRE_ADMIN_2FA=false` visible in an env file, and production still refuses to boot with that value. The policy is composed in one place (`secondFactorRequiredFor`), which fixes an asymmetry worse than either setting: the flag gated *requiring* enrolment but not the refusal to *disable*, so with it off an administrator could not be made to enrol and could not un-enrol either.

- **The navigation rail is grouped, and event creation left it** — *(the two named heading bars this describes are no longer drawn — see above. The grouping and its capability-boundary reasoning stand.)* flat, it reached eleven entries for the platform owner, ordered by when each was added rather than by what it is for. Eleven undifferentiated rows is a list read once and thereafter scanned by muscle memory, which is when a rarely-opened but consequential page — the audit trail — stops being noticed. There are now two named sections, **Administration** and **Platform**, and they follow the capability boundary that already exists rather than inventing a taxonomy on top of it: everything under Platform is a SUPER_ONLY capability, checked before per-user grants, so no amount of granting puts an administrator there. The grouping therefore teaches the real authority boundary instead of decorating it, and an administrator seeing no Platform section has learned something true about their account. A one-entry group keeps its heading on purpose, so an administrator and an owner can say "Administration → Appeals" to each other and both be looking at the same thing. The mobile "More" sheet is grouped identically — it is where a phone user meets the administrative pages, so it is the surface where this matters most, and leaving it flat would have kept the long list on the screen with the least room to scan. Sections are derived from the same filtered list the flat rail uses, never from a second pass over the table, because two independent filters over one set of entries is how a page becomes reachable on a phone and unfindable on a laptop.

- **The error dashboard is reachable only by a capability that cannot be granted** — `error.read` and `error.write` are super-only, which means `can()` refuses them *before* it consults per-user capability grants. No `user_capabilities` row can reach the dashboard and `capability.grant` is not a path to it. The route is gated and the navigation entry is hidden by the same capability, and every one of the four triage endpoints re-checks server-side on each request — hiding the entry is presentation, not the control. Resolving or reopening a problem writes its audit row in the same transaction as the status change, so there is no status change without a record of who made it and no audit row describing a change that rolled back. Reads are deliberately not audited: `admin_audit_logs` has no retention sweep, and auditing every dashboard poll would create an unbounded write path in a table nothing expires.
- **A resolved problem that happens again reopens itself** — nothing verifies that a fix worked, so "resolved" records a belief rather than a fact. The next occurrence moves the problem's last-seen time and returns its status to open. A still-broken thing sitting quietly in a resolved list is worse than no dashboard: it converts a problem nobody knew about into one somebody believes is already handled.
- **The root path no longer answers 404 to signed-out visitors** — `/` had never been declared as a route. It worked by accident, because the signed-out catch-all was a blanket redirect to `/welcome`. When that redirect was replaced with a real 404 page — correctly, since the redirect made a typo'd link indistinguishable from a working one — the front door went with it. `/` is now a declared route rendering the welcome page, so both things are true at once: the root is a real page, and `*` still means "no such page".
- **Sensitive actions are gated on step-up re-verification instead of an inline password check** — `DELETE /api/auth/account`, `POST /api/auth/change-password`, `POST /api/auth/change-email` and `POST /api/oauth/link` each performed their own `bcrypt.compare` against the account's stored hash. Individually correct, collectively impossible to reason about: the endpoint that forgot its check looked exactly like the endpoint that never needed one, which is how the data export above went years without a gate. All four now name a registered action from one server-side registry and are gated by `requireAAL2`, and each spends its verification inside the same transaction as the work it authorises — so a verification is bound to one action with its arguments, to one sign-in, for five minutes, and is spendable exactly once. Removing the four inline checks leaves sign-in as the only place in the application that compares a password to decide who someone is. Two user-visible behaviour changes come with it: the `currentPassword` and `password` request fields are gone (the verification is a separate step now), and every one of these actions asks for verification even immediately after signing in.
- **Deleting a provider-only account no longer accepts your own username as the confirmation** — an account that signs in only through Google or Microsoft has no password to re-prove, so deletion asked it to type its own username instead. The code said as much where it did it: *"Typing the account's own username is not a credential."* A username is public within the app and appears on every comment the person has ever posted, so anyone reading over a shoulder — or holding a live session — could supply it. It was the right stopgap while there was no other proof available for such an account; there is one now. Re-authenticating at the provider replaces it. A typed confirmation phrase remains in the interface, where a deliberateness check belongs, but it is no longer what the server accepts as proof.
- **A provider-only account can now set a first password, and connect a second sign-in provider** — neither was possible. `POST /api/auth/change-password` accepted only the current password as proof, which such an account does not have, so it was exempted from proving anything at all; `POST /api/oauth/link` refused it outright with *"that account has no password"*. Both restrictions existed because a password was the only credential these endpoints could check, and both are gone now that re-consent is one: losing access to a single Google account is no longer losing the WeVolunteer account. The guard on `POST /api/oauth/disconnect` that refuses to remove an account's last remaining way to sign in is unchanged, and setting a first password is what releases it.
- **`POST /api/oauth/link` now requires being signed in as the account it links** — it was unauthenticated, tied to an account only by a 15-minute token naming a user id, and proved by that account's password: 600 attempts per window against any address somebody could produce at a provider, which made it a better brute-force target than the login form. It is now authenticated, and refuses a token that names anyone other than the caller. Somebody who reaches the "connect these accounts" prompt while signed out signs in first, then verifies. The endpoint no longer issues a new session on success, which also stops it from replacing a session that supports per-device sign-out and step-up with one that supports neither.
- **Sessions created by signing in with a provider are now per-device revocable** — the OAuth routes minted their own session tokens with a near-copy of the shared function that omitted the per-session id. Everything keyed on that id therefore treated a provider sign-in as second class: signing out of one device did nothing, and no sensitive action could be verified from it at all. One definition now serves both sign-in paths.
- **Attendance confirmation now allows admins** — `POST /api/events/:id/attendance` previously allowed only the hosting organizer to finalize attendance and credit hours, denying admins entirely. Converting the route to the `attendance.mark` capability (part of the ongoing authorization-spine work) corrects this inconsistency: admins may now confirm attendance on any event, matching the access they already had on the related check-in and roster-export routes.
- **Check-in viewing now denies partners** — `GET /api/events/:id/checkin` previously blocked only students by name, so a `partner` account could view an event's check-in roster. Converting the route to the `attendance.view` capability corrects this: it now denies both students and partners, matching the capability table's intent for that role.
- **Closed an unreleased data leak in `GET /api/applications`** — the `partner` role (added to the role enum earlier on this branch, with no users and never released) fell through this route's role-branching into the unscoped "see everything" path, meaning a partner account could have read every application in the system — every student's name and event association — the moment one was created. Fixed before release by capability-scoping the route: `partner` now gets an explicit empty result. Not a behaviour change for any real account, since the role has never shipped.
- **Application status decisions now available to both admin tiers** — `PATCH /api/applications/:id` and `PATCH /api/applications/bulk` previously allowed only the hosting organizer to accept, waitlist, or reject an application: the handler's ownership check (`app.organizer_id !== req.principal.userId`) carried none of the `event.moderate` bypass the other twenty ownership checks on this branch use. `admin` held neither `applicant.review` nor `application.withdraw` and was refused outright; `super_admin` satisfied `applicant.review` through the `'*'` wildcard, entered the organizer branch, and was then denied on every application whose event it did not host — which, for a platform owner who hosts nothing, meant all of them. Neither admin-tier role could correct a mis-set application anywhere on the platform. Both ownership checks now carry the standard `!can(req.principal, 'event.moderate')` bypass, and the route is gated on `requireCapAny(['applicant.review', 'event.moderate', 'application.withdraw'])`. Deliberate behaviour change for `admin`, and the intended behaviour for `super_admin`: a school activities director must be able to correct an application, and a platform owner locked out of application review was the exact defect the authorization-spine work exists to eliminate. No change for `organizer` (unchanged ownership rules), `student` (withdrawal only, on their own row), or `partner` (denied before and after, now at the middleware gate). The authorization matrix row that should have caught this was passing because it used a fake application id with no `status` field, so the request 400'd at validation before the ownership check ran; it now uses a real seeded application and a real body.
- **Organizer statistics now available to admins** — `GET /api/stats/organizer` previously allowed only the requesting organizer's own stats (`role !== 'organizer'` denied everyone else, including admin). Converting the route to the new `analytics.own_events` capability (part of the ongoing authorization-spine work, Task 7d) deliberately grants it to admin too, matching the platform-wide oversight admin already has on `GET /api/applications` and the event roster. Not a behaviour change for organizer or any other existing role.
- **Content, message-search, and profile routes converted to capabilities** (Task 7d, final step of the authorization-spine work) — `contentRoutes.js`, `messageRoutes.js`, `userRoutes.js`, `accountRoutes.js`, and `geocodeRoutes.js` no longer compare `req.user.role` anywhere; every gate now asks `can(req.principal, '<capability>')`. Two new capabilities were added: `stats.self` (a student reading their own volunteer stats) and `analytics.own_events` (see above). `super_admin` — previously blocked on the comment-delete, announcement create/edit/delete, and both stats routes by role-string comparisons that never recognised it — now has the platform-wide access every other admin-tier route already gives it. No behaviour changed for `student`, `organizer`, `admin`, or `partner` on any route except the deliberate `analytics.own_events` widening above; `partner`'s existing (unrestricted) access to `GET /api/geocode` and `GET /api/organizers/:id/profile` was preserved by granting it `geocode.use` and `event.view` respectively, rather than accidentally narrowing it when those routes stopped comparing role strings.

## [1.0.0] — 2026-07-27

First production release. The platform is feature-complete for a single-district
pilot: volunteers can find and claim shifts, organizers can staff and confirm
events, and confirmed attendance produces a verifiable service record.

### Added

- **Volunteer experience** — event discovery with search and filters, per-slot
  applications, withdrawal and re-application, personal dashboard with hours
  progress and service history, printable certificates, opt-in leaderboard.
- **Organizer tools** — multi-date sign-up sheet builder, applicant review with
  volunteer history inline, bulk accept/waitlist/decline, announcements, CSV
  roster export, event duplication, mobile day-of check-in.
- **Auto Select** — weighted random selection after the application deadline,
  favouring volunteers with fewer credited hours. Reproducible per-slot seeding,
  stored drafts, a re-draw cap, and a required written reason on every re-draw.
- **Attendance and hours** — check-in separated from hours confirmation, so
  marking someone present during an event credits nothing. Hours are a snapshot
  and are never re-priced. Corrections require a reason and are attributed.
- **Hours ledger** — append-only record of every change to credited hours, with
  actor, source, and reason. Deliberately carries no foreign keys so it survives
  deletion of what it describes.
- **Certificates** — random `WEV-XXXX-XXXX` codes stored server-side, with a
  public verification endpoint that omits the student's grade.
- **Notifications** — in-app notifications for selection results, waitlist
  promotions, hours credited, announcements, and cancellations, plus a
  15-minute sweep for shift reminders, deadline warnings, and an organizer
  alert when a deadline passes with applicants still undecided.
- **Administration** — organizer approval queue, content moderation, reports
  queue, platform statistics.
- **Deployment artifacts** — systemd units for the application and a nightly
  backup timer, a WAL-safe integrity-checked backup script, and environment
  templates for both server runtime and client build configuration.
- **Documentation** — deployment runbook covering provisioning through incident
  response, and a pre-launch readiness review.

### Security

- Hours are derived from confirmed attendance and never stored on a user row,
  so the figure cannot be edited directly.
- Identity is re-read from the database on every request rather than trusted
  from the JWT payload; `token_version` lets a password reset end all sessions.
- Personally identifying information is scoped server-side: contact details,
  grade, and school are visible only to the student, administrators, and
  organizers hosting an event that student applied to. Confirmed future shifts
  are visible only to the student.
- The community leaderboard is opt-in and off by default.
- Startup guards refuse to boot on a missing `JWT_SECRET`, incomplete SMTP
  configuration in production, a missing `APP_URL` in production, or demo mode
  enabled alongside `NODE_ENV=production`.
- Certificate codes are cryptographically random and stored, replacing an
  earlier derivable scheme that could be forged offline.
- Rate limiting on authentication, email-sending endpoints, the public
  certificate-verify endpoint, and the API as a whole.
- Email uniqueness is case-insensitive, with a non-destructive reconciliation
  for pre-existing duplicates.

### Notes

- Requires Node.js 24 or later. The application uses the built-in `node:sqlite`
  module, which is not available on earlier versions without a flag.
- Selection results are delivered in-app only; email notification is on the
  roadmap.
- Rate limiting is in-memory and per-process, so the current design runs a
  single instance.
