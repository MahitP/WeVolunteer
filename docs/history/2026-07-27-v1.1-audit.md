# WeVolunteer v1.1 — Pre-release Audit

**Date:** 2026-07-27
**Baseline:** v1.0.0 (`9ae59db`), 25 test files / 256 tests passing, clean tree.
**Scope:** Full-repository engineering review ahead of a v1.1 release themed
"Security, Accessibility, and User Experience."

This is a point-in-time document in the `history/` tradition: it is not
maintained after the release it precedes.

---

## 1. What must not change

These are load-bearing and correct. v1.1 should treat them as fixed points.

**Server module boundaries.** `config.js` is side-effect-free and every router
imports configuration from it rather than from `server.js`. Importing a router
therefore does not open the production database, bind a port, or start the
notification sweep. This single decision is what makes 256 tests possible, and
it is the most valuable structural property in the repository.

**The derived-hours invariant.** Credited hours are summed from
`attendance WHERE present = 1` at read time (`formatUserResponse`, `utils.js:56`)
and never stored on a user row. There is no write path that can set a user's
hours directly. Do not add one, and do not "optimise" this into a cached column.

**The append-only hours ledger.** `hours_ledger` deliberately carries no foreign
keys so it survives deletion of the records it describes. That is a correct
audit-log design and reads as intentional in the code.

**Request-time identity re-derivation.** `authenticateToken` (`utils.js:6`)
re-reads role, email, and `token_version` from the database on every request
rather than trusting a payload that may be seven days old. A deleted account's
token stops working immediately; a password reset bumps `token_version` and ends
every live session. This is already stronger than the typical JWT deployment and
it is what makes the Priority 1 migration cheap rather than structural.

**The CORS handler** (`app.js:46-99`). Scoped to `/api` rather than mounted
globally, with a same-origin fallback and a development loopback branch that is
hard-gated on `!IS_PRODUCTION`. The comment block records the exact production
outage each branch exists to prevent. Do not simplify this.

**Certificates as random stored bearer codes** (`certificates.js`). The header
comment documents the previous derivable-hash scheme and why it was a PII leak.
The current design is right.

**Startup guards.** Missing `JWT_SECRET`, incomplete production SMTP, missing
production `APP_URL`, and demo-mode-in-production all refuse to boot, in a
documented order. Fail-fast on misconfiguration is the correct posture for an
operator-deployed product.

**Server-side PII scoping.** `/api/users/:id/profile` gates contact details on
self / admin / hosting-organizer, and restricts *confirmed future shifts* to the
student alone on the grounds that they disclose a minor's whereabouts at a known
time. That is genuine child-safety reasoning, correctly implemented server-side
rather than hidden in the UI.

**The test configuration.** `isolate: true` is pinned with a written record of
the observed flake counts that justify it, and `scratch/` is excluded because
Vitest walks the filesystem rather than git. Both comments prevent a future
maintainer from "simplifying" the config into order-dependent flakiness.

**`src/tokens.test.js`.** A build-time guard that every `var(--token)` referenced
under `src/` is defined in `index.css`, with a second test guarding the guard
against vacuous passes. This is the correct pattern and Priority 3 should extend
it rather than work around it.

**The comment culture.** Comments here explain *why*, and frequently record the
specific failure that motivated the code. This is the repository's single
biggest maintainability asset. Every v1.1 change should match this standard.

**The documentation split.** `operations/` maintained, `history/` explicitly
frozen, with the distinction stated in `docs/README.md`. Keep it.

**Responsive CSS.** Seven breakpoints plus `(hover: none) and (pointer: coarse)`,
`prefers-reduced-motion`, and a `@media print` block. The mobile foundation is
better than the brief assumes.

## 2. What needs improvement

### 2.1 Authentication (Priority 1)

**Current state.** JWT in `localStorage` under `wev_auth_token`, sent as
`Authorization: Bearer`. Seven-day expiry. `logout()` is a client-side
`localStorage.removeItem` only — the server is never told, and the token remains
valid until it expires.

**The honest tradeoff.** Moving to HttpOnly cookies is not a strict upgrade. It
trades one attack class for another:

| | localStorage + Bearer | HttpOnly cookie |
|---|---|---|
| XSS token theft | Exfiltratable by any injected script | Not readable from JS |
| CSRF | Structurally immune (header must be set explicitly) | **Newly exposed** — requires mitigation |
| Logout | Client-side only; token stays valid | Server clears the cookie |
| Token in browser storage | Persists, inspectable | Not in JS-visible storage |

The migration is only a net win if the CSRF mitigation is actually implemented.
Otherwise it is a lateral move.

**The finding that matters more than the storage question.** `app.js:29` sets
`contentSecurityPolicy: false`. CSP is disabled. XSS — the exact threat that
motivates moving off `localStorage` — currently has no mitigation at all. Moving
the token into a cookie while leaving CSP off addresses the *consequence* of an
XSS while leaving the *vector* wide open: an injected script cannot read an
HttpOnly cookie, but it can still make authenticated same-origin requests with
it. **Enabling CSP is the higher-value change and should ship alongside, not
after.** The app loads one external resource (Google Fonts, `index.css:1`), so a
policy is straightforward to write.

**Deployment compatibility.** Both topologies work:
- *Development*: Vite proxies `/api` → `:5050` (`vite.config.js`), so the browser
  sees one origin. A `SameSite=Lax` cookie without `Secure` works over plain HTTP.
- *Production*: the same Express process serves the SPA and the API (`app.js:216`),
  so it is genuinely same-origin. `Secure` + `SameSite=Lax` works.

`SameSite=Lax` alone blocks cross-site POST, which covers the CSRF surface for
this topology. A double-submit token adds defence-in-depth for the
same-site-subdomain case, which this deployment does not currently have.

**Related gaps.**
- No server-side logout endpoint.
- `getMe()` short-circuits on absence of a `localStorage` token; with cookies
  this check must go, and every cold load will hit `/api/auth/me`.
- Password minimum is 6 characters (`authRoutes.js:37`), below the NIST-recommended 8.

### 2.2 Frontend architecture (Priority 2)

**The `refreshKey` fan-out is real.** `handleStateChange` (`App.jsx:190`)
increments a counter that a single `useEffect` depends on. Each increment
re-runs `getMe` + `fetchEvents` + `fetchApplications` + `fetchFavorites` — four
requests, one of which recomputes every user's hours via a SQL `SUM`. There are
**16 `onStateChange()` call sites**. Favoriting an event, which already updates
local state optimistically, is the only mutation that avoids it.

**`EventModal.jsx` is 1,688 lines** — the largest file in the repository by a
factor of 2.5 over the next-largest source file, with 88 inline `style={{}}`
blocks. It covers viewing, editing, applicant review, Auto Select, check-in, and
attendance, and renders data from six endpoints. `App.jsx:617` already
acknowledges this in a comment. It is the highest-risk file to change and the
one most in need of decomposition.

**Dead code.** Three items:

- `src/components/common/EmptyState.jsx` and
  `src/components/common/LoadingSkeleton.jsx` are imported by nothing. They are
  well-written and their supporting CSS (`.empty`, `.skeleton`,
  `index.css:1551+`) exists. Priority 4 should adopt them, not rebuild them.
- `api.getCurrentCachedUser()` (`api.js:182`) is called from nowhere. It reads a
  `localStorage` copy of the user object that the auth migration removes anyway.

**No frontend test infrastructure.** Of 256 tests, 254 are server-side; the other
two files (`helpers.test.js`, `tokens.test.js`) are pure Node with no DOM. There
is no `jsdom`, no `@testing-library/react`. **Any requirement to test theme
switching, theme persistence, or frontend auth handling requires adding this
infrastructure.** This is the one place where the "no unnecessary dependencies"
constraint and the testing requirements are in direct tension, and it needs an
explicit decision rather than a silent one.

### 2.3 Theming (Priority 3)

**Better positioned than expected.** The tokens in `:root` are already *semantic*
rather than literal — `--paper`, `--ink`, `--surface`, `--rule`, `--brand-tint`.
That naming is the hard part of a theming system and it is already done. A dark
theme is largely a second value set for the same names.

**Concrete blockers:**
1. **42 hardcoded hex literals across 5 JSX files** — `CertificateModal.jsx`,
   `BarChart.jsx`, `EventAnnouncements.jsx`, `VolunteerPortfolio.jsx`,
   `VolunteerDashboard.jsx`. These will not respond to a theme switch and must be
   tokenised first.
2. **No `color-scheme` property**, so native form controls, scrollbars, and
   focus rings stay light in dark mode.
3. **All tokens live in a single `:root`** with no theme scope.
4. **`@media print` (`index.css:2282`)** must be verified to stay light — a
   certificate printed in dark mode wastes toner and looks unprofessional. This
   is the least obvious dark-mode regression and the most embarrassing one.
5. **No `prefers-color-scheme` block** anywhere today.

**The token guard extends naturally.** `tokens.test.js` can gain a test asserting
that the dark theme defines every token the light theme does — catching the
partial-theme failure mode, where a missed token silently inherits a light value
onto a dark surface.

### 2.4 User experience (Priority 4)

34 ad-hoc loading references across the JSX with no shared pattern. The shared
components exist and are unused (see 2.2). This is adoption work, not new
construction, and it is the cheapest quality win in the release.

### 2.5 Email notifications (Priority 5)

**Well-positioned.** `nodemailer` is already a dependency, the transport is
already configured with a console mock in development and a fail-fast guard in
production, and `createNotification()` (`utils.js:131`) is a **single choke
point** that every in-app notification already flows through. Email can hang off
it without a new subsystem.

**Design constraints that must be respected:**
- **Do not mirror every notification to email.** The sweep runs every 15 minutes
  and `notifyConfirmedVolunteers` fans out to an entire roster. Mirroring
  everything turns a useful bell into a spam cannon and will get the sending
  domain blocked. Email needs a per-kind allowlist — realistically `accepted`,
  `declined`, `promoted`, `hours`, `cancelled`.
- **Users need an opt-out.** A `users` column, surfaced in profile settings.
- **Sending must never block or fail a request.** The established pattern
  (`authRoutes.js:95`) is fire-and-forget with `.catch()`. Follow it.
- **`REQUIRE_EMAIL_VERIFICATION` defaults off**, so many pilot addresses are
  unconfirmed. Sending to unverified addresses risks bounces against the
  sending reputation.

### 2.6 QR check-in (Priority 6)

**The flow as specified does not work, and this needs saying plainly.**

The brief proposes scanning a *volunteer certificate* QR at check-in. But
certificates are issued per **completed** event (`certificates.js`) — they are
generated from confirmed attendance. A volunteer arriving at an event they have
not yet attended has no certificate for it. The credential the brief wants to
scan does not exist at the moment it would be scanned.

**The corrected version** is a QR encoding the *confirmed application* — which
does exist before the event, already carries (user, event, slot), and is exactly
what check-in needs to resolve. Certificate codes stay what they are: proof of
completed service for a school office.

**The dependency problem is unavoidable.** Decoding a QR from a camera needs
either `BarcodeDetector` (Chrome/Android yes, Safari/iOS **no** — and organizers
running check-in on an iPhone is the primary use case) or a JS decoder library.
There is no zero-dependency path that works on iOS. Generating a QR is cheap
(~2KB of self-contained code); *scanning* one is not.

Given the constraint against unnecessary dependencies, and that check-in already
works today via a mobile-optimised roster view (`CheckInView.jsx`), this is the
weakest cost/benefit item in the release.

## 3. Hidden regressions and risks

| # | Risk | Severity | Notes |
|---|---|---|---|
| R1 | CSP disabled (`app.js:29`) | **High** | The unmitigated XSS vector behind the entire Priority 1 rationale. |
| R2 | Cookie migration without CSRF mitigation | **High** | Would be a lateral security move, not an improvement. |
| R3 | `EventModal.jsx` at 1,688 lines | **High** | Every priority except P5 touches it. Highest regression surface in the release. |
| R4 | No frontend test infrastructure | **Medium** | Theme and frontend-auth tests are unwritable without new dev dependencies. |
| R5 | Dark mode leaking into `@media print` | **Medium** | Silent until someone prints a certificate. |
| R6 | Partial dark theme (missed tokens) | **Medium** | Fails invisibly — light values inherit onto dark surfaces. Mitigated by extending `tokens.test.js`. |
| R7 | Email fan-out on roster-wide notifications | **Medium** | Deliverability and reputation damage; hard to undo. |
| R8 | Password minimum of 6 characters | **Low** | Below current guidance; trivial to raise, but invalidates no existing hashes. |
| R9 | In-memory rate limiting | **Low** | Already documented in the v1.0.0 changelog as a single-instance constraint. Not a v1.1 problem. |
| R10 | `scratch/` and `SignUp Genius/` in the working tree | **Low** | Already excluded from Vitest; untracked clutter only. |

**Cross-cutting sequencing risk.** Priorities 1, 2, 3, and 4 all modify
`EventModal.jsx` and `App.jsx`. Done in parallel or in the wrong order they will
conflict repeatedly. The roadmap below sequences deliberately around this.

---

## 4. Assessment

v1.0 is a genuinely well-engineered codebase — better than the brief's framing of
it suggests. The server architecture, the hours invariant, the PII scoping, and
the comment culture are all at a standard that most shipped products do not
reach. The weaknesses are concentrated in the frontend: one oversized component,
one over-broad refetch pattern, no component test harness, and no theming layer.

The most valuable security change in this release is **not** the storage
migration the brief leads with — it is enabling CSP, which the brief does not
mention. The cookie migration is worth doing, but it is the second-most valuable
item, and doing it alone would be security theatre.
