# WeVolunteer v1.1 — Design

**Date:** 2026-07-27
**Theme:** Security, Accessibility, and User Experience Improvements
**Baseline:** v1.0.0 (`9ae59db`) — 25 test files / 256 tests passing
**Companion document:** [`2026-07-27-v1.1-audit.md`](2026-07-27-v1.1-audit.md)

A point-in-time document in the `history/` tradition: not maintained after the
release it precedes.

---

## Goal

Make an already well-engineered product feel more trustworthy and more finished.
Not a feature release. Every change below traces to a finding in the audit.

## Non-goals

Explicitly out of scope, recorded so they are not revisited mid-implementation:

- Backend architecture changes. The router/config separation stays exactly as it is.
- PostgreSQL, or any datastore change. `node:sqlite` stays.
- Microservices, queues, or added infrastructure.
- TanStack Query or any new runtime dependency in the client.
- QR check-in — deferred to v1.2, corrected design recorded in §7.
- The in-memory rate limiter's single-instance constraint. Already a documented
  v1.0 limitation; unchanged here.

## Operating context

**The platform has zero users.** No pilot cohort, no live sessions, no
production data. This removes migration pressure that would otherwise shape the
design:

- Auth is a **clean cutover**. No transitional Bearer-header acceptance, no dual
  code path, nothing to remove in v1.2. One mechanism live at a time.
- Schema changes still follow the established additive `ALTER TABLE` pattern in
  `db.js`, because that pattern is correct and cheap — not because data must be
  preserved.
- The password floor applies to all new passwords with no grandfathering concern.

## 1. Sequencing

Priorities 2, 3, and 4 all modify `EventModal.jsx` and `App.jsx`. Executed in
the brief's order they conflict repeatedly. Two ordering constraints resolve it:

1. **Auth before the API restructure**, so Stage 2 relocates an already-final
   `api.js` rather than rewriting a file that is about to change again.
2. **Decomposition before theming and polish**, so Stages 3 and 4 land on five
   focused files instead of one 1,688-line file.

| Stage | Work | Depends on |
|---|---|---|
| 0 | Test harness; tokenise hardcoded colours | — |
| 1 | CSP, cookie auth, logout, password floor | 0 |
| 2 | Feature folders, EventModal split, scoped invalidation | 1 |
| 3 | Dark mode and theming | 0, 2 |
| 4 | Loading and empty states, mobile pass | 2 |
| 5 | Email notifications | — (server-only; parallel-safe) |
| 6 | Documentation and release | all |

Each stage ships with the full suite green before the next begins.

## 2. Stage 0 — Foundation

Pure preparation. No user-visible change.

**Test harness.** Add `jsdom` and `@testing-library/react` as dev dependencies.
Dev-only, so production bundle size is unaffected. Justified by the audit
finding that 254 of 256 tests are server-side and the release's theme-persistence
requirements are otherwise unwritable.

Vitest gains an environment split so server suites keep running in `node` — the
existing `isolate: true` pin and `scratch/` exclusion are load-bearing and must
survive untouched. Server tests must not silently start running under jsdom.

**Colour tokenisation.** The 42 hardcoded hex literals in `CertificateModal.jsx`,
`BarChart.jsx`, `EventAnnouncements.jsx`, `VolunteerPortfolio.jsx`, and
`VolunteerDashboard.jsx` become `var(--token)` references. Where a literal has no
existing token, a token is added to `index.css` rather than the literal kept.

This is a prerequisite for Stage 3: a hardcoded colour does not respond to a
theme switch, and `tokens.test.js` cannot catch what is not a token reference.

**Exit criteria:** 256 tests still pass. No visual diff in light mode.

## 3. Stage 1 — Security

### 3.1 Content-Security-Policy

`app.js:29` currently disables CSP outright. This is the unmitigated XSS vector
that the cookie migration is nominally a response to, and it is the higher-value
fix of the two.

The app loads exactly one external resource — Google Fonts (`index.css:1`) — so
a policy is tractable:

- `default-src 'self'`
- `style-src 'self' 'unsafe-inline' https://fonts.googleapis.com` —
  `unsafe-inline` is required by the 576 inline `style={{}}` blocks the codebase
  uses throughout. Removing it is a far larger refactor than this release should
  attempt; it is recorded as a v1.2 candidate.
- `font-src 'self' https://fonts.gstatic.com`
- `img-src 'self' data:`
- `script-src 'self'` — the Stage 3 pre-paint script must therefore be external
  or nonce'd, not inline. This constrains Stage 3 and is called out there.
- `connect-src 'self'`
- `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`

**Tradeoff stated honestly:** `style-src 'unsafe-inline'` means this CSP does not
stop all XSS payloads. It does stop injected *script*, which is the vector that
matters for session theft. A policy that blocks script but permits inline style
is a large improvement over no policy at all, and pretending otherwise would be
the kind of security theatre this release is trying to avoid.

### 3.2 Cookie authentication

**Design:**

| Property | Value | Reason |
|---|---|---|
| `httpOnly` | `true` | Not readable by injected script |
| `secure` | `IS_PRODUCTION` | Dev is plain HTTP via the Vite proxy |
| `sameSite` | `'lax'` | Blocks cross-site POST; sufficient for a same-origin topology |
| `maxAge` | 7 days | Matches the existing JWT `expiresIn` |
| `path` | `/` | API and SPA share an origin |
| name | `wev_session` | — |

**Why `SameSite=Lax` is sufficient here, and no CSRF token is added.** Both
topologies are genuinely same-origin: production serves the SPA and the API from
one Express process (`app.js:216`), and development proxies `/api` through Vite
so the browser sees a single origin. `Lax` blocks cross-site POST/PATCH/DELETE,
which is the entire CSRF surface for this deployment. A double-submit token would
defend against a same-site-subdomain attacker, which this deployment does not
have. Adding one now would be unjustified complexity; if a subdomain is ever
introduced, this decision must be revisited — recorded here so that it is.

**Server changes.** `authenticateToken` (`utils.js:6`) reads the token from
`req.cookies.wev_session`. The `Authorization` header path is **removed**, not
kept as a fallback — zero users means no reason to carry two code paths. The
existing request-time identity re-derivation and `token_version` check are
untouched; they are already correct and are what makes this migration small.

`cookie-parser` is added to the server. It is ~4KB, maintained by the Express
team, and is the standard way to do this — it does not meet any reasonable
definition of a "large unnecessary dependency."

**Logout.** New `POST /api/auth/logout`. Clears the cookie *and* increments
`token_version`, so the session is dead server-side and not merely forgotten
client-side. This closes a real v1.0 gap: `api.logout()` was a
`localStorage.removeItem` and the token stayed valid for up to seven days.

**Client changes.** `apiFetch` sends `credentials: 'include'` and no longer sets
an `Authorization` header. `STORAGE_KEYS.TOKEN` is removed entirely.

`STORAGE_KEYS.USER` is **also removed**, along with its only reader,
`getCurrentCachedUser()` — which is defined at `api.js:182` and called from
nowhere in the codebase. It is dead code caching a duplicate copy of identity in
a place script can read, for no consumer. Every cold load hits `/api/auth/me`,
which is one request the app already made.

`getMe()` currently short-circuits on the absence of a `localStorage` token; with
an HttpOnly cookie the client cannot see whether a session exists, so that check
is removed and the endpoint answers the question.

### 3.3 Password floor

Minimum length 6 → 8, in both `/api/auth/signup` and `/api/auth/reset-password`.
No grandfathering needed.

### 3.4 Tests

New and extended coverage:

- Login sets a cookie with `HttpOnly`, `SameSite=Lax`, and `Secure` in production.
- An authenticated request succeeds with the cookie and fails without it.
- A request bearing only an `Authorization` header is now rejected — proving the
  cutover is real and not silently dual-path.
- Logout clears the cookie and invalidates the session: a request replaying the
  pre-logout cookie gets 401.
- An expired token is rejected.
- A token whose `tokenVersion` is stale is rejected.
- CSP response headers are present with the expected directives.
- Password below 8 characters is rejected at signup and at reset.

**Exit criteria:** full suite green; no route reachable with a header-only token.

## 4. Stage 2 — Frontend architecture

### 4.1 Structure

```
src/
  features/
    auth/          Login, Signup, ResetPassword, session hook
    events/        Browse, Create, Calendar, EventModal parts, EventCard
    applications/  ApplicantReview, AttendeeList, check-in
    certificates/  CertificateModal, VolunteerPortfolio, verification
  components/      Shared primitives: Modal, EmptyState, LoadingSkeleton, BarChart
  hooks/           useAppData, useTheme, useModal
  api/             api.js and per-feature request groups
```

Moves are mechanical. The rule: a file used by two or more features lives in
`components/`; anything else moves to the feature that owns it.

### 4.2 EventModal decomposition

1,688 lines covering six responsibilities and six endpoints. It splits along
seams that already exist in the file as comment-delimited sections:

- `EventModalShell` — layout, tabs, close handling, the error boundary contract
- `EventDetailsPanel` — read-only view, comments, announcements
- `EventEditPanel` — organizer editing
- `ApplicantReviewPanel` — review, bulk actions, Auto Select
- `AttendancePanel` — check-in and hours confirmation

**Risk control.** This is the highest-regression work in the release, on a file
with no existing test coverage. Mitigation: Stage 0's harness is used to write
characterization tests for each panel's render and primary interaction *as it is
extracted* — not afterwards. A panel is not considered extracted until it has a
test that fails when the extraction is wrong.

### 4.3 Scoped invalidation

`handleStateChange` (`App.jsx:190`) bumps one `refreshKey` that a single effect
depends on, re-running `getMe` + `fetchEvents` + `fetchApplications` +
`fetchFavorites` on all 16 call sites. `getMe` alone recomputes credited hours
with a SQL `SUM`.

Replace with `useAppData()`, exposing:

```js
const { events, applications, favorites, user,
        refresh } = useAppData();
// refresh.events()  refresh.applications()  refresh.favorites()
// refresh.user()    refresh.all()
```

Each of the 16 call sites is then reviewed individually and asks for what it
actually invalidated. Accepting an applicant refetches applications. Creating an
event refetches events. `refresh.all()` remains available and is used where a
mutation genuinely has broad effects, rather than being the default.

This is deliberately a small hook over `useState`/`useCallback`, not a caching
library. It fixes the measured problem — over-broad refetching — without
introducing a dependency or a new mental model.

**Exit criteria:** suite green plus new panel tests; no view refetches data a
mutation could not have changed.

## 5. Stage 3 — Theming

### 5.1 Mechanism

`<html data-theme="light|dark">`, set before first paint. Tokens are already
semantic (`--paper`, `--ink`, `--surface`, `--rule`, `--brand-tint`), so the dark
theme is a second value set under `[data-theme="dark"]` rather than a
restructure. This is why theming is cheap here.

- `:root` keeps the light values, unchanged.
- `[data-theme="dark"]` overrides them.
- `color-scheme: light` / `dark` accompanies each, so native form controls,
  scrollbars, and default focus rings follow the theme.

### 5.2 Preference resolution

Three user-facing options — Light, Dark, System — persisted in `localStorage`
under `wev_theme`. `System` follows `prefers-color-scheme` and responds live to
OS changes via a `matchMedia` listener rather than only at load.

Resolution order: stored explicit choice → OS preference → light.

The resolution logic lives in a pure, exported function so it is testable without
a DOM, with the React binding as a thin `useTheme()` hook over it.

### 5.3 Flash prevention, under CSP

The theme must be applied before first paint or the page flashes light before
going dark. The usual technique is an inline `<head>` script — but §3.1 sets
`script-src 'self'`, which forbids inline script.

**Resolution:** a tiny external script in `public/`, referenced from
`index.html` and loaded synchronously in `<head>`. It reads `localStorage` and
`matchMedia` and stamps `data-theme` before the bundle loads. Same effect, no
inline script, no CSP weakening and no nonce plumbing.

This dependency between two stages is the reason CSP is specified before theming.

### 5.4 Print

`@media print` (`index.css:2282`) must force light values regardless of
`data-theme`. A certificate printed in dark mode wastes toner and looks
unprofessional, and the failure is silent until someone prints one. This gets an
explicit override block and a note in the CSS explaining why it exists.

### 5.5 Contrast

Dark values are chosen to meet WCAG AA — 4.5:1 for body text, 3:1 for large text
and UI boundaries. The existing light palette already documents this intent
(`--ink-3` carries a comment about clearing 4.5:1 on paper, not merely on white);
the dark set holds the same standard.

Surfaces are not simple inversions. The dark palette keeps the "Field Notes"
character: a warm near-black rather than pure `#000`, hairline rules that stay
hairlines, and the amber `--accent` reserved for hours and credit exactly as in
light mode. Semantic colour meaning does not change between themes.

### 5.6 Coverage and tests

Every surface: all pages, modals, forms, the certificate view, and mobile
layouts. The toggle lives in the user menu (`App.jsx:431`) alongside Edit
profile, with a mobile-reachable equivalent.

Tests:

- **Token parity** — `tokens.test.js` gains a test asserting `[data-theme="dark"]`
  defines every token `:root` does. This catches the partial-theme failure mode,
  where a missed token silently inherits a light value onto a dark surface and
  nothing errors.
- Theme resolution: explicit choice wins over OS; System follows OS; default is light.
- Persistence: a choice survives reload.
- Switching updates `data-theme` and `color-scheme`.
- An OS preference change while set to System updates the applied theme.

**Exit criteria:** parity test passes; no page renders light-on-light or
dark-on-dark; print output is light.

## 6. Stage 4 — User experience

**Loading.** 34 ad-hoc loading references across the JSX with no shared pattern.
`LoadingSkeleton` already exists, is well-written, has supporting CSS
(`.skeleton`, `index.css:1573`), and is **imported by nothing**. Adopt it. Skeletons
mirror the shape of the content they replace rather than being generic bars.

**Empty states.** `EmptyState` is likewise written, styled (`.empty`,
`index.css:1551`), and unused. Adopt it with copy that says what is absent and
what to do next:

- "No upcoming volunteer opportunities" + a link to browse
- "No applications yet" + a prompt to find a shift
- "No certificates available" + a line explaining they appear after confirmed attendance
- Organizer: no events, no applicants, no attendance recorded

Copy states a fact and offers an action. No apologising, no exclamation marks.

**Mobile.** Audit dashboards, browse, organizer workflows, and check-in at 375px.
The CSS foundation is strong — seven breakpoints plus a coarse-pointer block — so
this is expected to surface touch-target sizes, horizontal overflow in tables,
and modal height on small screens rather than structural problems.

This stage is adoption and polish. It adds no new components.

## 7. Stage 5 — Email notifications

### 7.1 Integration point

`createNotification()` (`utils.js:131`) is the single choke point every in-app
notification already flows through. Email hangs off it. No new subsystem, no
queue, no scheduler.

### 7.2 Policy

**Not every notification becomes an email.** The sweep runs every 15 minutes and
`notifyConfirmedVolunteers()` fans out to an entire roster; mirroring everything
would turn a useful bell into a spam cannon and damage sending reputation
irreversibly.

Email is sent only for kinds where the student would otherwise not find out in
time, and only where the news is genuinely theirs:

| Kind | Email | Reason |
|---|---|---|
| `accepted` | yes | They need to know to show up |
| `declined` | yes | Silence is the worst outcome for a volunteer programme |
| `promoted` | yes | Off the waitlist — same as accepted |
| `hours` | yes | Credited service; often needed for a school requirement |
| `cancelled` | yes | Prevents someone travelling to nothing |
| `application` | no | Organizer-facing; high volume |
| `reminder`, `deadline` | no | Sweep-generated; the bell is sufficient |
| `announcement`, `comment` | no | Roster-wide fan-out |
| `waitlisted`, `approval`, `location`, `info` | no | Low urgency |

### 7.3 Constraints

- **Opt-out.** New `users.email_notifications` column, default 1, added via the
  established additive `ALTER TABLE` pattern in `db.js`. Surfaced in
  `ProfileEditModal`.
- **Never blocks a request.** Fire-and-forget with `.catch()`, matching the
  existing pattern at `authRoutes.js:95`. A mail failure must never fail an
  accept/reject.
- **Skip unverified addresses.** `REQUIRE_EMAIL_VERIFICATION` defaults off, so
  many addresses are unconfirmed. Sending to them risks bounces against sending
  reputation.
- **Development is unchanged.** The console-mock transport already in `email.js`
  prints these like any other mail.

### 7.4 Tests

Allowlisted kinds dispatch; non-allowlisted kinds do not. Opt-out suppresses.
Unverified address suppresses. A throwing transport does not fail the originating
request.

## 8. Deferred to v1.2 — QR check-in

Cut from this release, with the reasoning recorded so it is not re-litigated.

**The briefed flow cannot work.** It proposes scanning a *volunteer certificate*
at check-in, but certificates are issued per **completed** event
(`certificates.js`) — generated from confirmed attendance. A volunteer arriving
at an event they have not yet attended has no certificate for it. The credential
does not exist at the moment it would be scanned.

**The corrected design**, for whoever picks this up: encode the *confirmed
application*, which exists before the event and already carries (user, event,
slot) — exactly what check-in needs to resolve. Certificate codes stay what they
are: proof of completed service for a school office.

**Why not now.** Camera decoding needs `BarcodeDetector` (unsupported on
Safari/iOS, and an organizer with an iPhone is the primary use case) or a ~30KB
decoder library. `CheckInView.jsx` already provides a working mobile check-in
roster. Lowest cost/benefit in the release, and the only item requiring a runtime
dependency.

## 11. Risks

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| R1 | EventModal split regresses organizer workflows | **High** | Characterization tests written during extraction, not after; panel-by-panel with the suite green between each |
| R2 | CSP breaks a legitimate resource in production but not dev | **Medium** | Verify against a production build, not just the dev server; `style-src 'unsafe-inline'` retained deliberately |
| R3 | Partial dark theme | **Medium** | Token parity test makes it a build failure rather than a visual one |
| R4 | Dark mode leaks into print | **Medium** | Explicit print override plus manual verification of a printed certificate |
| R5 | Cookie not sent in some deployment topology | **Medium** | Tested in both dev-proxy and production same-origin configurations |
| R6 | Email fan-out damages sending reputation | **Medium** | Kind allowlist; opt-out; unverified skip; no roster-wide kinds enabled |
| R7 | Scoped invalidation misses a refetch, showing stale data | **Medium** | Each of the 16 call sites reviewed individually; `refresh.all()` where effects are genuinely broad |
| R8 | Stage 0 environment split silently runs server tests under jsdom | **Low** | Assert the environment in a server test; `isolate: true` and `scratch/` exclusion untouched |
