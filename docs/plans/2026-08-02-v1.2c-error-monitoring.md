### Guards that will fail your build

`server/authz.completeness.test.js` holds **five** guards. Two matter most here:

- **Guard 2** walks the live Express stack. A route is "gated" only if its
  middleware stack contains a function **literally named `capabilityGate`** —
  which is what `requireCap()` and `requireCapAny()` return. An arrow wrapper is
  invisible to it. If a route has `authenticateToken` and no `capabilityGate`, it
  must have a `ROUTE_REGISTRY` entry keyed `'<METHOD> <exact express path>'`
  with a `category` and a non-empty `reason`.
- **A route with NO `authenticateToken` needs no registry entry, and adding one
  fails the build** (`staleRegistryEntries`). This matters: the client error
  intake is deliberately reachable without a session (§5.2).

Client-side, three guards scan `src/` only and fail the build:
`tokens.test.js` (every `var(--x)` defined in `src/index.css`),
`noHardcodedColors.test.js` (no colour literal in any `src/**/*.{js,jsx}`;
`src/components/auth/` is the one exempt path), `noDanglingClasses.test.js`
(**both directions** — a CSS rule with no reference also fails).

Also: `src/routes/index.jsx`'s `withProps` **throws** if a route has no entry in
App.jsx's prop map, and `src/App.jsx`'s `NAV` **throws at module load** if an
entry declares neither `requiredCap` nor a non-empty `requiredCapAny`.

## 1. Goals

1. **Every unhandled server error is recorded**, with enough context to fix it
   and no more than that.
2. **Client crashes and failed requests are reported**, because a white screen in
   a student's browser is invisible from the server.
3. **A `super_admin` can see what is breaking, ranked by how much it matters** —
   not a raw log tail.
4. **Custom 404 / 403 / 500 pages** that tell a person what to do next.
5. **The table cannot grow without bound**, and **capture cannot itself break a
   request or leak personal data.**

### Explicit non-goals

- No third-party error service. It would mean shipping student data to a vendor
  with no contract, and the brief's "no paid APIs, no credit card" constraint
  applies with more force to PII than to map tiles.
- No distributed tracing, no metrics/time-series system, no alerting-by-email in
  this release. Alerting is a v1.3 concern once the email queue is trustworthy.
- No log aggregation. `console.error` to the systemd journal stays as it is.

## 2. Architecture

```
                     ┌─────────────────────────────────────────┐
  server throw ─────▶│ server/errorReporter.js                 │
  (error handler,    │  · redact()      — allowlist, not deny  │
  worker, scheduler) │  · fingerprint() — sha256, stable       │
                     │  · record()      — never throws         │
  client crash ─────▶│                                         │
  (ErrorBoundary,    └───────────┬─────────────────────────────┘
   window.onerror)               │
                                 ▼
                      ┌────────────────────┐
                      │ error_events       │  one row per OCCURRENCE (capped)
                      │ error_groups       │  one row per FINGERPRINT (counts)
                      └─────────┬──────────┘
                                │
        ┌───────────────────────┴────────────────────┐
        ▼                                            ▼
  GET /api/errors            (error.read)      sweepErrors()
  GET /api/errors/:id                          in the existing
  PATCH /api/errors/:id      (resolve/ignore)  maintenance sweep
```

**Two tables, not one.** A single `errors` table forces the dashboard to either
`GROUP BY` on every read or show a wall of duplicates. `error_groups` holds the
identity of a problem (fingerprint, first seen, last seen, count, status);
`error_events` holds bounded evidence for it. This is what makes retention
possible without losing the fact that something happened 4,000 times.

**Why `server/errorReporter.js` is its own module, importing no db:** the same
reasoning as `server/reauth.js` — `db` arrives as an argument, so a test drives
it against a throwaway file and there is no import cycle with `app.js`. It must
be importable by `server/workers/*` and `server/services/autoSelectScheduler.js`
too, which run outside any request.

## 4. Database migrations

**`server/migrations/004_error_events.js`** — additive only, no table rebuild, so
none of ENGINEERING_GUIDE §8.3's six destructive-rebuild guards apply. State that
in the module header so the next reader does not go looking for them.

```sql
CREATE TABLE IF NOT EXISTS error_groups (
  fingerprint   TEXT PRIMARY KEY,
  source        TEXT NOT NULL CHECK(source IN ('server','client','worker')),
  kind          TEXT NOT NULL,              -- constructor name, e.g. TypeError
  message       TEXT NOT NULL,              -- REDACTED, normalised
  route         TEXT,                       -- express pattern, never a real URL
  status        TEXT NOT NULL DEFAULT 'open'
                  CHECK(status IN ('open','resolved','ignored')),
  occurrences   INTEGER NOT NULL DEFAULT 0,
  users_seen    INTEGER NOT NULL DEFAULT 0,
  first_seen_at TEXT NOT NULL,
  last_seen_at  TEXT NOT NULL,
  resolved_at   TEXT,
  resolved_by   TEXT,
  release       TEXT                        -- from server/package.json version
);
CREATE INDEX IF NOT EXISTS idx_error_groups_triage
  ON error_groups(status, last_seen_at DESC);

CREATE TABLE IF NOT EXISTS error_events (
  id           TEXT PRIMARY KEY,
  fingerprint  TEXT NOT NULL,
  occurred_at  TEXT NOT NULL,
  stack        TEXT,                        -- REDACTED, truncated
  route        TEXT,
  method       TEXT,
  status_code  INTEGER,
  user_hash    TEXT,                        -- sha256(user_id)[0..31], NOT the id
  role         TEXT,                        -- coarse; see §6
  user_agent   TEXT,                        -- family only, e.g. "Safari/iOS"
  context      TEXT,                        -- JSON, allowlisted keys only
  FOREIGN KEY(fingerprint) REFERENCES error_groups(fingerprint) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_error_events_group
  ON error_events(fingerprint, occurred_at DESC);
```

**Decisions to preserve, with reasons:**

- **`user_hash`, not `user_id`.** The question a dashboard answers is "how many
  distinct people hit this" and "is it just one person's odd data". A hash
  answers both. Storing the id would make the error table a second index of who
  did what, retained on a different schedule from everything else.
  Precedent: `reauth_challenges.ip_hash` (v1.2b) exists for exactly this reason.
- **No IP column at all.** v1.2b stored a hashed IP because incident correlation
  genuinely needed it. Here it buys nothing a `user_hash` does not.
- **`route` is the Express pattern** (`/api/events/:id`), never `req.originalUrl`
  — a real URL carries query strings, and query strings carry search terms,
  addresses and email addresses.
- **`ON DELETE CASCADE`** so pruning a group cannot leave orphaned evidence.
- **Timestamps are ISO-8601 UTC from JS, never `datetime('now')`** — TD-10: the
  space-separated SQLite form breaks lexicographic comparison, which is how
  `last_seen_at DESC` and every retention cutoff work.

- [ ] **Migration idempotency is a required test** (`CLAUDE.md`): run `up`
      twice against the same database and assert no throw and no duplicate rows.

## 5. Backend changes

### 5.1 `server/errorReporter.js` (new)

```js
export const REDACTED = '[redacted]';
export function redactMessage(message) { … }
export function redactStack(stack) { … }
export function fingerprint({ source, kind, message, route }) { … }
export function recordError(db, event) { … }   // NEVER throws
export function sweepErrors(db, now = new Date()) { … }
```

**`recordError` must never throw, and that is the single most important property
in this release.** It is called from the Express error handler; an exception
there is an exception while handling an exception, which Express answers by
killing the response and — for a throw in an async path — can take the process
down. Wrap the entire body in `try/catch` and, in the catch, `console.error` and
return. Test it by passing a `db` whose `prepare` throws.

**Redaction is an allowlist, not a denylist.** A denylist ("strip emails, strip
tokens") fails on the first thing nobody thought of. Concretely:

- `context` accepts **only** these keys: `route`, `method`, `statusCode`,
  `migrationVersion`, `jobId`, `eventId`, `slotId`, `component`, `boundary`.
  Everything else is dropped, not sanitised.
- `redactMessage` replaces anything matching an email, a JWT-shaped token, a
  bearer token, a `reauth-*` challenge id, a long hex run (≥ 24 chars), or a
  digit run of ≥ 7 with `REDACTED`, **and then** truncates to 500 chars.
- `redactStack` keeps frames whose path is inside the repo, drops
  `node_modules` frames beyond the first, strips absolute path prefixes above
  the repo root (a deploy path can name a person), and truncates to 4,000 chars.
- **Request bodies are never captured.** Not redacted — not captured. There is
  no body field in the schema, deliberately, so a future author cannot add one
  by passing a key.

- [ ] **Every redaction rule needs a test with a realistic positive.** A
      redaction rule with no test is a comment. Include at minimum: an error
      message containing a student's email; a stack naming
      `/home/<someone>/wev/...`; a message containing a JWT; a `context` object
      carrying `password`, `newEmail` and `challengeId` and an assertion that
      all three are absent from what is stored.

**Fingerprinting** is `sha256(source | kind | normalisedMessage | route)`, where
normalisation strips digits and quoted strings from the message so
`Cannot read 'x' of undefined at row 41` and `... row 9` are one group. Test that
two occurrences differing only in an id share a fingerprint, and that two genuine
different bugs do not.

**Sampling and caps** — say the numbers, and enforce them in SQL:

- `error_groups` is unbounded in principle but bounded in practice by
  fingerprinting; a runaway would need distinct messages.
- `error_events` keeps at most **50 rows per fingerprint** (delete the oldest
  beyond that on insert) and **30 days**.
- `error_groups` rows with `status IN ('resolved','ignored')` are deleted after
  **30 days**; `open` groups are kept **180 days** and then deleted with their
  events.
- Above **100 occurrences of one fingerprint per hour**, increment
  `occurrences` but stop inserting events. The count stays true; the evidence
  stops duplicating.
- **State what happens at 10,000 errors/day:** that is at most a few hundred
  distinct fingerprints in practice, each capped at 50 events, so the table is
  bounded in the low tens of thousands of rows. The counter, not the evidence, is
  what grows.

`sweepErrors` runs from the **existing maintenance sweep in `server/utils.js`**
that already calls `sweepExpiredChallenges`. Do not add a new interval or worker
— `server/shutdown.js` would then need to drain it.

### 5.2 Intake

- **Server-side:** call `recordError` from the existing error handler in
  `server/app.js`, **after** the response has been decided, so a failure to
  record cannot change what the user sees. Also from
  `server/workers/notificationWorker.js`, `server/workers/exportWorker.js` and
  `server/services/autoSelectScheduler.js` — an error in a background job is
  currently invisible, which is the worst case, because nobody is watching.
- **Client-side:** `POST /api/errors/report`, **deliberately unauthenticated**.
  An error can happen before a session exists (the login screen, a failed
  `getMe`), and requiring auth would hide exactly the failures that lock people
  out. Consequences to handle explicitly:
  - It needs **its own rate limiter** — follow the pattern of the eight named
    limiters in `app.js`. Suggested: 20 per 15 minutes per IP, successes
    counted, `DEMO_MODE` ceiling like the others.
  - Body cap **below** the global 100 kB: use a route-level
    `express.json({ limit: '8kb' })`. A stack trace does not need more, and the
    endpoint is an unauthenticated write.
  - It must **not** appear in `ROUTE_REGISTRY` (no `authenticateToken` → Guard 2
    never examines it → a defensive entry fails the build as stale).
  - Server-assigned fields win: the client cannot set `source`, `release`,
    `occurred_at`, `user_hash` or `role`. If a session cookie is present, derive
    `user_hash`/`role` server-side; otherwise leave them null.

### 5.3 Read API

All behind `authenticateToken` + `requireCap('error.read')`, which is
`SUPER_ONLY`. **`super_admin` holds `'*'`**, so any `else if (can(...))` cascade
you write is not mutually exclusive — order most-privileged-first and end in an
explicit deny. This exact hazard produced a real data leak on the v1.2a branch.

| Route | Gate | Notes |
|---|---|---|
| `GET /api/errors` | `error.read` | groups, filter by status/source, `ORDER BY last_seen_at DESC`, paginated |
| `GET /api/errors/:fingerprint` | `error.read` | one group + its most recent events |
| `PATCH /api/errors/:fingerprint` | `error.write` | `{ status: 'resolved' \| 'ignored' \| 'open' }` |
| `GET /api/errors/summary` | `error.read` | counts by day and by source, for the chart |

- [ ] Every one of these carries a `capabilityGate`, so **none** needs a
      `ROUTE_REGISTRY` entry. Verify by running the suite, not by reasoning.
- [ ] `PATCH` writes an `admin_audit_logs` row. **This is the task that should
      introduce the missing audit helper** (`server/auditLog.js`) rather than a
      ninth raw inline INSERT — see §11.

## 6. Frontend changes

### 6.1 The error pages

`src/views/ErrorPage.jsx`, one component with a `kind` prop (`'404' | '403' |
'500'`). Three near-identical files would drift.

**The SPA-fallback trap, stated because it is easy to get wrong:** in production
`server/app.js` serves `dist/` and then `app.get('*')` returns `index.html` for
any non-`/api` path. So an unknown path already reaches the SPA — the 404 is a
**client-side** concern, handled by the existing catch-all routes in
`src/App.jsx` (line ~773 authenticated, ~506 signed-out). Today they
`<Navigate to="/" replace />`, which silently swallows a typo'd link. Replace
with the 404 page.

**A missing static file is a different bug and this does not fix it:** the
fallback returns HTML for a missing `/sw.js` too — the same failure mode that
once made socket.io retry forever. Note it as out of scope; v1.3's PWA work has
to confront it.

- [ ] 403 is reached when a capability check denies a route. `src/App.jsx`
      currently renders `denied = <Navigate to="/" replace />` for that. Bouncing
      someone to the dashboard with no explanation is why "nothing happens when I
      click it" reports exist. Use the page.
- [ ] **Do not add these to `APP_ROUTES` without also adding a prop-map entry** —
      `withProps` throws otherwise, and `src/App.routeTable.test.jsx` pins the
      current path set. Prefer rendering the component directly at the catch-all
      rather than registering a route.
- [ ] **Design tokens only.** Any colour literal in a `src/**/*.jsx` file fails
      `noHardcodedColors.test.js`. Any class matching
      `^(modal|btn|stack|seats|auth|field|alert)-[a-z-]+$` needs a rule in
      `src/index.css` specifically — a co-located `.css` file does not count.

### 6.2 Client capture

- Extend `src/components/ErrorBoundary.jsx`'s `componentDidCatch` to report.
- Add a `window.onerror` / `unhandledrejection` listener in `src/main.jsx`.
- **The two loops you must prevent, with the mitigation named:**
  1. *Reporting the reporter.* If `POST /api/errors/report` fails, never report
     that failure. Mark the reporter re-entrant-unsafe with a module-level flag.
  2. *A broken render.* React can re-render a failing tree many times per
     second. Cap at **5 reports per page load**, and dedupe by
     `message + first stack frame` within that. After the cap, drop silently —
     the server already has the fingerprint.
- Do **not** report `ApiError` with `isNetworkError: true`. That is someone on a
  school bus, not a defect, and it would drown the real signal. Report 5xx.

### 6.3 The dashboard

**There is no fourth dashboard, and this plan should not create one.**
`super_admin` currently gets `AdminDashboard` through the `staff` persona
(`src/App.jsx:66-72`, `PERSONAS`). Adding a persona is a larger change than this
release needs and would touch `PAGE_META`, `DASHBOARD_NAV` and
`src/App.shellByRole.test.jsx`.

Instead: a new route `/errors`, in `APP_ROUTES` with `requiredCap: 'error.read'`,
reachable from a `NAV` entry with the same capability. Because `error.read` is
`SUPER_ONLY`, the nav item and the route are invisible and denied to everyone
else — which is the mechanism already used everywhere else in the app.

- [ ] **The `NAV` entry must declare `requiredCap`** or `src/App.jsx` throws at
      module load. Not a lint warning — a hard throw, deliberately.
- [ ] **Add the `/errors` entry to App.jsx's route prop map** or `withProps`
      throws.
- [ ] Reuse `BarChart` from `src/components/BarChart.jsx` for occurrences-by-day.
      Note its `sr-only` table caption is **hardcoded to "Hours by period"** —
      fix that to take a prop as part of this task, since a chart of error counts
      announcing "hours" to a screen reader is wrong. That is a two-line change
      and `AdminDashboard` already mis-uses it the same way.

## 7. Security considerations

1. **PII is the whole risk.** Users are mostly minors. The allowlist in §5.1, the
   absence of a body field, `user_hash` instead of `user_id`, and the Express
   pattern instead of the URL are the four decisions that carry it. Each has a
   test.
2. **The intake endpoint is an unauthenticated write.** Rate limit, body cap,
   server-assigned fields. Say in the code why it is unauthenticated, or someone
   will "fix" it and blind the login screen.
3. **The dashboard shows stack traces, which name file paths and internal
   structure.** `SUPER_ONLY` is right. Do not add a "share this error" link.
4. **`error.read` must not be grantable per-user** through
   `user_capabilities` without thought — check how `SUPER_ONLY` interacts with
   `grantsFor` in `server/authz.js` before assuming, and write the test either
   way.
5. **Do not log the redacted-away original anywhere**, including `console.error`,
   in the belief that the journal is safe. The journal is on disk and in backups.

## 8. UX flows

**A student hits a 500.** Sees a page saying something went wrong, that their
data is safe, and offering a reload and a link back — the same register as the
existing `main.jsx` boundary copy. No error id: a code they cannot use is noise,
and asking a 14-year-old to quote a UUID is not a support process.

**A student follows a dead link.** 404, with a search-events link and a
dashboard link. Not a redirect.

**A student is denied.** 403 saying they do not have access to that page, and
what they can do — not a bounce to the dashboard.

**The platform owner triages.** `/errors` → open groups newest-first, each with
count and distinct-users → click for redacted stack and recent occurrences →
resolve or ignore. Resolve is audit-logged. A group that recurs after resolution
reopens automatically (its `last_seen_at` moves and `status` returns to `open`),
because a silently-still-broken thing marked resolved is worse than no dashboard.

## 9. Testing strategy

Coverage is proportional to consequence (`CLAUDE.md`). Required here:

- **Server tests boot the real app in-process** against a throwaway SQLite file
  via `server/testServer.js`. **Never statically import anything that reaches
  `db.js` at the top of a server test file** — `db.js` opens its database at
  module scope, so the first import decides the path. Dynamic imports inside
  hooks only.
- **Redaction:** one test per rule, each with a realistic positive (§5.1).
- **`recordError` never throws:** drive it with a `db` whose `prepare` throws,
  and assert the caller is unaffected.
- **The error handler still answers correctly when recording fails** — this is
  the one that protects users.
- **Fingerprint stability:** ids collapse, genuine differences do not.
- **Caps:** insert 200 events for one fingerprint, assert 50 rows and an
  occurrence count of 200. This is the test that proves the design, not the code.
- **Sweep:** aged rows go, fresh rows stay, and the sweep is idempotent.
- **Migration idempotency:** `up` twice.
- **Authorization:** every new route denied for `student`, `organizer`, `admin`,
  `partner` and allowed for `super_admin`. The authorization matrix test from
  v1.2a is where this belongs.
- **The intake endpoint:** rate limited; over-size body rejected;
  client-supplied `source`/`user_hash` ignored.
- **Client:** boundary reports once; the cap holds; a network error is not
  reported; the reporter does not report its own failure.

**Mutation-test every guard you add** (§5.1's caps, the loop breaker): delete the
check, confirm its test goes red, restore it. This is the practice that caught
three role-string bugs and two Criticals on the previous two branches; a guard
that cannot be shown to fire is not a guard.

## 12. Rollout order

Tasks are in dependency order above. The release is shippable after Task 6
(server capture + triage API) even if 7–9 slip; the pages and dashboard are
independently valuable but not load-bearing. Task 10 must not slip past a
production deploy — an unswept table is the one failure that gets worse with time.

## 13. Risk analysis

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| **A redaction gap ships PII into the error table** | Medium | High | Allowlist not denylist; no body field in the schema at all; one test per rule with a realistic positive; §11 Task 3 makes the tests the deliverable |
| **`recordError` throws inside the error handler and takes the process down** | Low | Critical | Total try/catch; a test that drives it with a hostile `db`; the response is decided before recording |
| **The unauthenticated intake is used to fill the disk** | Medium | Medium | Own rate limiter, 8 kB body cap, per-fingerprint event cap, sweep |
| **Client reporting loop** | Medium | High | Re-entrancy flag, 5-per-load cap, dedupe, never report a report failure |
| **The 404 page breaks client-side routing** | Medium | Medium | Render at the catch-all rather than registering a route; `withProps` throws if you get it wrong, which is the good outcome |
| **`SUPER_ONLY` interacts with per-user grants unexpectedly** | Low | High | Read `server/authz.js` and write the test either way (§7.4) |
| **Table grows unbounded because the sweep is never wired** | Low | High | Task 10 is a release blocker, not a follow-up |
| **A new dependency breaks the lockfile rule** | Low | High | §3 adds none; if one becomes necessary, `npm install` from the root only |

## 14. Acceptance criteria for the release

- [ ] A route that throws produces one `error_groups` row and one
      `error_events` row, with no email address, no token, no request body and no
      raw user id anywhere in either.
- [ ] The response a user receives when a handler throws is byte-identical to
      before this release.
- [ ] `recordError` with a database that throws leaves the request unaffected.
- [ ] 200 occurrences of one fingerprint produce 50 event rows and
      `occurrences = 200`.
- [ ] A client crash produces at most 5 reports per page load, and a failing
      report endpoint produces no recursion.
- [ ] `/errors` is invisible and denied for `student`, `organizer`, `admin` and
      `partner`; usable by `super_admin`.
- [ ] Resolving a group writes an `admin_audit_logs` row through
      `server/auditLog.js`, and no raw INSERT into that table remains anywhere.
- [ ] 404, 403 and 500 all render a page that says what happened and offers a way
      out; none of them is a redirect to `/`.
- [ ] The sweep removes aged rows and is idempotent.
- [ ] Four gates green on Node 24. `npm run verify:hours` still exits 0.
- [ ] `docs/ENGINEERING_GUIDE.md` and `CHANGELOG.md` updated.

## 15. Open questions for a human

None block starting. Each has an assumption to proceed under.

1. **Retention numbers** — 30 days of evidence, 180 days of open groups. A
   district records-retention policy may say otherwise. *Assumption: as above,
   and cheap to change since it is two constants.*
2. **Should `error.read` be grantable to a school `admin`?** It exposes stack
   traces and internal paths. *Assumption: no — `SUPER_ONLY` as already
   declared. Revisit if the platform owner is not the person operating it.*
3. **Is a fourth `super_admin` persona wanted?** §6.3 deliberately avoids
   creating one. *Assumption: no, a capability-gated route is enough; revisit in
   v2.0's W10, which adds enough owner-only surface to justify it.*
