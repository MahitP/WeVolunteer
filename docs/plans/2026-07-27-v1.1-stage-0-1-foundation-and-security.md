# WeVolunteer v1.1 — Stage 0 & 1: Foundation and Security

**Goal:** Add a frontend test harness, remove hardcoded colours, and migrate authentication from `localStorage` JWTs to HttpOnly cookies behind an enabled Content-Security-Policy — leaving the app strictly more secure than v1.0, not merely different.

**Architecture:** No architectural change. `authenticateToken` keeps its existing request-time identity re-derivation and `token_version` check; only the *transport* of the token changes, from an `Authorization` header to a `Secure`/`HttpOnly`/`SameSite=Lax` cookie. CSP is enabled in the existing `helmet()` call. The Express router/config separation, SQLite access, domain logic, hours ledger, attendance separation, and Auto Select are untouched.

**Tech Stack:** Node 24 (`node:sqlite`), Express 4, `jsonwebtoken`, `helmet`, new: `cookie-parser` (runtime, ~4KB), `jsdom` + `@testing-library/react` (dev only), Vitest 4, React 19, Vite 8.

## Global Constraints

- **Node.js >= 24.0.0.** The app uses built-in `node:sqlite`.
- **Test count is a floor, never a target.** Baseline is **256 tests / 25 files**. No task may reduce it. Run `npm test` at the end of every task.
- **No new runtime dependencies beyond `cookie-parser`.** No auth framework, no Redux, no TanStack Query, no QR library.
- **No CSRF token.** `SameSite=Lax` is sufficient for this same-origin topology; see Task 6 for the reasoning that must be recorded in code.
- **Do not change:** SQLite architecture, Express backend architecture, domain logic organization, the hours ledger model, attendance/hours separation, the weighted Auto Select algorithm, the additive `ALTER TABLE` migration philosophy, or the systemd deployment model.
- **Comment standard.** This codebase's comments explain *why*, and record the specific failure a decision prevents. Every non-obvious change in this plan must carry a comment at that standard. This is the repository's most valuable asset — match it.
- **Cookie name:** `wev_session`. **Theme storage key** (Stage 3, not this plan): `wev_theme`.
- **Commit after every task.** Conventional Commits format (`feat:`, `fix:`, `test:`, `refactor:`, `docs:`, `chore:`).

## Scope note

This plan covers **Stage 0 and Stage 1 only** — the foundation and the security migration. That is a coherent, independently shippable unit: after Task 12 the app is fully functional with hardened auth and a passing suite.

Stages 2–6 (frontend decomposition, dark mode, UX polish, email, docs) get their own plans, written after Stage 1 lands. This is deliberate: Stage 2's `EventModal.jsx` split produces the file layout that Stages 3 and 4 operate on, so planning them now would mean writing code against files whose shape is not yet decided.

- [ ] **Step 1: Write the failing guard test**

Create `src/noHardcodedColors.test.js`:

```js
import { describe, it, expect } from 'vitest';
import fs from 'fs';
import path from 'path';

/**
 * Colour-literal guard.
 *
 * A hardcoded `#0f6b45` in a JSX inline style does not respond to a theme
 * switch. It is also invisible to tokens.test.js, which only validates that
 * `var(--x)` references resolve to a defined token — a literal is not a
 * reference, so it passes that guard while being exactly the thing that breaks
 * dark mode.
 *
 * This test makes a colour literal under src/ a build failure. Colours belong
 * in index.css as tokens; JSX references them with var().
 *
 * index.css itself is excluded: it is where the literals are *supposed* to live.
 */

const SRC = path.join(process.cwd(), 'src');

// #abc, #aabbcc, #aabbccdd, rgb(...), rgba(...), hsl(...), hsla(...)
const COLOR_LITERAL = /#[0-9a-fA-F]{3,8}\b|\b(?:rgba?|hsla?)\s*\(/g;

function offenders() {
  const found = [];
  const walk = (dir) => {
    for (const entry of fs.readdirSync(dir, { withFileTypes: true })) {
      const full = path.join(dir, entry.name);
      if (entry.isDirectory()) { walk(full); continue; }
      if (!/\.jsx?$/.test(entry.name)) continue;
      if (entry.name.endsWith('.test.js') || entry.name.endsWith('.test.jsx')) continue;

      const text = fs.readFileSync(full, 'utf8');
      text.split('\n').forEach((line, i) => {
        for (const m of line.matchAll(COLOR_LITERAL)) {
          found.push(`${path.relative(process.cwd(), full)}:${i + 1} — ${m[0]}`);
        }
      });
    }
  };
  walk(SRC);
  return found.sort();
}

describe('colour literals', () => {
  it('are absent from JSX under src/', () => {
    expect(offenders()).toEqual([]);
  });
});
```

- [ ] **Step 3: Enable CSP**

```js
app.use(helmet({
  /**
   * CSP was disabled outright in v1.0, which left cross-site scripting with no
   * mitigation at all — the same threat that motivated moving the session token
   * out of localStorage. An HttpOnly cookie stops an injected script *reading*
   * the session; it does nothing to stop the script running and making
   * authenticated same-origin requests with it. This directive set is the half
   * of that pair that addresses the vector rather than the consequence.
   */
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],

      // No 'unsafe-inline'. This is the directive that matters: it is what
      // stops an injected <script> from executing. Stage 3's theme pre-paint
      // script is an external file in public/ specifically to satisfy this.
      scriptSrc: ["'self'"],

      /**
       * 'unsafe-inline' is required here and is a deliberate, bounded
       * concession: the client uses 576 inline `style={{}}` blocks, and
       * removing them is a far larger refactor than a security release should
       * smuggle in. It is recorded as a v1.2 candidate.
       *
       * The asymmetry with scriptSrc is the point — inline *style* cannot
       * exfiltrate a session; inline *script* can.
       */
      styleSrc: ["'self'", "'unsafe-inline'", 'https://fonts.googleapis.com'],

      // index.css:1 imports Bricolage Grotesque and Public Sans.
      fontSrc: ["'self'", 'https://fonts.gstatic.com'],

      // data: covers the inline SVG favicon and any base64 image.
      imgSrc: ["'self'", 'data:'],

      // The API is same-origin in both topologies: production serves the SPA
      // and the API from this process, and development proxies /api through
      // Vite. Nothing legitimate calls a third-party origin.
      connectSrc: ["'self'"],

      frameAncestors: ["'none'"],
      objectSrc: ["'none'"],
      baseUri: ["'self'"],
      formAction: ["'self'"]
    }
  },
  crossOriginResourcePolicy: { policy: 'cross-origin' }
}));
```

```js
/**
 * Session cookie.
 *
 * Replaces the v1.0 scheme of a JWT in localStorage sent as an Authorization
 * header. The token itself is unchanged — same claims, same 7-day expiry, same
 * signing secret. Only the transport moved, into a place script cannot read.
 */
export const COOKIE_NAME = 'wev_session';

/** Must match the JWT's `expiresIn: '7d'` — a cookie that outlives its token
 *  produces a confusing 403 on a session the browser still believes in. */
const SEVEN_DAYS_MS = 7 * 24 * 60 * 60 * 1000;

/**
 * Options for the session cookie.
 *
 * `sameSite: 'lax'` and NO CSRF token, deliberately.
 *
 * Cookies reintroduce CSRF, which an Authorization header is structurally
 * immune to — so this is only an upgrade if that exposure is actually closed.
 * It is, by the topology: production serves the SPA and the API from one
 * Express process (app.js), and development proxies /api through Vite, so the
 * browser sees a single origin in both. `Lax` blocks cross-site POST, PATCH and
 * DELETE, which is the entire CSRF surface available here.
 *
 * A double-submit token would add nothing against that threat model — it
 * defends against a same-site attacker on a sibling subdomain, which this
 * deployment does not have. Adding one now would be unjustified complexity.
 *
 * REVISIT THIS if the app is ever served from a subdomain alongside another
 * application, or if the API moves to a different origin from the SPA. Either
 * change invalidates the reasoning above and makes a CSRF token necessary.
 *
 * `secure` is gated on production because development runs over plain HTTP
 * through the Vite proxy; a Secure cookie is silently dropped there, which
 * presents as "login succeeds but every subsequent request is 401" — a failure
 * with no visible cause.
 */
export function cookieOptions() {
  return {
    httpOnly: true,
    secure: IS_PRODUCTION,
    sameSite: 'lax',
    maxAge: SEVEN_DAYS_MS,
    path: '/'
  };
}
```

/** Parses a Set-Cookie header into { value, attrs } — attrs lowercased for
 *  case-insensitive matching, since servers vary on capitalisation. */
function parseCookie(setCookie, name) {
  if (!setCookie) return null;
  const parts = setCookie.split(';').map(s => s.trim());
  const [k, ...rest] = parts[0].split('=');
  if (k !== name) return null;
  return {
    value: rest.join('='),
    attrs: parts.slice(1).map(a => a.toLowerCase())
  };
}

describe('login and signup issue a session cookie', () => {
  it('sets wev_session on a successful login', async () => {
    const res = await fetch(`${srv.base}/api/auth/login`, {
