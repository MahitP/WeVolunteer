# v1.2b — Step-Up Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace four scattered, inline `bcrypt.compare` checks with one auditable step-up layer, and give provider-only accounts a real credential to re-prove with instead of typing their own username.

**Architecture:** A server-side `reauth_challenges` row grants AAL2 for one action, with its arguments bound in, for five minutes, once. A `requireAAL2(action)` middleware consumes it. Verification is satisfied by password **or** OAuth re-consent, so an account with no password is no longer a second-class citizen.

**Tech Stack:** Node 24, `node:sqlite`, Express, vitest, React 19.

**Depends on:** v1.2a (merged, `bd00c6d`). `principalFor()` already carries `aal`, defaulting to `1` — this plan is what starts setting it to `2`.

## 0. What the enumeration found — read before trusting the master plan

The v2 master plan (§4.3) said no step-up existed anywhere. That was wrong, and wrong in a way worth recording: it came from grepping for `reauth`, `step-up`, `verifyIdentity`, and `confirmPassword`, none of which this codebase uses. **Enumerating the actual sensitive endpoints tells a different story.**

| Endpoint | What it does today | Verdict |
|---|---|---|
| `DELETE /api/auth/account` (`accountRoutes.js:21`) | Password account → `bcrypt.compare`. **Provider-only → type your own username.** | Step-up exists, but the provider path is not a credential |
| `POST /api/auth/change-password` (`:353`) | Requires `currentPassword`, `bcrypt.compare` at `:377` | Real step-up, inline |
| `POST /api/auth/change-email` (`:423`) | Requires `password`, `bcrypt.compare` at `:462` | Real step-up, inline |
| `POST /api/oauth/link` (`oauthRoutes.js:458`) | Requires `password`; explicitly 409s an `!OAUTH_ONLY!` account at `:455` | Real step-up, inline; provider-only cannot link a second provider |
| `POST /api/oauth/disconnect` | Last-credential guard already present — *"Never leave an account with no way back in"* | Already correct; **do not regress it** |
| `POST /api/privacy/export` (`privacyRoutes.js:15`) | `authenticateToken` + rate limit only | **No step-up.** Bulk PII egress |
| `POST /api/auth/change-username` (`:602`) | `authenticateToken` + cooldown only | No step-up; arguably fine — reversible, and there is a cooldown |

**Two corrections to the master plan follow from this:**

1. **"Account deletion is broken" is fixed already.** The handler's own comment records the defect — *"the previous code therefore asked for nothing at all: a single request against a live session irreversibly anonymised the account."* That was the bug. It closed before this plan.
2. **The remaining defect is the one the original brief named explicitly.** The brief said *"Do not use username-only verification."* The provider-only deletion path does exactly that, and the code concedes it: *"Typing the account's own username is not a credential, but it is a server-checked deliberate act."* It was the right stopgap with no OAuth re-consent available. This plan makes re-consent available.

**So this plan is a consolidation plus one genuine gap**, not a greenfield build. The scattered inline checks are the same anti-pattern v1.2a removed from authorization: correct today, individually reviewed, and impossible to reason about or extend as a set.

## Global Constraints

- Node `>=24.0.0 <25`. **Add no dependencies.** `node:crypto` is built in.
- **Timestamps:** ISO-8601 UTC generated in JS (`new Date().toISOString()`). Never SQLite `datetime('now')` — TD-10.
- **Ids:** `TEXT` via `crypto.randomUUID()`. **Booleans:** `INTEGER` 0/1.
- **Tests:** vitest. Server tests must import anything reaching `server/db.js` **dynamically inside a hook or test body** — `server/testServer.js` throws a long explanatory error otherwise.
- **Schema changes go through `server/migrations/`**, never `addColumnIfMissing` in `db.js`. The registry hashes each migration module's canonicalised source; see ENGINEERING_GUIDE §8.3. Migration version numbers continue from **3**.
- **No role-string comparisons** — `server/authz.completeness.test.js` Guard 1 fails the build on `req.user.role`, `.effectiveRole`, `.actualRole`, a destructured `role`, or any `.role` compared to a role literal, across all of `server/` and `src/`.
- **Every new authenticated route must carry `capabilityGate`** (via `requireCap`/`requireCapAny`) or be declared in Guard 2's registry with a reason. An undeclared route fails the build.
- **Capability cascades are ordered most-privileged-first and end in an explicit branch**, never a bare `else`. `can()` returns true for every capability when the role is `super_admin`. See `server/authz.js`'s header docstring.
- The `'!OAUTH_ONLY!'` sentinel is the marker for a password-less account. It is **not** a bcrypt hash — `bcrypt.compare` against it silently returns false, which reads as "wrong password". Always test the sentinel explicitly before comparing.
- Conventional commit prefixes. `npm run lint` zero warnings. `npm run build` must succeed and **must not delete `dist/`** — two `server/app.ordering.test.js` tests depend on it.
- Baseline: **102 test files / 1459 tests, all passing.**

- [ ] **Step 2: Run it and confirm it fails** — `npx vitest run server/sensitiveActions.test.js`, expect "Cannot find module".

- [ ] **Step 3: Implement**

```js
import crypto from 'crypto';

/**
 * Every action that requires a fresh proof of identity, in one place.
 *
 * A registry rather than a check at each call site, because the failure mode of
 * scattered checks is silent omission: the endpoint that forgets its gate looks
 * exactly like the endpoint that never needed one. Before this module, four
 * endpoints each did their own inline bcrypt.compare and a fifth
 * (POST /api/privacy/export, bulk PII egress) did none at all.
 *
 * `bindsParams` lists the request fields folded into the grant. Without it,
 * verifying in order to change your email to a@x.com would also authorise
 * changing it to attacker@x.com inside the same five-minute window — the subtle
 * bug in most step-up implementations.
 */
export const SENSITIVE_ACTIONS = {
  'account.delete':   { label: 'delete your account',            methods: ['password', 'oauth'], bindsParams: [] },
  'password.change':  { label: 'change your password',           methods: ['password', 'oauth'], bindsParams: [] },
  'email.change':     { label: 'change your email address',      methods: ['password', 'oauth'], bindsParams: ['newEmail'] },
  'oauth.link':       { label: 'connect a sign-in provider',     methods: ['password', 'oauth'], bindsParams: ['provider'] },
  'data.export':      { label: 'export all of your data',        methods: ['password', 'oauth'], bindsParams: [] },
};

export function isSensitiveAction(action) {
  return Object.prototype.hasOwnProperty.call(SENSITIVE_ACTIONS, action);
}

/** Canonical hash of the bound params. Key order must not matter; values must. */
export function paramsHash(action, params = {}) {
  if (!isSensitiveAction(action)) throw new Error(`Unknown sensitive action: ${action}`);
  const bound = SENSITIVE_ACTIONS[action].bindsParams;
  const canonical = bound
    .slice()
    .sort()
    .map(k => `${k}=${String(params?.[k] ?? '')}`)
    .join('&');
  return crypto.createHash('sha256').update(`${action}|${canonical}`).digest('hex');
}
```

 * Short-lived, single-use grants proving a fresh identity check.

      id          TEXT PRIMARY KEY,

**Rules the tests must pin — each is a real attack, not a hypothetical:**

| Rule | Why |
|---|---|
| Single use — `consumed_at` set atomically | A replayed grant is a second free sensitive action |
| Expires at exactly 5 minutes | Bounds the window on a stolen session |
| Bound to `action` | Verifying to change your email must not authorise deleting your account |
| Bound to `params_hash` | Verifying for `a@x.com` must not authorise `attacker@x.com` |
| Bound to `session_jti` | A grant must not be usable from a different session |
| Password path rejects the `'!OAUTH_ONLY!'` sentinel explicitly | `bcrypt.compare` against it returns false, reading as "wrong password" and stranding the user |
| OAuth path verifies the returned `sub` matches the linked `oauth_accounts` row | Otherwise any provider account satisfies the challenge |
| 5 failed attempts locks the challenge | Brute-force |
| `methods` omits `'password'` for a provider-only account | Never offer a prompt the user cannot answer |

- [ ] **Step 3:** Add to `server/authz.js`:

```js
/**
 * Requires a fresh proof of identity for this action.
 *
 * Mounted after authenticateToken and after any requireCap — capability first
 * ("may this kind of actor ever do this"), then assurance ("prove it is still
 * you"). Reversing them tells an unauthorised caller that re-verifying might
 * help, which it never would.
 *
 * Pure: reads a value already resolved onto the principal and performs no I/O,
 * so authz.js keeps the zero-imports property authz.test.js asserts.
 */
export function requireAAL2(action) {
  if (!action) throw new Error('requireAAL2: an action is required');
  return function assuranceGate(req, res, next) {
    if (!req.principal) return res.status(401).json({ error: 'Access token required' });
    if (req.principal.aal < 2 || req.principal.aalAction !== action) {
      return res.status(403).json({ error: 'Identity verification required', code: 'reauth_required', action });
    }
    return next();
  };
}
```

Validate `action` against the registry at the **call site** in route files rather than importing `sensitiveActions.js` here, to preserve purity — Task 5 adds a test asserting every `requireAAL2(...)` argument is a registered action.

- [ ] **Step 4:** In `server/utils.js`, resolve the real AAL. The consuming route supplies the challenge id (header `X-Reauth-Challenge` or body field); `authenticateToken` looks it up, and on a valid unconsumed grant sets `aal: 2` and `aalAction`. **Consumption happens in the handler's transaction, not here** — a middleware that consumes on the way in burns the grant even when the handler later fails validation.

- [ ] **Step 5:** Run, confirm green, run the full suite.
- [ ] **Step 6: Commit** — `feat: add requireAAL2 and resolve assurance level per request`

## Task 6b: Close the `auto_linked` door (added mid-implementation)

**Found by:** the Task 6 implementer, while gating `POST /api/oauth/link`. Confirmed by reading the callback.

**Files:** `server/routes/oauthRoutes.js`, `server/routes.oauth.test.js`, `CHANGELOG.md`

### The gap

Task 6 gates `POST /api/oauth/link` on `requireAAL2('oauth.link')`. That endpoint
serves only the **mismatched-address** flow — the one reached via `link_required`,
where the provider's email differs from the account's. The Settings "connect a
provider" button, for the ordinary case where the addresses **match**, does not go
through it at all. It lands in the callback's `auto_linked` branch
(`oauthRoutes.js:319-331`), which adds an `oauth_accounts` row on the strength of
`decodedState.userId === existingUser.id` and nothing else.

The state carries `userId` because `/api/oauth/:provider/url` folds it in when a
session is present (`oauthRoutes.js:153-154`). So a live session is the whole
proof, and the row it writes is a **new way to sign in** — the callback's first
branch (`oauthRoutes.js:284`) logs in anyone presenting that provider identity
from then on. That outlives the session that created it.

### Why this is Important and not Critical

Reaching it requires authenticating at the provider as an identity whose email
**equals the account's own address**. Anyone who can do that controls the
victim's mailbox at the IdP, and can therefore already take the account through
password reset. So the branch grants an attacker no capability they lack, and the
gate is defence in depth rather than a closed hole.

It is still wrong to leave. The taxonomy this release establishes is *adding a
sign-in credential requires proving identity*, and a release that states that
while leaving the door most users actually walk through ungated is a release whose
documentation is false. That is the failure mode this branch has been bitten by
repeatedly.

### The shape of the fix

`requireAAL2` cannot be middleware here: `POST /api/oauth/:provider/callback` also
serves login and signup, and gating the whole route would break both.

- [ ] **Step 1:** `/api/oauth/:provider/url` accepts an optional `challengeId` and
      folds it into the signed state, exactly as `reauthRoutes.js` does for
      re-consent. Reject a `challengeId` from an unauthenticated caller.
- [ ] **Step 2:** In the `auto_linked` branch only, require the state to carry a
      challenge and spend it with `consumeChallenge` — action `oauth.link`, params
      `{ provider }` — in the same transaction as the `oauth_accounts` upsert.
      Refuse through the shared `reauthResponses.js` table; a missing challenge is
      `reauth_required` with the action, so the client knows what to open.
- [ ] **Step 3:** The signup and login branches are untouched. Neither adds a
      credential to an existing account: login requires the identity to already be
      linked, signup creates the account the identity will own.
- [ ] **Step 4:** Tests — auto-link with no challenge is refused; with a challenge
      for a different action is refused; with a challenge bound to a different
      provider is refused; the grant is single-use; login and signup still work
      with no challenge at all (the regression that matters most).
- [ ] **Step 5:** Client wiring lands in Task 7, which must open the challenge
      *before* redirecting to the provider — there is no way to interrupt a
      callback to ask for one.
- [ ] **Step 6: Commit** — `fix: require step-up to auto-link a provider to an existing account`

## Known hazards, carried from v1.2a

1. **Consuming the grant in middleware burns it on handler-side validation failure.** Consume inside the handler's transaction.
2. **`bcrypt.compare` against `'!OAUTH_ONLY!'` returns false, not an error** — it reads as "wrong password" and strands the user. Test the sentinel first, every time.
3. **The matrix asserts status codes, not payloads.** Any test using a fake id may 400 before reaching the gate and record a false pass — this exact defect hid a real lockout in v1.2a.
4. **Guard 1 spellings.** Three role checks evaded guards on this branch by being spelled differently. Prove a new detector fires by injecting the bug, not by reading the regex.
