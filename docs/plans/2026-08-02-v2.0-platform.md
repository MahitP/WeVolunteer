# v2.0 — Platform Implementation Plan

> **For agentic workers:** implement task-by-task. Steps use `- [ ]` checkboxes.
> Read `docs/plans/2026-08-02-roadmap-index.md` first if you have no context.

**Goal:** the release a school district could adopt. The demo story is *"Student
shows a QR. I scan. Hours are on their transcript, signed by the NHS advisor."*
Everything here has to survive an administrator asking "how do you know that's
true?"

**Three workstreams:**
- **W8** — service portfolio and external hours (hours the platform did not observe)
- **W9** — QR attendance, with a real threat analysis
- **W10** — super admin, platform ownership, impersonation, public impact page

**Depends on:** v1.2a, v1.2b (both prerequisites, not preferences), v1.2c
(error visibility — this release adds the most surface), v1.3 (W9's offline mode
needs the outbox; §6.5 says what W9 does without it), v1.4 (W8's portfolio
categorisation wants the taxonomy).

## 0. What exists — verified, and it changes the plan

### 🟢 The capabilities are already defined. Do not invent new ones.

Verified present in `server/authz.js`: **`qr.present`, `attendance.scan`,
`service.verify.own_event`, `service.verify.external`, `portfolio.write`,
`capability.grant`**, plus `analytics.school`, `analytics.public`,
`analytics.platform`, and `impersonation.start` / `admin.create` /
`error.read` / `error.write` in **`SUPER_ONLY`**.

Read the table before designing a gate. The v1.2a work laid these down for
exactly this release.

**`super_admin` holds `'*'`**, so `can()` returns true for everything. An
`else if (can(...))` cascade is **not** mutually exclusive: order
most-privileged-first and end in an explicit deny. This produced a real data leak
on the v1.2a branch. Unknown capabilities are denied *before* the wildcard check,
so a typo cannot resolve true for the owner.

### The hours model — the invariants that outrank every feature here

| Table | Reality |
|---|---|
| **`attendance`** | `event_id, slot_id, user_id, present INTEGER CHECK(present IN (0,1)) NOT NULL, hours_awarded REAL NOT NULL, PRIMARY KEY(slot_id, user_id)`, three FKs CASCADE. **No `id`, no `created_at`, no `marked_by`.** |
| **`attendance_checkin`** | Separate, created in `server/attendance.js` (not `db.js`): `event_id, slot_id, user_id, present, marked_by, marked_at, PRIMARY KEY(slot_id, user_id)`. **No foreign keys at all.** |
| **`hours_ledger`** | `id`, **`user_id` / `event_id` / `slot_id` all `TEXT NOT NULL`** (see the red box below — this blocks external hours), snapshots `user_name/event_title/slot_name`, **`action TEXT NOT NULL CHECK(action IN ('credited','revoked','adjusted','migrated','voided'))`**, `present_before/present_after`, `hours_before/hours_after`, `delta REAL NOT NULL`, `actor_id`, **`actor_role CHECK(actor_role IN ('organizer','admin','system'))`**, **`source TEXT NOT NULL CHECK(source IN ('attendance_screen','event_edit','event_delete','migration','admin_correction'))`**, `reason`, `created_at`. |
| **`certificates`** | `user_id, event_id, code TEXT NOT NULL UNIQUE, created_at, PRIMARY KEY(user_id, event_id)` + five `*_snapshot` columns. Codes are `crypto.randomBytes`, stored, never derived. |

**Rules that cannot be broken:**

- **Credited hours are never stored on a user.** Derived on every read as
  `SUM(hours_awarded) WHERE present = 1`. Every change is appended to
  `hours_ledger`. `npm run verify:hours --workspace=server` exits non-zero on
  mismatch.
- An existing credit **keeps its original value permanently** — hours are a
  snapshot, never re-priced when a slot is edited later.
- Attendance writes touch **only** the volunteers named in the request, so a
  partial submission cannot silently mark anyone absent.
- `initHoursLedger()` runs `backfillHoursLedger` then `verifyLedgerParity` at
  boot — **a mismatch logs an error but does NOT halt boot.** Consider whether
  W8's new sources should change that (§4.4).

### 🔴 `hours_ledger` blocks external hours in TWO ways, not one

**1. Three CHECK constraints.** `action`, `actor_role` and `source` are all
CHECK-constrained. External hours are a new `source`, and arguably a new
`actor_role` (an outside attester is neither organizer, admin, nor system).
**SQLite cannot alter a CHECK.**

**2. `event_id` and `slot_id` are `NOT NULL`.** Verified directly:

```sql
user_id         TEXT NOT NULL,
event_id        TEXT NOT NULL,
slot_id         TEXT NOT NULL,
```

**External hours have neither.** They are, by definition, service the platform
did not host — there is no event row and no slot row to point at. So a ledger
row for them cannot be written at all until those two columns are nullable.

**This is the trap to design around, and it is easy to miss** because the CHECK
problem is the one that announces itself. An agent who rebuilds the table only to
widen the enums will discover the `NOT NULL` on the first insert — and will then
be facing a **second** rebuild of the audit table, which is precisely the
operation this plan wants to do once and carefully. **Do both in the same
migration.**

Do **not** work around it with synthetic placeholder ids (`'external'`, a UUID,
the empty string). The columns are the ledger's link to a real event, and filling
them with something that is not one makes every join and every report that reads
them quietly wrong — while looking populated. Nullable is honest: there is no
event, so the column says so.

Two consequences to carry:

- **`verifyLedgerParity` compares the ledger against `attendance`.** An external
  row has no attendance row, so it must be excluded from that comparison or the
  parity check fails on correct data — which would be worse than no check, since
  the response to a red parity check is to go looking for corruption. §4.5.
- **The good news:** `hours_ledger` has **no foreign keys in either direction** —
  nothing references it, and it references nothing (verified). So the rebuild's
  blast radius really is just this table's own rows, which is why §4.1 judges it
  acceptable where the `events` rebuild in v1.4 is not.

§4.1 confronts the whole thing directly.

### Certificates and the public verifier

`GET /api/certificates/verify/:code` is **fully public** (only `verifyLimiter`),
lives in `server/routes/attendanceRoutes.js`, prefers the `*_snapshot` columns
over live joins, and **deliberately omits `grade`**. That omission is the
precedent to follow for W10's public impact page.

**Note the path is `/api/certificates/verify/:code`, not `/verify/:code`.**
`GET /api/certificates` is authenticated with **no capability gate** (a
`SELF_ONLY` registry entry).

### Attendance routes as they stand

`POST /api/events/:id/checkin` and `POST /api/events/:id/attendance`
(`attendance.mark`); `GET /api/events/:id/checkin` and
`GET /api/events/:id/roster.csv` (`attendance.view`). Each carries an inline
`!can(principal,'event.moderate') && event.organizer_id !== principal.userId`
→ 403 host check. `POST .../attendance` throws `AttendanceRefused` (400 for
`reason_required`, else 409), flips the event to `completed`, and dispatches
`HOURS_APPROVED` / `CERTIFICATE_AVAILABLE` (dedupe key `cert:${event.id}`) /
`HOURS_ADJUSTED`.

### Step-up is complete and is the mechanism W8/W10 must use

`server/reauth.js`, `server/sensitiveActions.js`, `server/reauthResponses.js`,
`requireAAL2` in `authz.js`. Five registered actions. Grants bind action + params
+ session, single-use, five minutes, bounded per challenge (5), per account
(15/15 min) and per IP.

**`requireAAL2` is an early refusal, NOT the check.** The handler must also call
`spendChallenge(db, req, action, params)` inside its own `inTransaction`.
`consumeChallenge` is **synchronous** because `bcryptAsync.test.js` forbids an
`await` inside `inTransaction`. **Read `docs/ENGINEERING_GUIDE.md` §6.8 in full
before adding an action** — it lists every rule with the incident behind it.

### Audit logging

`admin_audit_logs` exists (`id, admin_id NOT NULL FK→users, action,
target_user_id, details, created_at`) but **there is no helper function** — all 8
call sites are raw inline INSERTs, `action` is free-text with no CHECK, and
**there is no severity column or concept.** W10's audit requirements are the
strongest justification in the roadmap for introducing `server/auditLog.js`. If
v1.2c has already introduced it, use it; if not, W10 must.

### Guards that will fail your build

`server/authz.completeness.test.js`, **six guards**:
1. No server-side role-string comparison, in any of seven spellings.
2. Every authenticated route is `capabilityGate`-gated **or** declared in
   `ROUTE_REGISTRY` with a category and reason. Gated detection is by middleware
   **function name** `capabilityGate` — an arrow wrapper is invisible. **An
   unauthenticated route needs no entry, and adding one fails as stale.**
3. The same role-string scan over `src/`.
4. Every `requireAAL2(...)` argument is a **string literal** naming a registered
   action.
5. Every file with a `requireAAL2` gate also contains a `spendChallenge` for the
   same action. The detector requires literally `db` then `req` as the first two
   arguments — **aliasing either makes the spend invisible and the guard fails.**
6. Every direct `consumeChallenge` call site is declared in
   `DECLARED_DIRECT_CONSUMERS` with a reason. Use `spendChallenge` unless the
   handler genuinely has no authenticated request (the OAuth callback is the only
   such case today); a new direct call must be justified there, and a stale
   declaration fails too.

Client-side: `src/routes/index.jsx`'s `withProps` **throws** without a prop-map
entry; `src/App.jsx`'s `NAV` **throws at module load** without a capability; the
three `src/` guards fail the build and the class guard runs **both directions**.

## 2. Architecture

```
W8   external_hours ──(verified)──▶ hours_ledger(source='external_attestation')
       │                                    │
       │  attestation_tokens                ▼
       │  (emailed, single-use)     derived totals stay derived
       │                            provenance travels with every read
       ▼
     portfolio view / certificate / export  ── all label provenance

W9   slot_qr_tokens (rotating, server-signed)
       │  student presents  ──▶ scanner posts  ──▶ attendance_checkin (EXISTS)
       │                                            │
       └── offline: v1.3 outbox ────────────────────┘

W10  impersonation_sessions (time-boxed, audited)
       │  a SEPARATE short-lived token, never a mutated principal
       ▼
     read-mostly; every write refused; visibly banded UI
```

**The three through-lines:**
1. **Provenance is a property of the hour, not of a screen.** It travels into
   every read path or the transcript is not trustworthy.
2. **A QR code proves possession of a code, not presence of a person.** Design
   accordingly and say so.
3. **Impersonation is a separate identity, not a modified one.** Never mutate
   `req.principal.effectiveRole` and hope every downstream check notices.

## 4. W8 — external hours

### 4.1 🔴 The `hours_ledger` CHECK problem, decided

External hours need `source = 'external_attestation'` and arguably
`actor_role = 'external'`. Both columns are CHECK-constrained; SQLite cannot
alter a CHECK.

**Three options:**

- **A — rebuild `hours_ledger`.** Clean. It is an append-only audit table with
  three indexes and no children, so the blast radius is much smaller than
  rebuilding `events` — but it **is** the audit trail, and losing a row is losing
  the record of an hour.
- **B — do not write external hours to `hours_ledger` at all.** Keep them wholly
  in `external_hours`, and have every read path union the two. **Rejected:** it
  creates a second source of truth for hours, which is precisely the thing the
  ledger exists to prevent, and `verify:hours` would no longer see the whole
  picture.
- **C — reuse an existing enum value** (`'migrated'`, `'admin_correction'`).
  **Rejected outright.** It makes the audit trail lie about where an hour came
  from, and the entire point of W8 is provenance.

**Recommendation: A**, with all six ENGINEERING_GUIDE §8.3 guards, modelled
structurally on `server/migrations/001_authz_roles.js`:
1. Back up first.
2. `PRAGMA foreign_keys = OFF` **outside** the transaction, then **assert it took
   effect** — it is a silent no-op inside an open transaction, and that silent
   failure was invisible to the four original guards.
3. An **explicit column list**, never `SELECT *` — column order differs between
   databases.
4. An unknown/missing-column guard.
5. A **schema-derived row-count comparison** before and after (the ledger has no
   children, so this is a self-count, and it must be exact).
6. `foreign_key_check` before commit.
Plus `ownTransaction: true`.

- [ ] **Then run `npm run verify:hours --workspace=server` and require it to
      exit 0** as part of the migration's acceptance, not afterwards.
- [ ] Take a **verified backup of `pilot.db` first**, with row counts compared
      after. There is precedent: `pilot.db` needed repair twice during v1.2a.

### 4.2 Schema

```sql
CREATE TABLE IF NOT EXISTS external_hours (
  id            TEXT PRIMARY KEY,
  user_id       TEXT NOT NULL,
  title         TEXT NOT NULL,
  organisation  TEXT NOT NULL,
  category_id   TEXT,                  -- v1.4 taxonomy; nullable if not shipped
  description   TEXT,
  served_on     TEXT NOT NULL,         -- date of service, ISO-8601
  hours         REAL NOT NULL CHECK(hours > 0 AND hours <= 24),
  state         TEXT NOT NULL DEFAULT 'draft'
                  CHECK(state IN ('draft','pending','verified','rejected','withdrawn')),
  attester_name  TEXT NOT NULL,
  attester_email TEXT NOT NULL,        -- see §4.6 on why this one is plaintext
  attester_role  TEXT,                 -- "NHS advisor", "site supervisor"
  verified_by    TEXT,                 -- users.id if an in-app verifier, else NULL
  verified_at    TEXT,
  rejected_reason TEXT,
  ledger_id      TEXT,                 -- hours_ledger.id once credited
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL,
  FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_external_hours_user ON external_hours(user_id, state);

CREATE TABLE IF NOT EXISTS attestation_tokens (
  token_hash   TEXT PRIMARY KEY,       -- sha256 of the emailed token, NOT the token
  external_id  TEXT NOT NULL,
  expires_at   TEXT NOT NULL,
  used_at      TEXT,
  ip_hash      TEXT,
  created_at   TEXT NOT NULL,
  FOREIGN KEY(external_id) REFERENCES external_hours(id) ON DELETE CASCADE
);
```

**`token_hash`, not the token.** Same reasoning as a password: a stolen database
must not yield working attestation links. The repo has the precedent —
`certificates.code` is stored because it is a *public* verifier, whereas this is
a *capability*. State the distinction in the migration header, because the two
sit next to each other and the difference matters.

**`CHECK(hours > 0 AND hours <= 24)`** — a self-asserted figure needs a sanity
bound at the schema level, not only in validation. 24 is generous and defensible;
a per-entry cap is a policy question (§15).

### 4.3 Provenance must survive into every read path

**This is the part that makes or breaks W8.** A distinction visible only on the
screen that created it is not a distinction.

- [ ] **`GET /api/stats/volunteer`** — return `hours.observed` and
      `hours.external` separately, never one summed number.
- [ ] **The portfolio / transcript view** — two labelled sections, or one list
      with an unmistakable marker on every external row. The label should read
      like *"Verified by an outside organisation"*, not a subtle icon.
- [ ] **Certificates** — a certificate covering external hours must say so. If
      that is hard, **do not issue certificates for external hours in this
      release** and say why; an ambiguous certificate is worse than none.
- [ ] **The public verifier** (`/api/certificates/verify/:code`) — must not
      present external hours as platform-observed. It already prefers snapshots,
      so the snapshot must carry the provenance.
- [ ] **The privacy export** — include `external_hours` with its state, or a
      student's export is incomplete, which is a GDPR/FERPA-shaped problem.
- [ ] **`GET /api/admin/stats`** and every aggregate — split, or an administrator
      reading "12,000 district hours" cannot tell how many the district actually
      witnessed.
- [ ] **The leaderboard** — decide explicitly whether external hours count.
      *Recommendation: no.* A leaderboard is a competition, and self-asserted
      entries in a competition invite inflation. Say so in the UI.
- [ ] Add a test asserting provenance survives **each** of these paths. One test
      per read path, because "we changed the model" is exactly the change that
      leaks through the path nobody listed.

### 4.4 Verification flow

1. Student creates an entry (`portfolio.write`) → `draft`.
2. Student submits → `pending`, and an attestation email goes to
   `attester_email` with a single-use link.
3. **The attester needs no account.** A link is the whole point: an NHS advisor
   or a soup-kitchen supervisor will not create one.
4. `GET /api/attest/:token` shows what is being claimed; `POST` confirms or
   rejects, with an optional note.
5. On confirmation: **inside one transaction** — set `verified`, append a
   `hours_ledger` row with `source='external_attestation'`, and record
   `ledger_id`. Either both happen or neither.
6. An in-app verifier holding **`service.verify.external`** (already defined) can
   also confirm, without a token.

**Where step-up applies.** Verifying external hours writes to a student's
permanent record. Per `W1 → W8`:

- [ ] **An in-app verifier using `service.verify.external` must pass
      `requireAAL2`.** That means a **new registered action** in
      `server/sensitiveActions.js` — e.g. `service.verify`, binding
      `{ externalId }`. Read §6.8 of the guide first, and remember **Guards 4 and
      5**: the argument must be a string literal, and the same file must contain
      `spendChallenge(db, req, 'service.verify', { externalId })` with literally
      `db` and `req` as the first two arguments.
- [ ] **The token-based attester does not and cannot use step-up** — they have no
      account. The token *is* their credential: single-use, hashed at rest,
      short-lived, and bound to one `external_id`. Say this explicitly in the
      code, because it looks like a missing gate and is not.
- [ ] A student **cannot** verify their own entry. If `attester_email` matches
      the student's own address (or any address on their account), refuse at
      submit time. **This is the obvious attack and it needs a test.**

### 4.5 🔴 Boot parity — external hours BREAK it unless you change the query

**Read the implementation before touching this.** `verifyLedgerParity`
(`server/hoursLedger.js`) is not a general consistency check. It is one specific
comparison, per user:

```sql
SELECT user_id, SUM(delta)         AS total FROM hours_ledger GROUP BY user_id
SELECT user_id, SUM(hours_awarded) AS total FROM attendance WHERE present = 1 GROUP BY user_id
```

and any user whose two totals differ is a mismatch.

**External hours are on the ledger side and have no attendance row.** So the
moment the first one is credited, that user's ledger total exceeds their
attendance total and parity reports a mismatch **on correct data** — which is
worse than having no check, because the documented response to a red parity check
is to go looking for corruption.

- [ ] **Exclude external rows from the ledger side of that query**, by `source`:
      `WHERE source != 'external_attestation'`. Not from the attendance side —
      there is nothing there to exclude.
- [ ] **Then add the second comparison** that the excluded rows now need:
      per-user `SUM(delta) WHERE source = 'external_attestation'` against
      `SUM(hours)` over `external_hours WHERE state = 'verified'`. Without it,
      external hours become the one kind of credit with no parity check at all —
      exactly the gap the ledger exists to close.
- [ ] `npm run verify:hours --workspace=server` must exit non-zero on either
      mismatch.

**The good news: this check is known to work.** `server/dataIntegrity.test.js`
proves it catches a real divergence — it deletes attendance rows behind the API
and asserts the exact mismatch shape — so it is a safety net worth preserving
rather than one to take on trust. Add the equivalent proof for the new
comparison: break it deliberately and assert it is caught.

- [ ] Consider whether boot should now fail on parity mismatch. *Recommendation:
      still log, not halt* — a refusal to boot over a historical inconsistency
      takes the whole app down for every user to protect one wrong number.
      Instead surface it as a v1.2c error group.

### 4.6 One deliberate PII exception

`attester_email` is stored **in plaintext**, unlike every other address in this
roadmap. Reasons, stated because it contradicts the pattern:

- It is an **adult third party**, not a student.
- The attestation must be **re-sendable** — a hash cannot be emailed.
- An administrator auditing a suspicious entry needs to see who attested it.

- [ ] Bound it anyway: purge the address once the entry has been `verified` or
      `rejected` for 12 months, keeping `attester_name` and `attester_role` for
      the record. Say so in the privacy documentation.

## 5. W9 — QR attendance

### 5.1 What the QR encodes, and what makes it unforgeable

**A rotating, server-signed slot token — not a student identity.**

```
wev1:<slotId>:<window>:<hmac>
  hmac = HMAC-SHA256(secret, `${slotId}|${window}`)   truncated to 16 bytes
  window = floor(unixSeconds / 30)
```

- **Signed, so it cannot be forged** without the server secret. A student cannot
  mint a code for a slot they are not in.
- **Rotating every 30 seconds**, so a screenshot is worthless within a minute.
- **The organizer's device displays it**; students scan it. This direction is
  deliberate — see §5.2.
- The secret is a config value; production **fails closed** without it, matching
  the existing `JWT_SECRET` guard.

### 5.2 🔴 Threat analysis — and what this does **not** prevent

Which direction to scan is the central design decision, so both are analysed.

**Chosen: the organizer displays, the students scan.** Requires each student to
have a phone (a real equity problem — §5.3 handles it), but it makes the
one-student-checks-in-the-group attack much harder, because each check-in comes
from a distinct authenticated session.

| Threat | Mitigation | **Residual risk — accepted** |
|---|---|---|
| **Screenshot replay** | 30-second window; server rejects a stale `window` | A code shared *within* 30s works. Accepted: at that point the sharer is at the event. |
| **Code shared to a group chat** | 30s rotation makes it near-useless; each check-in still needs the student's own session | **A student physically present can still relay a live code to an absent friend.** This is the fundamental limit of any QR system. **Accepted and must be documented for administrators.** Mitigation is procedural: the organizer sees a live check-in count and can compare it to the room. |
| **One student checks in the group** | Each check-in requires that student's own authenticated session | A student with a friend's unlocked phone succeeds. Accepted; equivalent to lending a school ID. |
| **Forged code** | HMAC | None, given secret hygiene. |
| **Scanner used off-site** | Not prevented by the code itself | **Accepted.** Optional coarse geofence (event lat/lon ±500 m) as a *warning*, not a block — GPS indoors is unreliable and a false block at a gym door is worse than a soft signal. Never store the coordinate (§W6 reasoning). |
| **Clock skew** | Accept the current window ±1 (90s total) | A device 2 minutes out fails. Accepted, with a clear error: "your device clock is wrong". |
| **Replay after the event** | Window bound + the slot's own time bounds | None material. |
| **Offline** | v1.3 outbox | **Check-in recorded locally is not confirmed.** The UI must say "will submit when online", never show a tick. §6.5. |
| **A student checks in and leaves** | Not prevented at all | **Accepted, and important to state:** check-in is not attendance. The existing two-step model — check-in credits nothing, an organizer confirms hours separately — is what protects the hours. This is already how the app works and it is the right answer. |

**The honest summary for an administrator:** QR check-in makes attendance-taking
fast and tamper-*resistant*. It does not make it tamper-*proof*, and hours are
still credited by a human confirming them. Put this in
`docs/operations/`, not only in code comments.

### 5.3 Equity — this is a requirement, not a nicety

Not every student has a phone. **The manual roster must remain fully functional
and equally prominent**, not a hidden fallback. `POST /api/events/:id/checkin`
already exists and already works; QR is an *addition* to it.

- [ ] An organizer can always check someone in by name. Test that the manual path
      still works with QR enabled.

### 5.4 Schema

**None required.** `attendance_checkin` already exists with `marked_by` and
`marked_at`. A QR check-in is a check-in.

- [ ] Consider adding a `method TEXT` column (`'manual' | 'qr'`) via
      `addColumnIfMissing` — useful for the threat analysis to be auditable after
      the fact, and additive so no rebuild.
- [ ] **`attendance_checkin` has no foreign keys at all.** Do not "fix" that here
      — it would be a rebuild, and it is out of scope. Note it as debt.

### 5.5 Routes

| Route | Gate |
|---|---|
| `GET /api/events/:id/slots/:slotId/qr` | `authenticateToken` + `requireCap('attendance.mark')` + the existing inline host check |
| `POST /api/checkin/scan` | `authenticateToken` + `requireCap('qr.present')` |

`qr.present` is already a student capability; `attendance.scan` already exists for
the organizer side if a scanner-direction flow is added later.

- [ ] `POST /api/checkin/scan` takes the token and derives the slot from it —
      **never** trust a `slotId` in the body alongside a token for a different
      slot.
- [ ] It must verify the student actually has an **accepted application** for that
      slot. A signed token proves the slot is real, not that the scanner belongs
      in it.
- [ ] Rate-limit it. A scan endpoint is a brute-force target for the truncated
      HMAC, and 16 bytes is comfortable but the limiter is free.

## 6. W10 — super admin and impersonation

### 6.1 🔴 Impersonation — the most dangerous feature in the roadmap

> **The user's explicit instruction: "Switch Access should NOT create dangerous
> multi-role accounts."**

**The architectural commitment: impersonation is a separate, short-lived identity,
never a mutated principal.** Do not set `req.principal.effectiveRole` to the
target's role and rely on downstream checks noticing. That is precisely how a
"multi-role account" happens, and `super_admin`'s `'*'` wildcard makes it worse —
a principal that is both owner and target passes every gate.

Instead: a distinct token, with its own claim, resolved by `buildPrincipal` into a
principal that is **the target's role and nothing more**, plus an
`impersonation` marker that every write path checks.

### 6.2 What an impersonating session may NEVER do

Enumerated, because a list is testable and a principle is not:

- [ ] **No writes at all.** Read-only, full stop. A blanket refusal is the only
      version of this that can be verified; a list of forbidden writes is a list
      someone will forget to extend. Implement as middleware that refuses any
      non-GET request from an impersonating session, mounted so it cannot be
      bypassed per-route.
- [ ] **No credential changes**, covered by the above but assert it separately —
      it is the one that turns impersonation into account theft.
- [ ] **No step-up.** An impersonating session must not be able to open or spend
      a reauth challenge. `openChallenge` binds to `session_jti`; refuse when the
      session is impersonating, and test it. Otherwise the owner can delete a
      student's account "as" them.
- [ ] **No nested impersonation.** An impersonating session cannot start another.
- [ ] **No `capability.grant`, no `admin.create`.** Both are `SUPER_ONLY` and an
      impersonated session is not the owner.
- [ ] **No data export, no certificate issuance, no messaging.** Sending a message
      as a student is impersonation in the harmful sense.
- [ ] **No socket connection as the target**, or realtime events leak.

### 6.3 Time-boxed, audited, visible

- **Time-boxed:** the token expires in **15 minutes**, non-renewable. Starting
  again requires step-up again.
- **Step-up gated:** starting impersonation requires `impersonation.start`
  (already `SUPER_ONLY`) **and** `requireAAL2` with a **new registered action**
  (`impersonation.start`), binding `{ targetUserId }`. The params binding is what
  stops a grant for impersonating student A authorising student B — exactly the
  hole the params binding exists for.
- **Audited:** an `impersonation_sessions` row plus an `admin_audit_logs` entry on
  start **and** on end, through `server/auditLog.js`. Record who, whom, when,
  from what IP hash, why (a required free-text reason), and how it ended
  (expired / ended / revoked).
- **Visible:** a persistent, unmissable band across every screen — *"You are
  viewing WeVolunteer as <name>. Read-only. Ends in 12:34."* Not a subtle badge.
  The failure mode is an owner forgetting and misreading what they see as their
  own view.
- **Termination:** an explicit "stop" that discards the token; automatic expiry;
  and revocable by bumping the impersonation row, so an admin can be kicked out.
  On tab close the token simply expires — it lives in memory and a
  `sessionStorage` key cleared by `signOut`.

```sql
CREATE TABLE IF NOT EXISTS impersonation_sessions (
  id            TEXT PRIMARY KEY,
  actor_id      TEXT NOT NULL,
  target_id     TEXT NOT NULL,
  reason        TEXT NOT NULL,
  started_at    TEXT NOT NULL,
  expires_at    TEXT NOT NULL,
  ended_at      TEXT,
  ended_reason  TEXT CHECK(ended_reason IN ('expired','ended','revoked')),
  ip_hash       TEXT,
  FOREIGN KEY(actor_id)  REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY(target_id) REFERENCES users(id) ON DELETE CASCADE
);
```

- [ ] **Interaction with `users.token_version` and per-session `jti`:** an
      impersonation token must carry its own `jti` and be revocable by the same
      mechanism, and bumping the **target's** `token_version` must invalidate it.
      Otherwise a student who signs out everywhere is still being watched.
- [ ] `buildPrincipal` re-reads identity from the DB on every request. Extend it
      to resolve the impersonation claim, so the read-only rule is enforced from
      one place rather than per-route.

### 6.4 🔴 The public impact page

Unauthenticated, aggregating data about minors. **An "impact by category" page
showing a category with one participant names that participant** to anyone who
knows the school.

- [ ] **Aggregation floor: suppress any cell with fewer than 10 distinct
      students.** Not 5 — a class is 25 and a club is 12, and 5 is
      re-identifiable by anyone in the building.
- [ ] **Suppress complementary cells too.** If a total is published and all but
      one category is suppressed, the last is derivable by subtraction. Suppress
      the second-smallest as well, or publish no total.
- [ ] **No names, no grades, no schools if there is more than one school.** The
      existing public certificate verifier **deliberately omits `grade`** — follow
      that precedent.
- [ ] **No time series fine enough to identify an event.** Monthly at the finest.
- [ ] Gate the data behind `analytics.public` server-side even though the page is
      public, so the same scoping code is used.
- [ ] Rate-limit and cache it. It is the one unauthenticated read that touches
      aggregate student data.
- [ ] **No `ROUTE_REGISTRY` entry** if it has no `authenticateToken` — adding one
      fails the build.

### 6.5 If v1.3 has not shipped

W9's offline mode depends on the v1.3 outbox. Without it:

- [ ] Ship QR **online-only**, with an explicit "you need a connection to check
      in" state. **Do not** build a second, W9-specific outbox — two offline
      queues in one app is a synchronisation bug waiting to happen, and v1.3's is
      designed as a reusable primitive for exactly this.

## 7. Security considerations, consolidated

1. **Impersonation is read-only, blanket-enforced in middleware** (§6.2). The
   single most important control in this release.
2. **Impersonation cannot use step-up**, or it becomes account takeover.
3. **The params binding on `impersonation.start`** stops a grant for one target
   authorising another.
4. **A student cannot attest their own external hours** (§4.4) — the obvious
   attack, with a test.
5. **Attestation tokens are hashed at rest, single-use, short-lived**, and bound
   to one entry.
6. **The QR token is signed and rotating**; the scan endpoint verifies the
   student's own accepted application, not just the token.
7. **Provenance travels into every read path** (§4.3), or the transcript lies by
   omission.
8. **The public page has an aggregation floor and complementary suppression**
   (§6.4).
9. **`hours_ledger` remains the single source of truth.** No feature here writes
   hours anywhere else.
10. **Every new `requireAAL2` needs a paired `spendChallenge` in the same file,
    with literal `db, req` first** — Guard 5, and the aliasing trap is real.

## 8. UX flows

**External hours.** Portfolio → "Add outside service" → form → "Who can confirm
this?" → submitted, shown as *Awaiting confirmation*. The student sees clearly
that it is not counted yet. On confirmation it moves to a **separately labelled**
section, permanently marked.

**Attester.** An email → a page showing exactly what is claimed, by whom, for how
long, with Confirm and "This isn't right" — and a note that they are attesting a
student's service record. Plain language, no jargon, one screen, works on a phone,
requires no account.

**QR check-in.** Organizer opens the slot's check-in screen → a large rotating
code on their device → students scan with the app → the count rises live →
manual check-in is a peer control on the same screen, not hidden. Afterwards the
organizer confirms hours as they do today — check-in credits nothing.

**Switch Access.** Owner finds a user → "View as" → **step-up** → a required
reason → the session opens with a permanent band and a countdown, everything
read-only, every write refused with an explanation rather than a generic 403 →
"Stop viewing" returns them.

**Public impact.** A single page: total hours, participation, categories, all
above the floor, with a line explaining that small groups are hidden to protect
privacy.

## 9. Testing strategy

- **Server tests boot the real app** via `server/testServer.js`. **Never
  statically import anything reaching `db.js`** at the top of a server test file —
  dynamic imports inside hooks only.
- `docs/ENGINEERING_GUIDE.md` requires a test for any auth/authz change, anything touching
  credited hours, any migration (assert idempotency), any new boot guard, and any
  security fix — and a **failing test first** for any bug fix. Nearly everything
  here qualifies.

**The tests that matter most:**

- **Impersonation refuses every non-GET**, enumerated across a representative set
  of write endpoints — and a test that the refusal is in middleware, so a new
  route added later is covered without being listed.
- **Impersonation cannot open or spend a reauth challenge.**
- **Impersonation cannot nest**, cannot outlive 15 minutes, and dies when the
  target's `token_version` is bumped.
- **A student cannot attest their own hours.**
- **An attestation token is single-use** and useless after `used_at`.
- **Provenance survives every read path in §4.3** — one test each.
- **`verify:hours` exits 0** after external hours are credited.
- **The ledger rebuild preserves every row** — exact count, plus
  `foreign_key_check`.
- **A stale QR window is rejected**; a forged HMAC is rejected; a student without
  an accepted application is rejected.
- **The manual roster still works with QR enabled** (equity).
- **The impact page suppresses a 9-student cell**, and does not allow the
  suppressed value to be derived by subtraction.
- **Authorization matrix rows** for every new route × all five roles, negatives
  included.

**Mutation-test every guard.** Delete the check, watch its test go red, restore
it. This practice caught three role-string bugs and two Criticals on earlier
branches; a guard that cannot be shown to fire is not a guard.

## 15. Open questions for a human

1. **🔴 How does the district want hours attested?** This is **policy, not
   engineering.** Is an email confirmation from a named supervisor sufficient for
   an NHS transcript, or must a school staff member counter-sign? Does the
   district have an existing form? *Assumption: email attestation by a named
   adult, plus optional counter-verification by a staff holder of
   `service.verify.external`.* **The answer changes W8's flow, so ask before
   Task 3.**
2. **🔴 Are external hours allowed to count toward a service-hour requirement at
   all, and is there a cap?** *Assumption: they count, are labelled everywhere,
   are excluded from the leaderboard, and are capped at 24 per entry with no
   aggregate cap.* A district may want an aggregate cap (e.g. no more than 50% of
   a requirement).
3. **Q3 — is there a persistent disk for evidence files?** W8 above is
   link-and-attestation only, with no uploads. *Assumption: no uploads in this
   release, which removes the question.*
4. **Q5 — who grants `service.verify.external`?** *Assumption: school admin,
   audit-logged via `capability.grant`.*

   prefer the reverse (organizer scans student codes). *Assumption: as designed,
   with the manual roster as the equal-status fallback.*
6. **Should a geofence block or warn?** *Assumption: warn only — a false block at
   a gym door is worse than a soft signal.*
7. **What goes on the public impact page at all?** *Assumption: total hours,
   participation rate, and categories above the floor. No school breakdown while
   there is one school.*
8. **🔴 Q6 — is a second district near-term?** If yes, tenancy should land before
   W8's scoped capabilities. *Assumption: single district through v2.0.*
