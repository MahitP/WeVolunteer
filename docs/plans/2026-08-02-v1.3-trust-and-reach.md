# v1.3 — Trust & Reach Implementation Plan

> **For agentic workers:** implement task-by-task. Steps use `- [ ]` checkboxes.
> Read `docs/plans/2026-08-02-roadmap-index.md` first if you have no context.

**Goal:** email that provably arrives, and an app that installs on a phone and
survives a dead spot in a school gym.

**Two tracks, one release.** They are coupled at one point and only one: push
notifications reuse W2's job queue and preference table. Track A can ship
without Track B; Track B's push work cannot ship without Track A.

**Depends on:** v1.2a (merged), v1.2b (complete), and — strongly recommended —
v1.2c. Shipping a service worker without error visibility means finding out from
users, and a bad service worker is the one failure with no server-side remedy.

- `src/main.jsx` is the natural registration point. It uses `StrictMode`, which

- Logout is `signOut` in `src/session/SessionProvider.jsx`. It already clears

### 🔴 A correction the master plan gets wrong

It states the manifest's `theme_color`/`background_color` will be token-checked
by `tokens.test.js`. **They will not.** All three client guards walk `src/` only
and match `.js`/`.jsx`/`.css`; `public/manifest.webmanifest` is invisible to
them, and a manifest cannot use `var()` anyway. **If you want the manifest colour
guarded you must write a new test** that parses the hex out of `src/index.css`
and compares.

Conversely: **`src/sw.js` WOULD be scanned by `noHardcodedColors.test.js`.** A
service worker containing `background:#fff` for an inline offline response
**fails the build**. Put the offline page's styling in a real stylesheet or
inline the token values via the build.

### Test-harness constraint

`vitest.config.js` has two projects — `client` (jsdom, `src/**/*.test.{js,jsx}`)
and `server` (node) — both `isolate: true`, both excluding `**/scratch/**`. All
measured, documented, load-bearing; do not "simplify" either. **A service-worker
test at `src/sw.test.js` runs in jsdom, where `ServiceWorkerGlobalScope`,
`caches` and `self.addEventListener('push')` do not exist.** Decide: mock them,
or add a third vitest project with a node/miniflare-ish environment. Say which
in Task 8.

## 1. Goals

**Track A — email you can trust**

1. Every send is recorded with its outcome, so "did they get it?" is answerable.
2. Bounces and complaints are honoured. An unhonoured suppression list gets the
   sending domain blocked, which breaks password reset for everyone.
3. Retry has backoff **and a poison-message ceiling**.
4. Templates live in one place with one layout.
5. The free-tier ceiling is designed for, not discovered.

**Track B — an app on a phone**

6. Installable on Android and iOS, with real icons and a manifest.
7. The shell and static assets work offline; the app says so rather than showing
   a broken page.
8. An offline **outbox** for writes — designed as a reusable primitive, because
   v2.0's QR attendance depends on it.
9. Push notifications, opt-in, reusing the existing preference table.
10. A mobile UX pass on what the audit finds.

### Non-goals

- No native app, no app-store presence.
- No background sync of reads. Only writes go in the outbox.
- No push for `MESSAGES` in this release — a chat push needs a read-state
  round trip to avoid notifying about something already read in another tab, and
  that is its own design.

## 2. Architecture

### Track A

```
domain event ──▶ notification_jobs (EXISTS)  ──▶ notificationWorker (EXISTS)
                                                        │
                                                        ▼
                                              server/email.js
                                                        │
                        ┌───────────────────────────────┼──────────────────┐
                        ▼                               ▼                  ▼
                 email_messages              suppression check      provider API
                 (new: one row per                 (new)                  │
                  send, with state)                                       │
                        ▲                                                 │
                        └──────── POST /api/webhooks/email ◀──────────────┘
                                  (new, HMAC-verified)
```

`email_messages` is the delivery ledger: queued → sent → delivered → bounced /
complained / failed. `email_suppressions` is the consequence: an address that
hard-bounced or complained is never sent to again until a human clears it.

### Track B

```
src/main.jsx ──registers──▶ /sw.js  (injectManifest, hand-written)
                              │
              ┌───────────────┼────────────────┬─────────────────┐
              ▼               ▼                ▼                 ▼
        precache shell   runtime caches   outbox (IndexedDB)  push handler
        (immutable        per-route table  writes replayed     → showNotification
         assets)          — see §6.2      when online
                              │
                              ▼
                    purge on SIGNED_OUT
                    (from signOut AND postMessage)
```

**`injectManifest`, not `generateSW`.** The caching rules are security-sensitive
and must be readable in review. A generated service worker is a black box that a
reviewer cannot check against the FERPA hazard in §7.

## 3. Dependencies — and the decisions behind them

| Package | Track | Why, and the alternative rejected |
|---|---|---|
| `vite-plugin-pwa` | B | Manifest emission + `injectManifest` + precache manifest generation. Hand-rolling the precache list means it drifts from the build's hashed filenames. |
| `web-push` | B | VAPID signing. The protocol is not something to implement by hand. **Install at the root**, even though only the server uses it — the lockfile rule is absolute. |
| **Email provider SDK** | A | **Do not install one.** Use `fetch` against the provider's REST API. An SDK is a dependency, an auth surface and a breaking-change risk for what is one POST. |

**Playwright is an open question, not a decision.** `tests/e2e/` holds a spec but
`@playwright/test` is not a dependency and there is no npm script. A service
worker's update behaviour is very hard to test honestly in jsdom. Options:

- (a) Adopt Playwright: real coverage of the highest-risk thing in this release,
  at the cost of a large devDependency and CI time.
- (b) Do not: unit-test the SW's pure logic (cache-key derivation, route
  matching, outbox ordering) with mocked globals, and accept that
  update/skip-waiting is verified manually against a checklist.

**Recommendation: (b) for this release, with the manual checklist written into
`docs/operations/`.** Adopting a browser harness is a change to the project's
testing contract and belongs to a human (§15).

## 4. Database migrations

Numbering: v1.2c also claims **004**. Whichever release lands second shifts.
Assume v1.2c ships first, so these are **005** and **006**.

### `005_email_delivery.js` — additive, no rebuild

```sql
CREATE TABLE IF NOT EXISTS email_messages (
  id            TEXT PRIMARY KEY,
  job_id        TEXT,                       -- notification_jobs.id when queued
  user_id       TEXT,                       -- nullable: password reset pre-auth
  to_hash       TEXT NOT NULL,              -- sha256(lower(address))[0..31]
  to_domain     TEXT NOT NULL,              -- 'gmail.com' — deliverability triage
  template      TEXT NOT NULL,
  subject       TEXT NOT NULL,
  provider_id   TEXT,                       -- provider's message id, for webhooks
  state         TEXT NOT NULL DEFAULT 'queued'
                  CHECK(state IN ('queued','sent','delivered','bounced',
                                  'complained','failed','suppressed')),
  attempts      INTEGER NOT NULL DEFAULT 0,
  last_error    TEXT,
  queued_at     TEXT NOT NULL,
  sent_at       TEXT,
  settled_at    TEXT,
  FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE SET NULL
);
CREATE INDEX IF NOT EXISTS idx_email_messages_provider ON email_messages(provider_id);
CREATE INDEX IF NOT EXISTS idx_email_messages_state ON email_messages(state, queued_at DESC);

CREATE TABLE IF NOT EXISTS email_suppressions (
  address_hash  TEXT PRIMARY KEY,           -- sha256(lower(address))[0..31]
  reason        TEXT NOT NULL CHECK(reason IN ('hard_bounce','complaint','manual')),
  detail        TEXT,
  created_at    TEXT NOT NULL,
  cleared_at    TEXT,
  cleared_by    TEXT
);
```

**Why `to_hash` and not the address.** The account's address is already in
`users.email`; a second copy in a table with a different retention schedule is a
second thing to purge on deletion and a second thing to leak. The hash answers
every question the ledger needs — "was this address suppressed", "did this
message reach this person" — and `to_domain` (not personal) carries the
deliverability signal. **`user_id` is `ON DELETE SET NULL`, not CASCADE:** the
delivery record of a bounce is operational history that should survive an account
deletion, and after the null it names nobody.

**Why suppression is keyed by hash and not by `user_id`:** password reset and
email-change confirmations go to addresses that may not belong to any account row
yet.

### `006_push_subscriptions.js` — additive

```sql
CREATE TABLE IF NOT EXISTS push_subscriptions (
  id            TEXT PRIMARY KEY,
  user_id       TEXT NOT NULL,
  endpoint      TEXT NOT NULL UNIQUE,
  p256dh        TEXT NOT NULL,
  auth          TEXT NOT NULL,
  user_agent    TEXT,                       -- family only, for support
  created_at    TEXT NOT NULL,
  last_used_at  TEXT,
  failure_count INTEGER NOT NULL DEFAULT 0,
  FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_push_subs_user ON push_subscriptions(user_id);
```

`endpoint UNIQUE` is what makes re-subscribing idempotent — a browser hands back
the same endpoint, and `StrictMode`'s double-invoked effect will subscribe twice.
`ON DELETE CASCADE` because a subscription is worthless without its account.

**No migration is needed for the `'push'` channel** — verified, not assumed:

```sql
CREATE TABLE IF NOT EXISTS notification_preferences (
  user_id TEXT NOT NULL,
  category TEXT NOT NULL,
  channel TEXT NOT NULL,          -- no CHECK, no enum
  enabled INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY (user_id, category, channel),
  FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE CASCADE
)
```

`channel` is plain `TEXT NOT NULL` with no constraint, so `'push'` rows insert
freely. `category` is the same, which matters for the pseudo-pair the global
opt-out already uses (`('global', 'email')`).

**The flip side, and it is the real risk here:** nothing at the schema level
stops a typo. `'psuh'` inserts happily, silently disables nothing, and the user's
preference appears not to work. **Validate the channel against a known set in the
route** (`server/routes/userRoutes.js`'s `POST /api/user/preferences`) and reject
an unknown one, rather than relying on a constraint that does not exist.

- [ ] All migrations: **idempotency test** (`up` twice), ISO-8601 UTC timestamps
      from JS never `datetime('now')` (TD-10), and
      `node bin/migration-checksums.mjs` after.

## 5. Track A — backend

### 5.1 Provider choice

**Constraint from the brief: a free provider, no credit card.**

| Provider | Free tier | Notes |
|---|---|---|
| **Brevo** | 300/day | No card. Transactional API + webhooks. Day-bounded, which is the wrong shape for a school (see below). |
| **Resend** | 3,000/month, 100/day | No card. Clean API. 100/day is low for a school. |
| **Mailgun** | 100/day after trial | Card required for the good tiers. |
| **Google Workspace SMTP relay** | ~2,000/day per user | **Strictly better if the district has Workspace** — district domain, no new vendor, no IT ticket for DNS. Requires the district to have it. |

**Design for the ceiling, because a school day is spiky.** An organizer
broadcasting to 300 volunteers at 8am will hit any of these limits in one action.
Required behaviour, not optional:

- The worker checks a **daily budget** before sending and leaves over-budget jobs
  `pending` with `next_attempt_at` set past midnight UTC-offset local.
- Jobs carry a **priority**: transactional (password reset, email change,
  verification) always sends; bulk (broadcast, digests) yields to the budget.
  **A password reset must never be starved by a broadcast** — that is the failure
  that locks someone out of their account.
- The budget is a config value, not a literal, so raising a tier is a deploy not
  a code change.
- When the budget is exhausted, log it and surface it on the v1.2c error
  dashboard as a `SYSTEM`-severity group. Silent non-delivery is the worst case.

*Assumption if Q4 is unanswered: Resend for transactional, and bulk broadcast
deferred behind the budget until the district's Workspace status is known.*

### 5.2 Suppression

- Checked **before** every send, by `to_hash`. A suppressed address short-circuits
  to `state = 'suppressed'` and does not call the provider.
- **Hard bounce** and **complaint** both suppress. A soft bounce does not — it
  retries with backoff and gives up at the ceiling.
- **A suppressed address that becomes valid again** is a real case (a full
  mailbox emptied, a school account reactivated). Clearing is **manual**, gated
  on `audit.read`-class capability, audit-logged through `server/auditLog.js`,
  and visible in the UI as "we could not reach this address" on the account's own
  settings page — so the person can tell someone rather than silently never
  receiving mail again.
- **The user-visible half matters as much as the ledger.** If the account's own
  address is suppressed, `VerifyEmailWall` and the email card must say so.

### 5.3 The webhook

`POST /api/webhooks/email`, **unauthenticated by necessity** — the provider has
no session.

- **Authenticated by HMAC** over the raw body with a shared secret from config.
  This requires the **raw** body, and `express.json()` has already consumed it —
  mount a `express.raw({ type: 'application/json', limit: '64kb' })` on this path
  **before** the global json parser, or verify against a re-serialisation, which
  is fragile. Prefer the raw mount and say why in a comment.
- Production **fails closed** on a missing webhook secret, matching the existing
  `JWT_SECRET`/`SMTP_*` guards. A webhook that accepts anything is an endpoint
  that lets a stranger suppress a victim's address — a denial-of-service on
  password reset.
- **Idempotent**: providers retry. Key on `(provider_id, event_type)`.
- Its own rate limiter, following the eight in `app.js`.
- **No `ROUTE_REGISTRY` entry** — it has no `authenticateToken`, so Guard 2 never
  examines it, and adding an entry fails the build as stale.

### 5.4 Templates

`server/email/templates/` — one layout, one file per message, plain-text
alongside HTML. Every template gets a rendering test asserting the subject, that
no `undefined` appears in the body, and that the unsubscribe/preferences link is
present for non-transactional mail. Transactional mail (password reset) must
**not** carry an unsubscribe link.

## 6. Track B — the service worker

### 6.1 The dangerous part, addressed first

**A bad service worker is a permanently broken app for every user who loaded it,
with no server-side remedy.** Design these four things before writing a cache
rule:

1. **Versioning.** Every cache name carries the build's version:
   `wev-shell-<version>`, `wev-api-<version>`. `activate` deletes every cache
   whose name does not match the current version. Read the version from
   `server/package.json`-derived build info, not a hand-edited constant.
2. **Update strategy.** `skipWaiting` is **not** automatic. A new worker taking
   over mid-session can serve a new shell to a page holding old JS chunks, which
   is a white screen. Instead: the new worker waits, the app detects
   `registration.waiting`, and shows a non-blocking "A new version is ready —
   reload" prompt. `skipWaiting` fires only on that click.
3. **A kill switch.** `/sw-kill.json` (or a flag on `/health`) which, when true,
   makes the worker `self.registration.unregister()` and clear all caches on next
   fetch. **This is the only remedy if a bad worker ships**, so it must be in the
   first version, not added later. Test it.
4. **`sw.js` must be served `no-cache`.** Add an explicit rule to `app.js`'s
   static handling — today it matches neither the `index.html` branch nor the
   `assets/**` branch and gets only an ETag. And because `app.get('*')` returns
   `index.html` for a missing file, add a test that `/sw.js` returns JavaScript
   and not HTML in a production build.

**`VITE_*` values are compiled into the bundle**, so a changed value needs a
rebuild — and with a cached shell, a rebuild the user has not fetched. The
version-keyed caches plus the reload prompt are what make that safe; say so in
the SW header comment.

### 6.2 Caching rules

| Pattern | Strategy | Reason |
|---|---|---|
| Hashed `assets/**` | CacheFirst, immutable | Content-addressed; safe forever |
| `index.html` | NetworkFirst | Must be able to change |
| `/api/auth/**`, `/api/oauth/**`, `/api/auth/reauth/**` | **NetworkOnly** | Never cache a credential exchange or a step-up grant |
| `/api/privacy/**` | **NetworkOnly** | A cached data export is the export leaking |
| `/api/errors/**` | **NetworkOnly** | Owner-only |
| `GET /api/events` | NetworkFirst, 3s timeout, 5min | The browse list is the one worth having offline |
| `GET /api/weather`, `/api/geocode`, map tiles | StaleWhileRevalidate, capped | Slow, non-personal, rate-limited upstream |
| Every mutation (POST/PATCH/PUT/DELETE) | NetworkOnly + outbox | See §6.3 |
| Navigation fallback | `/offline.html` | A page, not a browser error |

**Everything not in this table is NetworkOnly.** Default-deny, for the same
reason `authz.js` denies unknown capabilities: a new personal endpoint added
later must not be cached because nobody thought to exclude it.

### 6.3 The outbox — designed as a primitive

v2.0's QR attendance depends on this, so it is not a one-off.

- IndexedDB store of `{ id, url, method, headers, body, queuedAt, attempts }`.
- Replayed on `online` and on SW activate, **in insertion order**, one at a time.
  Order matters: two edits to the same event replayed out of order silently lose
  one.
- **Never queue a request carrying a step-up grant.** A challenge lives five
  minutes and is single-use; replaying it half an hour later fails with `expired`
  and the user cannot tell why. Any request with the `X-Reauth-Challenge` header
  fails fast and tells the user to retry online. **This is a hard rule** — put it
  in the outbox code, with the reason.
- Idempotency: replayed writes need to be safe. Most of this app's mutations are
  already idempotent by shape (`ON CONFLICT` upserts, status transitions), but
  **application creation is not**. Either add a client-generated idempotency key
  or exclude that endpoint. Say which.
- Cap the outbox (say 100 items, 7 days) and surface its depth in the UI. A
  silent outbox that never drains is data the user thinks they saved.

### 6.4 🔴 The FERPA hazard — the sharpest risk in this release

A service-worker cache is **origin-scoped, not session-scoped.** On a shared
school Chromebook, student A's cached `/api/events?mine=true` response — or a
roster, or a profile — is readable by student B who logs in next. **This is a
student-records disclosure, not a bug.**

Required mitigations, all of them:

1. **Never cache a response to a request that carried a session cookie, except
   the explicitly allowlisted `GET /api/events`.** Everything else personal is
   NetworkOnly by the default-deny rule.
2. **On sign-out, delete every `wev-*-api` cache and clear the outbox.** Hook
   `signOut` in `src/session/SessionProvider.jsx` — which already clears
   `sessionStorage` and calls `clearStepUpState()`, with a comment about shared
   computers — **and** `api.logout()`, which swallows network failures so it runs
   offline too.
3. **Also purge on a `SIGNED_OUT` `postMessage`**, so a sign-out in one tab
   clears the cache another tab's worker holds.
4. **Purge on user-id change.** If `getMe` returns a different user id than the
   cache was populated for, purge before serving anything. This is the backstop
   for a sign-out that never ran (tab closed, battery died).
5. **Include the user id hash in the API cache name.** Then a different user
   physically cannot read the previous one's entries, and (2)–(4) become
   defence in depth rather than the only line.

Every one of these gets a test. This is the section to re-read before shipping.

### 6.5 Push

- VAPID keys in config; production fails closed if push is enabled without them.
- `POST /api/push/subscribe`, `DELETE /api/push/subscribe` — authenticated,
  `SELF_ONLY`, so each needs a `ROUTE_REGISTRY` entry with a reason (they write
  only the caller's own rows) **or** a capability gate. Prefer the registry entry
  with `SELF_ONLY`, matching the existing 25 entries.
- **The cookie the SW cannot read is not a problem**: `subscribe` is a normal
  authenticated fetch from the page, and the push *delivery* is signed by the
  server with VAPID and needs no cookie at all.
- Add `'push'` to the channels in `NotificationPreferences.jsx` and to whatever
  the worker consults. Default **off** — an opt-in, because a notification
  permission prompt on load is the pattern browsers punish and users refuse.
- **Prompt at a moment of intent**, not on load: after a user accepts a shift, or
  from Settings. Never in a `useEffect` on mount.
- **Dedupe against the socket.** A foreground tab connected via `socket.io` and a
  push for the same event will both fire. Tag notifications with the
  notification id and use `tag` + `renotify: false` so the OS collapses them, and
  have the page tell the SW it is visible.
- **iOS Safari specifics, named rather than assumed:** push requires the app to
  be **installed to the home screen** (iOS 16.4+); `window.Notification` is
  `undefined` in a normal Safari tab, which the existing bell code already
  stumbles over; there is no `beforeinstallprompt`, so installation must be
  explained with instructions rather than triggered; and standalone mode has no
  browser chrome, which is where the `vh`/`dvh` issue in §6.6 bites.

### 6.6 Mobile UX audit

Findings already established, so the audit has a starting point:

- **`src/index.css` uses `dvh` in exactly one place** (the auth screen, with a
  comment explaining why `100vh` pushed the submit button under the browser bar).
  **Everything else uses `vh`.** In standalone mode there is no chrome, so `vh`
  and `dvh` diverge differently again. Sweep them.
- **There is no `@media (display-mode: standalone)` rule anywhere.** Installed,
  the app has no back button and no address bar; at minimum the top bar needs
  safe-area padding and in-app back affordances.
- `env(safe-area-inset-*)` appears in 13 places already — the pattern exists,
  it is coverage that is missing.
- **`.mobilenav` has two conflicting `@media (max-width:700px)` blocks**, the
  second winning with `display: flex !important` and horizontal scroll-snap.
  Reconcile them; a `!important` fighting an earlier rule in the same file is a
  latent layout bug.

## 7. Security considerations

1. **The FERPA cache hazard (§6.4) is the top risk in this release.** Five
   mitigations, all tested.
2. **The webhook is an unauthenticated write that can suppress an address** —
   HMAC, fail-closed secret, idempotency, rate limit. Without HMAC it is a
   remote denial-of-service on password reset.
3. **Never cache or replay a step-up grant** (§6.3).
4. **A service worker can rewrite every response the app sees.** Same-origin only
   (CSP `defaultSrc 'self'` already enforces `worker-src`), reviewed by hand,
   `injectManifest` so it is readable.
5. **Email addresses of minors**: hashed in the ledger, domain kept separately,
   never in a log line. Follow v1.2b's `ip_hash` precedent.
6. **Push payloads must not carry personal content.** "You have a new message"
   not the message body — a notification renders on a lock screen in a classroom.
7. **`sw.js` served `no-cache`**, or a broken worker outlives the fix.

## 8. UX flows

**Install.** A dismissible "Add to home screen" hint after a second visit, with
platform-specific instructions on iOS (no `beforeinstallprompt`). Never a modal
on first load.

**Offline.** A persistent, non-blocking banner. Cached content stays usable;
uncached navigations get `/offline.html`. A write goes to the outbox and the UI
says "will send when you're back online" — never a success message for something
that has not happened, which is the same class of lie as the toast-only buttons
this settings screen used to be full of.

**Update.** "A new version is ready — reload." Never a forced reload; someone is
mid-form.

**Push opt-in.** Offered after accepting a shift, and in Settings. Declining is
remembered and not re-asked.

**Suppressed address.** The account's own settings say "we could not reach this
address" with what to do, so the user is not silently unreachable.

## 9. Testing strategy

- **Server tests boot the real app** via `server/testServer.js`. **Never
  statically import anything reaching `db.js`** at the top of a server test file
  — dynamic imports inside hooks only.
- **Email:** suppression short-circuits before the provider (assert the provider
  fetch was not called); a hard bounce suppresses and a soft bounce does not; the
  poison ceiling stops retrying; the daily budget defers bulk but never
  transactional; the webhook rejects a bad HMAC and is idempotent under replay;
  every template renders with no `undefined`.
- **The budget test is the one that matters most**: queue 400 bulk jobs and one
  password reset, assert the reset went.
- **Service worker:** unit-test the pure logic with mocked globals — route
  matching (assert `/api/privacy/export` is NetworkOnly), cache-name derivation
  including the user hash, outbox ordering, the step-up refusal, the kill switch,
  and the version-purge on activate.
- **The FERPA tests, explicitly:** populate the API cache as user A, switch to
  user B, assert nothing of A's is readable; assert `signOut` purges; assert a
  `SIGNED_OUT` postMessage purges.
- **Mutation-test every guard.** Delete the check, watch its test fail, restore.
- **Manual checklist in `docs/operations/`** for what jsdom cannot cover:
  install on Android and iOS, offline reload, update prompt, kill switch, push on
  an installed iOS PWA.

## 11. Task breakdown

Track A and Track B are independent until Task 12. They can run in either order;
A first is recommended because push depends on it and because the SW is riskier.

### Track A

**Task 1 — the delivery ledger schema.** Migration `005`. Tests: shape,
idempotency, ISO-8601. Commit: `feat: add the email delivery ledger and suppression list`

**Task 2 — record every send.** `server/email.js` writes `email_messages` around
each send; the worker records outcomes. Tests: a send produces one row in

**Task 6 — templates.** One layout, per-message files, plain-text alongside.
Tests: render, no `undefined`, unsubscribe present for bulk and absent for

**Task 7 — manifest and icons.** `vite-plugin-pwa` (root install),

## 12. Rollout order

1. **Track A entirely**, and let it run in production for a week. Delivery
   tracking is observability; you want it trustworthy before you depend on it.
2. **Track B Tasks 7–11**, but ship the service worker **behind a flag** (an env
   value that makes `main.jsx` skip registration) for one deploy, so the kill
   switch and the update prompt are exercised by the team before any student
   loads a worker.
3. **Task 12 (push)** last. It is the most visible and the least reversible —
   people who granted permission and got a bad notification do not grant it
   again.
4. Task 13 can land any time.

**The service worker is the one thing in this roadmap that can break the app for
a user with no server-side fix.** Ship it separately from anything else, so a
rollback is unambiguous.

## 13. Risk analysis

| Risk | L | I | Mitigation |
|---|---|---|---|
| **🔴 Cached personal data served to the next student on a shared device** | Medium | **Critical** | §6.4's five mitigations, user-hash in the cache name, tests for each |
| **A bad SW permanently breaks the app** | Medium | **Critical** | Kill switch in v1; version-keyed caches; no auto-`skipWaiting`; flagged first deploy; `sw.js` `no-cache` |
| **Free tier exhausted; password resets silently stop** | **High** | Critical | Priority classes; transactional never yields; budget surfaced as an error group |
| **Unauthenticated webhook lets a stranger suppress a victim's address** | Medium | High | HMAC over the raw body; fail-closed secret; audit-logged clearing |
| **Replayed outbox writes duplicate an application** | Medium | Medium | Idempotency key or exclude the endpoint — decide in Task 11, do not leave implicit |
| **A step-up grant replayed from the outbox** | Medium | Medium | Hard refusal in the outbox, with the reason in the code |
| **Push notification leaks content to a lock screen** | Medium | Medium | Title-only payloads |
| **`sw.js` served as `index.html`** | Medium | High | Explicit static rule + an assertion, because the SPA fallback makes it silent |
| **iOS behaves unlike Android and the feature looks broken** | High | Low | Named limitations, instruction-based install, install-gated push |
| **Suppressed user is silently unreachable for ever** | Medium | Medium | Surface it on their own settings page; manual clearing |
