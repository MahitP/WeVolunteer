# v1.4 — Meaning Implementation Plan

> **For agentic workers:** implement task-by-task. Steps use `- [ ]` checkboxes.
> Read `docs/plans/2026-08-02-roadmap-index.md` first if you have no context.

**Goal:** make the data the app already holds answer questions a real person
asks. A taxonomy worth filtering by, dashboards worth looking at, and a map that
respects its provider's terms.

**Order is not negotiable: W7 → W5 → W6.** Category analytics built on the
current `CHECK` constraint would have to be rebuilt when the taxonomy lands, so
building W5 first means building it twice. W6 is last because it is polish and
because its distance filter shares a query builder with W7's tag filter.

**Depends on:** v1.2a (merged), v1.2b (complete). v1.2c strongly recommended —
this release changes read paths across every dashboard, and a silent 500 in an
aggregate query is exactly what error capture is for.

## 0. What exists — verified, and it changes the plan substantially

### 🔴 The taxonomy tables in the master plan do not exist

`event_categories`, `event_tags`, `event_tag_map` and `user_tag_interests` appear
**only in the master plan document**. There is no `categories` table, no `tags`

```sql
category TEXT CHECK(category IN ('School','5K','Food Pantry','Fundraiser','Other')) NOT NULL
```

the single largest risk in the release and §4 addresses it directly.

`attendee_visibility NOT NULL DEFAULT 'accepted'`, `address`, `latitude REAL`,
`longitude REAL`. Status is `CHECK(status IN ('open','closed','completed','cancelled'))`.

## 4. 🔴 Database migrations — the CHECK-constraint rebuild

Numbering: v1.2c claims 004, v1.3 claims 005–006. **Assume these are 007–008**;
verify `server/migrations/index.js` and adjust.

### The problem

`events.category` is `CHECK(category IN ('School','5K','Food Pantry','Fundraiser','Other'))`.
SQLite cannot alter a CHECK. Introducing a `categories` table means the column
must either lose its constraint or become a foreign key — either way, **a 12-step
table rebuild of `events`**.

### Two options — choose deliberately

**Option A — full rebuild, `category_id` FK.** Clean end state. Requires all six
ENGINEERING_GUIDE §8.3 guards on a table with **eight child tables** — counted
from the schema, not from memory:

`slots`, `applications`, `attendance`, `conversations`, `event_comments`,
`user_favorites`, `event_announcements`, `auto_select_runs`.

An earlier draft of this plan said "five" and then listed seven, omitting
`conversations`. That is exactly the mistake §8.3's fifth guard exists to catch —
a **schema-derived** child-row count, queried from `pragma foreign_key_list`
rather than typed out, so a table nobody remembered is still counted. Derive the
list; do not copy the one above. A mistake here anonymises or orphans real
volunteer data.

**Option B — additive `category_id`, leave the old column.** Add a nullable
`category_id` via `addColumnIfMissing`, backfill it from the string, and read
only `category_id` from then on. **No rebuild, no risk.**

> ### 🔴 The catch, and you must design around it
>
> `events.category` is **`NOT NULL`** as well as CHECK-constrained:
>
> ```sql
> category TEXT CHECK(category IN ('School','5K','Food Pantry','Fundraiser','Other')) NOT NULL
> ```
>
> Adding `category_id` does **not** free new inserts from that. Every
> `INSERT INTO events` must still supply one of those five strings, or the write
> fails the CHECK — so a genuinely new category ("Beach Cleanup") cannot be
> written into the old column. **Option B therefore does not, on its own, let a
> new category be added without a migration.** Getting this wrong looks like a
> working feature until the first event uses a new category and the insert is
> rejected.
>
> **The design that does work.** Keep the old column satisfied with a
> **compatibility value**, chosen from the five, while `category_id` carries the
> truth:
>
> - The five seeded categories map to their own original string, so nothing
>   about existing events changes.
> - Every category added later writes **`'Other'`** into `category`, because
>   that is what a pre-taxonomy reader should see for something it has no name
>   for — and `'Other'` is already a legal value with exactly that meaning.
> - `categories` gains a **`legacy_value`** column holding which of the five to
>   write. It is not cosmetic: it is what makes the insert legal, so it is
>   `NOT NULL` with its own CHECK against the same five strings.
> - **One writer.** Put the insert behind a single helper so no route composes
>   the pair by hand — the failure mode is a caller that sets `category_id` and
>   forgets `category`, which the CHECK catches only at runtime.
>
> Once the rebuild eventually happens, `category` and `legacy_value` both go.

**Recommendation: Option B, with the compatibility value above**, and the
rebuild deferred to a task of its own once the taxonomy has proven itself in
production. The reasoning is proportionality: the rebuild's blast radius is every
event, application and attendance row in the database, and the benefit is
tidiness. ENGINEERING_GUIDE §8.3's guards exist because a rebuild went wrong
once; the safest rebuild is the one you do not need to do yet.

**Note what this costs honestly.** Option B is not free — it is a dead column, a
`legacy_value` column that exists only to satisfy it, and a rule every writer has
to honour. Option A pays that off in one dangerous migration. Someone choosing
between them should be choosing between those two prices, not between "safe" and
"unsafe".

**If a human chooses Option A**, the migration MUST carry all six guards, copied
structurally from `server/migrations/001_authz_roles.js` — the only sanctioned
rebuild in the repo:
1. Back up first.
2. `PRAGMA foreign_keys = OFF` **outside** the transaction, then **assert it took
   effect** — it is a silent no-op inside an open transaction, and a silent
   failure was found to be invisible to the four original guards.
3. An **explicit column list**, never `SELECT *` — column order differs between
   databases.
4. An unknown/missing-column guard.
5. A **schema-derived child-row count comparison**, before and after.
6. `foreign_key_check` before commit.
Plus `ownTransaction: true`.

### `007_event_taxonomy.js` (Option B shape)

```sql
CREATE TABLE IF NOT EXISTS categories (
  id          TEXT PRIMARY KEY,
  slug        TEXT NOT NULL UNIQUE,
  label       TEXT NOT NULL,
  description TEXT,
  colour_token TEXT,            -- e.g. 'chart-2'; a TOKEN NAME, never a hex
  -- Which of events.category's five legal strings to write alongside
  -- category_id, because that column is NOT NULL and CHECK-constrained. See the
  -- red box in §4. NOT NULL with its own CHECK: a null here makes every insert
  -- using this category fail, at runtime, in production.
  legacy_value TEXT NOT NULL
                 CHECK(legacy_value IN ('School','5K','Food Pantry','Fundraiser','Other')),
  sort_order  INTEGER NOT NULL DEFAULT 0,
  archived_at TEXT,             -- archive, never delete: events reference it
  created_at  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS tags (
  id         TEXT PRIMARY KEY,
  slug       TEXT NOT NULL UNIQUE,
  label      TEXT NOT NULL,
  created_by TEXT,
  created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS event_tags (
  event_id TEXT NOT NULL,
  tag_id   TEXT NOT NULL,
  PRIMARY KEY(event_id, tag_id),
  FOREIGN KEY(event_id) REFERENCES events(id) ON DELETE CASCADE,
  FOREIGN KEY(tag_id)   REFERENCES tags(id)   ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_event_tags_tag ON event_tags(tag_id);
```

Then `addColumnIfMissing('events', 'category_id', 'TEXT REFERENCES categories(id)')`.

**`colour_token` holds a token NAME, not a colour.** A hex in the database would
be a colour literal that `noHardcodedColors.test.js` cannot see, defeating the
guard by going around it, and it would not follow dark mode. Validate on write
that the name resolves against the known `--chart-*` set.

**Archive, never delete.** An event references its category; deleting a category
either breaks the reference or rewrites history.

### Backfill and the rows that fit nothing

Seed `categories` with exactly the five existing values so **no event changes
meaning**. Then:

- [ ] Backfill `category_id` by matching the string. Assert afterwards that
      **zero** events have a null `category_id` — with five seeded categories
      covering the five legal values, any null means the CHECK was already
      violated, which is worth knowing about loudly.
- [ ] Seed each of the five with `legacy_value` equal to its own name, so no
      existing event changes meaning and no existing insert changes behaviour.
- [ ] **`'5K'` and `'Food Pantry'` must survive.** They are narrow, and a
      well-meaning "tidy taxonomy" that folds them into "Other" destroys the
      district's own reporting history. Renaming a label later is a one-row
      update; merging categories is not reversible.
- [ ] New categories a human adds later are additive and need no migration —
      which is the entire point of the change.

- [ ] Every migration: **idempotency test** (`up` twice), ISO-8601 UTC from JS
      never `datetime('now')` (TD-10), then `node bin/migration-checksums.mjs`.

## 5. W5 — dashboards, and the rule that governs them

> **The user's explicit instruction: "Do not add meaningless graphs."**

So every chart below states the question, the decision it drives, and why a
number alone would not do. **Anything that cannot answer all three is cut** — and
several existing things are cut on that basis.

### 5.1 Invariant that outranks every dashboard

**Credited hours are never stored on a user.** They are derived on every read as
`SUM(hours_awarded) WHERE present = 1`, every change is appended to
`hours_ledger`, and `npm run verify:hours --workspace=server` exits non-zero on
mismatch.

**A dashboard that caches a total is a correctness bug.** If an aggregate becomes
slow:

- First, add an index and measure. The dataset is one school district.
- Only if that fails, a materialised summary — and then it must be derived by a
  job that recomputes from `attendance`, never incremented on write, with
  `verify:hours` extended to check it. State the staleness window in the UI.
- **Do not** add a `volunteeredHours` column. Note that
  `VolunteerDashboard` already reads `currentUser.volunteeredHours` — trace where
  that comes from before trusting it; if it is derived per-request, fine, and if
  it is stored, that is a pre-existing bug this release should surface.

### 5.2 Per dashboard

**Volunteer.** Keep: hours-vs-goal meter (question: *am I going to make my
requirement?* — decision: sign up for more, or not; a bare number cannot show
distance-to-goal). Keep `DonutChart` of hours by category (*where has my time
gone?* — drives what to do next). Keep the `BarChart` of monthly hours (*am I
falling behind?* — a trend is the answer; a total is not).

- [ ] **`HOUR_GOAL = 25` is a hardcoded literal.** A service-hour requirement is
      school policy and differs by school and grade. Move it to configuration at
      minimum; ideally per-school. Until then, label it honestly rather than
      implying the app knows their requirement.
- [ ] **Cut** nothing here; this dashboard is the one that already passes the
      test.

**Organizer.** Currently has **no charts**, and should gain exactly one:
fill-rate per upcoming event (*which of my events will be under-staffed?* —
drives who to chase; a list of counts buries the one at 30%). Use `Sparkline` or
a compact `BarChart`.

- [ ] Wire up the already-fetched-and-unused `stats.perEvent` rather than
      computing it again client-side.
- [ ] Three of four stat tiles are client-computed from the `applications` prop.
      Leave them — they are cheap and correct — but **stop fetching the four
      server fields nobody reads** (`eventCount`, `totalAccepted`,
      `totalPending`), or start using them. Fetching and discarding is how a
      response shape drifts unnoticed.

**Admin/staff.** Keep the three `RateCard`s (show-up rate, completion rate,
participation rate) — each is a question a principal asks. Keep monthly hours.

- [ ] **Cut one of the two `BarChart`s.** Both are fed `totals.monthlyHours`;
      hours and volunteer-count over the same months are two renderings of one
      trend, and the second earns nothing. Keep hours; show volunteers as a

- [ ] **Either render or stop returning** `signupsByMonth`, `selectionSplit`,

      being used?* — and is a candidate to render. The rest are counts already
      shown elsewhere.
- [ ] Add category breakdown once W7 lands (*which kinds of service is the
      district actually doing?* — drives where to recruit partners).

**Partner.** `analytics.public` exists and nothing uses it. Either build a
minimal partner view or leave the capability unused — but **do not** grant
partners a dashboard scoped by accident. A partner seeing another school's
numbers is the failure mode.

## 6. W6 — maps, location, weather

### 6.1 Provider terms are a requirement, not a footnote

**Constraint: no paid APIs, no credit card.**

- **Tiles.** The [OSM Foundation Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/)
  is explicit: no heavy use, a valid identifying `User-Agent`/`Referer`, required
  attribution, no bulk downloading. `tile.openstreetmap.org` is **not** a CDN for
  an app to lean on. CartoDB basemaps (already in the CSP) have their own terms.
  - [ ] **Attribution must be visible on every map**, not in a footer elsewhere.
        This is a licence condition.
  - [ ] Cap tile usage: no prefetching, no bulk area loads, sensible max zoom.
        The v1.3 service worker's StaleWhileRevalidate cache with a capped entry
        count is the mitigation — cross-reference it.
- **Geocoding.** Nominatim's policy requires an identifying User-Agent, **max 1
  request/second**, and no bulk geocoding. `GET /api/geocode` already exists with
  its own `geocodeLimiter` — verify it actually enforces ≤1/s **server-wide**,
  not per-IP. A per-IP limiter does not protect a shared upstream. Cache
  geocoding results in the database, keyed by normalised address: an event's
  address does not move.
- **Weather.** Open-Meteo is free for non-commercial use with no key and no card.
  `GET /api/weather` already exists.
  - [ ] **It is fully unauthenticated** (`weatherLimiter` only). For a
        server-side proxy of a free upstream that is defensible, but it means
        anyone can use the district's server as a weather proxy. Decide: add
        `authenticateToken`, or keep it open and document why. Do not leave it
        undecided.

### 6.2 🟢 Distance filtering is ALREADY BUILT — verify and preserve, do not rebuild

An earlier draft of this plan specified this as new work, with a coarse bounding
box and a client-side haversine refine. **That was wrong on both counts.** It
exists, in SQL, and its design is the opposite of what that draft proposed.

What `server/eventQuery.js` already does (329 lines, its own module specifically
so the predicates can be tested against a database rather than only through the
route):

- `parseEventFilters` validates `lat`, `lng` and `maxDistance`, requires the
  coordinates to travel together, bounds them, and refuses `sort=distance`
  without them.
- `eventQueryFragments` builds a **full-precision haversine expression in SQL**
  using `radians()`, exposed as `distance_miles`.
- Distances are in **MILES** (`R = 3958.8` in `helpers.js`), not kilometres.
- An event with **no coordinates is excluded** by a distance filter and sorts
  **last** by distance — deliberately mirroring the client behaviour this
  replaced (`distance != null` and `?? Infinity`).
- There is a documented named-parameter trap: the distance expression sits in the
  SELECT list, so `sort=distance` with no `maxDistance` still binds `lat`/`lng`
  or SQLite raises "Unknown named parameter" and the request 500s. **Read that
  comment before touching the fragments.**

**So the privacy question is about behaviour that already ships, not a design
choice still open.** The facts, verified:

- **Precise coordinates DO reach the server**, in the query string. That is
  required — the sort is computed in SQL so the server can paginate, which is the
  whole reason this moved off the client.
- **They are NOT logged.** `server/app.js`'s request-log middleware does
  `req.originalUrl.split('?')[0]` — the query string is stripped deliberately, so
  a position never reaches the log or a log aggregator.
- **They are NOT stored.** No column holds a user's location.

That posture is sound, and the load-bearing part of it is one line of
`app.js`. So the work here is to keep it true, not to redesign it:

- [ ] **Do not widen the request log to include query strings.** That single
      change turns every "near me" search into a stored position for a minor. If
      request logging is ever made more detailed, coordinates must be excluded
      explicitly — and v1.2c's error capture has the same obligation, which is why
      its plan captures the Express **route pattern** rather than the URL.
- [ ] **Do not add a stored location** as part of this release. If a "home area"
      is genuinely wanted later: a postal code or a school, never a street
      address; opt-in; in the privacy export and the deletion path; and its own
      privacy review.
- [ ] `src/contexts/LocationContext.jsx` already holds the browser position in
      memory. Read it before adding anything client-side.

**Coarsening to a bounding box is NOT recommended.** It would degrade an accurate
sort — the feature's entire point — to protect a value that is already neither
logged nor stored. The exposure it addresses is the coordinate being *in flight*
over TLS to a server that discards it, which is not where the risk is.

- [ ] What remains for W6 is genuinely W7's job: **tag and category filters must
      compose with the distance predicates already in `eventQuery.js`**, in that
      one module, so there is one place where filters combine and one place to
      review for injection. That is Task 4's work, not a separate distance task.

## 7. API changes

| Route | Change | Gate |
|---|---|---|
| `GET /api/events` | `?category=`, `?tags=`, `?near=lat,lon&radius=` | unchanged (`event.view`) |
| `GET /api/categories` | new — list, for filter UI and event form | authenticated; `event.view` |
| `POST /api/categories` | new | `requireCap('event.moderate')` or a new admin cap — prefer existing |
| `PATCH /api/categories/:id` | new — rename, reorder, archive | as above |

| `POST /api/events` / `PATCH /api/events/:id` | accept `categoryId`, `tags[]` | unchanged |
| `GET /api/stats/*` | fields added/removed per §5 | unchanged |

- [ ] Every new authenticated route gets a **`capabilityGate`** (so no registry
      entry) or a reviewed `ROUTE_REGISTRY` entry. Not both — a gated route with
      an entry fails as stale.
- [ ] **Tag creation is a write by a low-privilege user.** Cap tags per event
      (say 5), cap tag length, normalise to a slug, and rate-limit creation, or
      `tags` becomes a spam table. Deduplicate case-insensitively — the repo
      already has precedent in `dedupeCaseInsensitiveUsernames`.

## 8. UX flows

**Browsing.** Category chips plus a tag typeahead on `BrowseEvents`. Filters are
in the URL so a filtered view is shareable and survives a reload — and so the
back button works, which it currently does for `?event=`.

**Creating.** Category is required (it already is); tags are optional with
suggestions from existing tags, to converge vocabulary rather than fragment it.

**Managing categories.** A small admin screen: rename, reorder, archive.
Archiving explains that existing events keep it and it stops being offered.

**Near me.** A "sort by distance" control that asks for location at the moment it
is used, never on page load, and works without it (falls back to date order).

**Dashboards.** Same information architecture, fewer and better numbers. Every
chart has a one-line caption saying what it answers — which is also the test from
§5: if the caption cannot be written, the chart is cut.

## 9. Testing strategy

- **Server tests boot the real app** via `server/testServer.js`. **Never
  statically import anything reaching `db.js`** at the top of a server test file
  — dynamic imports inside hooks only.
- **Migration:** idempotency; the backfill leaves zero null `category_id`; the
  five original values survive with their labels intact. If Option A is chosen,
  add the child-row count comparison and `foreign_key_check` assertions.
- **Filtering:** category, tag, multi-tag (AND vs OR — decide and test), and
  distance, composed together. Assert an event with no tags is not excluded by an
  unrelated tag filter.
- **Aggregates match the ledger:** compute a dashboard total and assert it equals
  `SUM(hours_awarded) WHERE present = 1` for the same scope. **This is the test
  that protects the invariant** — not a snapshot of a number.
- **Scoping:** the authorization matrix, one row per (role, stats endpoint),
  including negatives. Assert an admin at school A cannot read school B's
  aggregate.
- **`verify:hours` still exits 0** after every task that touches a read path.
- **Client:** `BarChart.test.jsx` (new); the three `src/` guards, remembering the
  class guard runs **both directions** so a removed chart's CSS must go too;
  `App.routeTable`, `App.shellByRole`, `routes.test` and `hookOrder` still pass.
- **Mutation-test every guard added.** Delete the check, watch the test fail,
  restore it.

## 13. Risk analysis

| Risk | L | I | Mitigation |
|---|---|---|---|
| **🔴 A rebuild of `events` orphans or anonymises volunteer data** | Medium | **Critical** | Option B avoids the rebuild entirely (§4); if a human picks Option A, all six §8.3 guards plus a verified backup |
| **A dashboard total disagrees with the ledger** | Medium | High | Task 7's parity tests land first; no cached totals; `verify:hours` in every gate |
| **A dashboard leaks another school's numbers** | Medium | High | Every aggregate scoped; matrix rows including negatives (Task 11) |
| **Taxonomy migration folds `'5K'`/`'Food Pantry'` into `'Other'`** | Medium | High | Seed exactly the five existing values; assert they survive; renaming is reversible, merging is not |
| **Tag table becomes spam** | Medium | Medium | Per-event cap, length cap, slug normalisation, case-insensitive dedupe, rate limit |
| **OSM/Nominatim usage policy breach gets the app blocked** | Medium | High | Visible attribution; ≤1/s server-wide; geocode cache; no prefetch |
| **A stored home address becomes a minor's location record** | Low | **Critical** | Not in scope; in-memory only; coarse bbox; explicitly out-of-scope in §6.2 |
| **A colour literal reaches the database via `colour_token`** | Medium | Medium | Store a token name; validate on write; a hex would bypass `noHardcodedColors` entirely |
| **Removing a chart leaves a dead CSS rule and fails the build** | High | Low | `noDanglingClasses` runs both directions — expect it, and remove the rule with the chart |
| **Multi-district tenancy arrives after this ships** | Low | High | Ask Q6 (roadmap index §7) **before** starting W5; retrofitting after analytics ship is the expensive path |

## 15. Open questions for a human

1. **🔴 Option A or B for the taxonomy migration (§4)?** *Assumption: B — additive
   `category_id`, no rebuild, dead column accepted.* This is the highest-stakes
   question in the release.
2. **🔴 The category vocabulary.** The current five are `School`, `5K`,
   `Food Pantry`, `Fundraiser`, `Other`. Who decides what is added, and does the
   district have an existing reporting taxonomy to match? *Assumption: seed the
   existing five unchanged and let an admin add more; do not invent a vocabulary
   on the district's behalf.*
3. **Multiple tags — AND or OR?** *Assumption: OR within tags, AND across filter
   types (category AND (tag1 OR tag2)), because that is what a person expects
   from chips. Document it in the UI.*
4. **The service-hour goal.** `HOUR_GOAL = 25` is hardcoded. Is 25 the district's
   number, is it per-grade, per-school? *Assumption: config value, one number,
   labelled as a target rather than a requirement until confirmed.*
5. **Should `/api/weather` require authentication?** *Assumption: yes, add
   `authenticateToken` — it costs nothing and stops the server being a free
   weather proxy.*
6. **Does the `partner` role get a dashboard?** `analytics.public` exists and is
   unused. *Assumption: not in this release; leave the capability unused rather
   than granting an accidentally-scoped view.*
7. **🔴 Q6 from the roadmap index — is a second district near-term?** If yes,
   `school` should become an `organizations` entity **in this release**, before
   analytics are built on the `TEXT` column. *Assumption: single district through
   v2.0.*
