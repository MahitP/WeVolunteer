# v1.2c — Final Release Review

**Date:** 2026-08-04 (revised same day after the three blockers were cleared)
**Branch reviewed:** `fix/v1.2c-review-findings` @ `e73f396`
**Version:** 1.2.0
**Scope:** error monitoring, the triage dashboard, and everything v1.2c changed
**Method:** independent. Prior conclusions were treated as claims to test, not as findings to inherit.

---

## 1 — Executive summary

v1.2c gives WeVolunteer the ability to see its own failures. The design is
unusually careful for its size: redaction happens before storage rather than on
the way out, the user is a hash rather than an id, the route is a pattern rather
than a URL, and there is deliberately no request-body column to fill in later.
The one unauthenticated write endpoint in the application is bounded four
independent ways, and each bound covers a blind spot in the others.

This review re-derived those properties by attacking the running application
rather than by reading the previous review. Most of them held under attack, and
several held better than documented. Four did not, and all four are now fixed
with tests verified to fail without their fix.

The most serious was a **partial** redaction failure, which is the dangerous
shape: `josé.garcía@lincolnhigh.k12.il.us` was stored as `josé.garcí[redacted]`
— a student's given name and most of their surname, on a row that reads as
redacted, in a table retained up to 180 days, in an application whose users are
mostly minors. The email rule was ASCII-only, so it did not fail cleanly on a
non-ASCII address; it matched from the ASCII run that reached the `@`.
`notificationWorker.js` records the message of a failed send verbatim, so one
bounced email was the whole path.

Nothing found is architectural. Everything found was a gap between what the code
was documented to do and what it actually did — which is what an adversarial
pass is for, and why "the tests pass" was never sufficient evidence.

**A second pass then cleared the three release blockers** this review had raised
but not fixed, because at the time each looked like a decision rather than a
task: the version number, the missing privacy notice, and the absence of any
alerting. All three are now closed in code (§3, B-1 to B-3), and the verdict has
moved from READY WITH WARNINGS to **READY**. What remains is deployment
configuration — three items, none of them a code change, all of them needing the
production host or a district decision.

### F-1 — an accented name survived redaction *(the one that mattered)*

**Exploit path.** No attacker needed. A student with an accented name gets a
bounced or rejected email; `notificationWorker.js` records `err.message`
verbatim; the address is in it. The rule
`[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}` cannot start on `é`, so it
began matching at the ASCII run that reached the `@` and consumed only
`a@lincolnhigh.k12.il.us`. Stored: `SMTP bounce for josé.garcí[redacted]`.

This is worse than no rule. An absent rule leaves an obviously unredacted row
that a reader recognises as a leak. A partial rule produces a row containing
`[redacted]`, which is exactly what a reader takes as evidence that redaction
worked.

**Fix.** Unicode letter classes, with `\p{M}` so a decomposed accent (`e` +
U+0301) cannot terminate the match the same way in a different normalisation
form. Verified against precomposed, decomposed, non-Latin (`田中@例え.jp`) and
accented-domain forms.

### F-2 — a certificate code could reach the table inside a message

`GET /api/certificates/verify/:code` is unauthenticated and answers with a
student's name, their event, their organizer and their hours. The code is a
**bearer credential**, and `normaliseClientRoute` has always refused to store one
in `route` — there is a test for it. Nothing stopped one arriving inside
`message`, where it would sit for up to 180 days.

No automatic path to this was demonstrated, so it is defence in depth rather
than a confirmed leak. It was fixed because the asymmetry was indefensible: the
same value was carefully excluded from one column and unguarded in the next one
over. The rule uses the generator's own alphabet and is case-**sensitive**, so it
cannot eat the lowercase `wev-test-*` scratch directories that appear in stack
traces — over-redaction has a real cost.

### F-3 — the one unbounded parameter was reachable as a 500

`?offset=1e20` → **HTTP 500**. `limit` was clamped from the start; `offset` was
not. Every hostile value anyone had thought to test was small or non-finite, so
the gap survived: a *finite* offset past `Number.MAX_SAFE_INTEGER` floors to
itself, `node:sqlite` refuses to bind it, and the screen whose entire job is to
show errors was itself reachable as one. `max` is now required rather than
optional, because the single caller that omitted it is the one that broke.

### F-4 — the 413 named the wrong limit

`/api/errors/report` is mounted with its own 8 kB parser. A 9 kB report was
correctly refused and told *"That request was too large. The limit is 100kb."* —
the one piece of advice guaranteed not to work, on the endpoint a browser
retries from. The limit is now read from body-parser's own `err.limit`.

### B-1 — the version was a released number

Both manifests and all three lockfile fields read `1.1.0` — a version that was
tagged and released on 2026-07-31. v1.2a, v1.2b and v1.2c had all accumulated
under it, so `/health` misidentified the running code during exactly the moment
it is consulted, and `error_groups.release` — a v1.2c feature whose only job is
telling releases apart — stamped `1.1.0` on all three.

**1.2.0, not 1.1.1 and not 2.0.0.** Additive throughout: new capabilities, new
endpoints, new tables, no route removed. The wrinkle is v1.2b's step-up gates,
which changed the request contract on seven existing endpoints — an operational
breaking change inside a minor release, precisely like 1.1.0's own mandatory
`JWT_SECRET` guard. §4.2's lesson from that release was to call it out
prominently whatever the number says, so the CHANGELOG now opens with it.

A second defect surfaced on the way: the changelog section was never closed at
the tag. The released commit still said `## [1.1.0] — Unreleased`. Split by
diffing against `git show v1.1.0:CHANGELOG.md`, so each section now describes
what actually shipped in it.

Verified through the running application, not just the files: a boot against a
restored database reports `{"status":"ok","database":"connected","writable":true,"version":"1.2.0"}`.

### B-2 — a privacy notice, and the line it does not cross

`VITE_PRIVACY_URL` was empty, so the signup acknowledgement did not render and
the app collected minors' names, emails, grades and schools with no disclosure.
The flag was right to fail closed — the alternative is a checkbox linking
nowhere — but it meant the blocker could only clear when someone wrote a
document, and nobody was.

`/privacy` now ships. It is **public** (read before you have an account, which
is when you are deciding whether to create one) and it separates two things
carefully:

- **Facts about the software** — what is stored, who can see it, what it does
  not do. Read off the schema and the route handlers, true wherever this runs.
- **The district's policy** — retention, deletion contact, under-13 consent.
  Supplied as build-time config. Nothing is guessed, and while any is missing
  the page shows a warning **above** the reassuring content saying it is not a
  reviewed policy.

That ordering is the design. `src/config.js` warns that placeholder legal text
is worse than none because it manufactures the appearance of review; a page that
admits it is unfinished cannot do that. The mutation test confirms it: making
the page invent a plausible retention sentence fails **eight** assertions.

**A latent routing bug came with it.** The public-route branch in `App.jsx` tested
`currentPath.startsWith('/verify/')` — a hardcoded second copy of
`PUBLIC_ROUTES`. Any route added to that table fell through to the signed-out
catch-all and answered 404 while looking perfectly declared. The check is derived
from the table now, and matches segment-wise rather than by prefix, so
`/privacy` cannot also match `/privacy-settings`.

### B-3 — something now causes a human to look

The alerting gap was the largest remaining operational risk in the first pass.
`ALERT_EMAIL` closes it: a new open `server` or `worker` problem produces one
email on the existing 15-minute sweep. Unset — the default — nothing happens.

**Email, on the existing sweep.** SMTP is already a hard production boot
requirement, so there is no service to run and no credential to rotate. A
webhook would add both, for a district that may have nowhere to point it. It sits
inside `runNotificationSweep` beside `sweepErrors`, for that function's own
reason: no new interval, no new worker, nothing more for `shutdown.js` to drain.

**The email carries almost nothing, and that is the security decision.** Counts,
error class, fingerprint, link. No message, no stack, no route, nothing about
who was affected. An alert leaves the application into a mailbox `error.read`
does not protect and which will be forwarded — and finding S-4 of this very
review established that redaction does not cover names, addresses or IPs. Safe
enough for a table behind a super-only capability is not safe enough to mail.
Client reports never alert: their error class is attacker-supplied.

Two design choices are worth recording because their opposites are the obvious
ones:

- **Per-group state (`alerted_at`), not a "last alerted" timestamp.** A stored
  timestamp plus "first seen since then" is smaller and loses alerts — a
  restart, a missed tick, or two ticks racing drops whatever fell in the gap,
  and a dropped alert is indistinguishable from nothing being wrong.
  `alerted_at IS NULL` cannot drop anything.
- **Marked before the send, not after.** A failed send loses one digest.
  Marking afterwards re-sends the same one every 15 minutes forever, and a
  repeating alert is how a channel gets muted — after which every future alert
  is lost too.

Migration 005 backfills existing rows to already-alerted, so deploying this does
not mail the entire historical backlog and get the channel muted in its first
hour. It was applied to a real populated database during the restore rehearsal:
clean, no data loss, no FK violations.

Backup failures still alert separately, through systemd `OnFailure=`. A backup
that cannot run is exactly the situation where the application may not be
running either, so routing that alert through the application would route it
through the broken thing.

## 4 — Security findings

Independent adversarial pass. Every result below was produced by attacking the
running application in-process, not by reading the source.

### 4.1 What held under attack

| Attack | Result |
|---|---|
| Forge `source: 'server'` to escape the client ceiling | Ignored; stored as `client` |
| Forge `fingerprint`, `status`, `release`, `user_hash`, `occurred_at` | All server-assigned; every forged value discarded |
| Smuggle `password` through `context` | Dropped — allowlist, not denylist |
| Prototype pollution via `context.__proto__` and body `__proto__` | No pollution |
| SQL injection via `status`, `source`, `fingerprint` | Parameterised; unknown filter values ignored |
| `limit=1e9`, `limit[]=5`, repeated params | Clamped or refused to the default |
| `PATCH status` as array / object / `__proto__` / null | 400 on all four |
| Path traversal, protocol-relative, NUL, `%2e%2e` in `route` | All → `unknown` |
| Query string carrying a reset token or address | Dropped before matching; pattern stored, never the input |
| Student / anonymous access to all four triage endpoints | 403 / 401 on all |
| **`user_capabilities` row granting `error.read`, inserted directly into the DB** | **403** — `SUPER_ONLY` is checked before per-user grants |
| Stored XSS payload round-trip | Stored raw; not exploitable (see 4.3) |
| Flood the dashboard with 700 distinct problems | Ceiling held at exactly 500 + 1 overflow row, counter = 200 |
| Record a genuine **server** error during that flood | **Still recorded** — the ceiling is client-only |

Two properties are stronger than documented and worth stating:

- **The fingerprint's digit collapsing is an anti-flood control.** 1,000 reports
  differing only in numbers produced **53** groups, not 1,000. An attacker must
  vary non-numeric text to inflate the table.
- **A client flood cannot blind server-side monitoring.** Verified directly: with
  the ceiling reached and overflow counting, a fresh server error still recorded
  normally. This is the property that decides whether the flood is vandalism or
  an actual attack, and it holds.

### 4.2 Open findings

| ID | Finding | Severity | Disposition |
|---|---|---|---|
| S-1 | Report attribution survives logout | **Low** | Accepted risk |
| S-2 | `role` on an error event comes from the JWT, not the DB | **Low** | Accepted risk |
| S-3 | Dashboard pollution costs 25 IPs | **Low** | Accepted, by design |
| S-4 | Names, addresses, IPs, DOBs are not redacted | **Low** | Documented, not fixable by pattern |
| S-5 | `npm audit`: 3 high (2 advisories) | **Low** | Both assessed not applicable |

**S-1 — attribution survives logout.** *Exploit path:* `POST /api/auth/logout`
increments `token_version`; a report sent afterwards with the same cookie is
still attributed (`user_hash` and `role` populated). `optionalReporter` uses bare
`jwt.verify` and checks neither `token_version` nor revocation.
*Why accepted:* the endpoint is unauthenticated on purpose — the failures worth
seeing most happen before a session exists. Checking `token_version` means a
database read on the one endpoint an attacker can hit without credentials, which
converts an attribution nicety into a denial-of-service lever. The blast radius
is a wrong `user_hash` on a diagnostic row and a slightly inflated
`users_seen` — no access is granted and no data is disclosed. The existing
comment explains why `authenticateToken` is not used but does not mention
revocation; that gap is now closed in §6.10.
*If ever fixed:* compare `token_version` from an in-memory cache, never a
synchronous read.

**S-2 — stale role.** Same root cause. A user demoted from admin to student
still reports as `admin` until their token expires. Cosmetic; affects one column
on a triage row.

**S-3 — dashboard pollution.** The limiter is 20/IP/15min and the ceiling is 500
groups, so 25 addresses reach the ceiling. The consequences are bounded and
deliberate: forged groups are single-occurrence by construction and swept at 7
days, the overflow row makes the flood *visible* rather than silent, and server
and worker capture are unaffected. Measured cost of a 700-report flood: **816 kB
total database size**. This is the design working, not a defect.

**S-4 — what redaction does not cover.** Confirmed by probing: personal names,
street addresses, IPv4/IPv6, and dates of birth pass through. There is no
pattern for a name, and a rule broad enough to catch one would redact the words
that make a message diagnosable. The real control is upstream — *do not
interpolate user data into an error message* — and every `throw new Error(...)`
in `server/` was checked against it during this review: none carries a name, an
address, or an email. The limit is now stated explicitly in §6.10 rather than
left for a reader to infer from a list of what *is* covered.

**S-5 — dependency advisories.** Both re-verified against the code, not against
the previous assessment:
- *react-router RSC CSRF* (2 of 3 entries): `src/main.jsx` mounts
  `BrowserRouter`; there is no `createBrowserRouter`, no `RouterProvider`, and no
  route `loader`/`action` anywhere in `src/`. The RSC surface is never
  instantiated. **No fixed 7.x exists** — `npm audit fix --force` *downgrades* to
  7.11.0, a breaking change taken to remove a risk that does not exist here. Do
  not run it.
- *brace-expansion DoS* (new since v1.2b): reached only via
  `server → nodemon → minimatch`. `nodemon` is a devDependency, absent from
  `npm ci --omit=dev`. A non-breaking fix exists and should be the first commit
  **after** the merge — taking it now would invalidate every gate already run.

### 4.3 Cross-site scripting — assessed, not exploitable

`<img src=x onerror=alert(document.cookie)>` and `<script>alert(1)</script>`
round-trip through the intake and are stored raw. The reasoning that makes this
safe was verified rather than assumed:

- The only consumer is `ErrorDashboard.jsx`, which renders every field as a React
  text child. There is no `dangerouslySetInnerHTML` or `innerHTML` anywhere in
  `src/` (grepped).
- Responses are `application/json` with `X-Content-Type-Options: nosniff`.
- CSP is `default-src 'self'` with **no `unsafe-inline` for scripts**, so an
  injected inline handler would not execute even if it reached the DOM.

Storing raw is the right call: escaping on write would corrupt stack traces,
which routinely contain `<`, `>` and quotes. **This assessment is void** if any
error field is ever rendered outside React, exported to CSV or HTML, or emailed.

### 4.4 Data protection — minors

The design decisions here are correct and were verified end to end against the
database, not against helper return values: `user_hash` is a truncated one-way
digest and no id is stored; `route` is always a pattern from a closed allowlist,
so a certificate code or a live reset token is *unstorable* rather than merely
unlikely; there is no request-body column in the schema at all; `context` is an
allowlist. Retention is tiered and enforced by a sweep that only ever DELETEs, so
it cannot resurrect a counter or reopen a group somebody closed.

The one real gap in this area was F-1, and it is fixed.

- **14 tests** (`PrivacyNotice.test.jsx`) — the factual sections always render;

- **17 tests** (`alerting.test.js`) — what is sent, what is not, throttling

- **9 tests** (`alerting.integration.test.js`) — the wiring, separately from the

**Mutation testing.** No mutation framework is installed; this was done by hand.

recorded. **14/14 mutations killed** across both passes — 6 for the security
fixes, 8 for the blockers.

One is worth recording because it failed first. The initial attempt at mutating
the alert body — appending `g.message` to it — **survived**, and the test looked
fine. `pendingAlerts` does not SELECT `message`, so the mutation appended
`undefined` and changed nothing: a no-op mutation, not a passing guard. The real
mutation (widening the SELECT *and* the body) does fail the test. That near-miss
is why `alerting.test.js` now also pins the SELECT column list directly —
asserting only on the rendered body leaves the sensitive columns one property
access away from whoever next edits the template.

## 6 — Operational readiness

### Backup and restore — **rehearsed, with evidence**

The procedure was **not** missing. `bin/backup.sh`, `bin/verify-restore.sh`, a
systemd service and timer, runbook §7, and a release-checklist item all already
existed. What was missing was evidence that any of it had ever been run.

It has now been run, end to end, on this host:

```
backup.sh    → verified: users=29 credited_hours=8.5 certificates=6 → 24K .gz
verify-restore.sh
  integrity_check: ok
  foreign_key_check: no violations
  contents: users=29 credited_hours=8.5 certificates=6 ledger_rows=6
  hours ledger parity: PASS
  health: {"status":"ok","database":"connected","writable":true,"version":"1.1.0"}
  RESTORE REHEARSAL PASSED
```

Every stage passed, including the two that distinguish a real rehearsal from a
file-integrity check: **ledger parity re-verified inside the restored copy**, and
**the application booted against it and reported writable**.

> **What this does and does not prove.** It proves the tooling is correct and the
> procedure is followed by a script rather than improvised. It was run on a
> development machine against development data. It is **not** evidence that the
> production backup works — nothing is, except running `verify-restore.sh` on the
> production host against a production archive. That remains **PENDING** and is
> item 4 in §7.

Note the rehearsal output also independently confirms the version problem:
`/health` reports **1.1.0**.

> `ALERT_EMAIL`. **Setting it is a deployment step, not a code one** — unset is
> the default and means alerting is off — so this is only closed once §7 item 3
> is done on the real host.

### Scaling risks

Re-verified independently; the existing analysis (ENGINEERING_GUIDE §10.1/§10.2,
runbook H5) is accurate and needs no correction. What v1.2c adds:

**SQLite concurrency.** Not a pilot concern, and now measured rather than
assumed. The intake sustained **~1,180 reports/sec** from a single connection,
including the group-creation path. A 700-report flood grew the whole database to
816 kB. At pilot scale this is not close to a bottleneck.

Worth recording, though: `recordError` issues **six** statements per report
(existence check, INSERT-or-UPDATE, recent-event count, event INSERT, evidence
prune, `users_seen` recount) and is **not** wrapped in a transaction, so each is
its own implicit WAL commit. That makes the unauthenticated intake the heaviest
per-request write path in the application. It is bounded well below anything
that matters today; it is the first thing to measure if write contention ever
appears.

**In-memory rate limiting** (runbook H5) gains a v1.2c-specific edge worth
stating: `errorReportLimiter` uses the default memory store, so a restart clears
it — but `CLIENT_GROUP_CEILING` is database-backed and therefore **survives a
restart**. In a restart loop the request-rate bound evaporates while the storage
bound holds. That is the right way round, and it means a restart loop cannot be
used to fill the error table.

**Multi-instance** is blocked and *enforced* (`instanceLock.js`), not merely
documented. v1.2c adds no new obstacle: `sweepErrors` runs inside the existing
15-minute sweep, which is already single-instance state.

**Redis** is required by the same trigger as everything else — a second instance,
for any reason. v1.2c does not move that trigger.

## 7 — Deployment checklist

Ordered. Items 1–3 are blocking. **None is a code change** — every one needs the
production host or a district decision, which is why they could not be done from
here.

- [ ] **1. Supply the district's three privacy answers, then rebuild.**
      *Blocking, and a district decision.* `/privacy` ships and states accurately
      what the software stores and who sees it. It does **not** state retention,
      the deletion contact, or under-13 consent, and until all four values are
      set it displays a prominent "not a reviewed policy" warning on every view.
      In `.env.production.example`:
      ```
      VITE_PRIVACY_URL=/privacy
      VITE_PRIVACY_OWNER=…
      VITE_PRIVACY_RETENTION=…
      VITE_PRIVACY_CONTACT=…
      VITE_PRIVACY_UNDER13=…
      ```
      **A rebuild is required** — `VITE_*` values are compiled into the bundle,
      and setting them on a running server does nothing. Use an external URL
      instead if the district publishes its own notice; the consent checkbox
      works either way.

- [ ] **2. Fill `/etc/wevolunteer/wevolunteer.env`.** *Blocking.* Every
      `REPLACE_ME`. `TRUST_PROXY` and `BIND_ADDRESS` are easy to miss and both
      matter: unset `TRUST_PROXY` behind a proxy puts every user in one
      rate-limit bucket, and the default `BIND_ADDRESS` is `0.0.0.0`, which
      bypasses nginx and therefore TLS.

- [ ] **3. Set `ALERT_EMAIL`.** *Blocking.* The alerting code ships; unset is the
      default and means it is off. Without this the application records its own
      failures perfectly and tells nobody, which is how a pilot learns about a
      week-old outage from a student rather than from the software.
      ```
      ALERT_EMAIL=ops@district.example
      ```
      Optionally `ALERT_MIN_INTERVAL_MS` (default one hour). Send yourself a test
      by triggering a server error and waiting one sweep tick.

- [ ] **4. Run `verify-restore.sh` on the production host.**
      ```bash
      sudo -u wev WEV_BACKUP_DIR=/var/backups/wevolunteer bin/verify-restore.sh
      ```
      The rehearsal in §6 proves the tooling on a development machine. Only this
      proves your backup.

- [ ] **5. Add `OnFailure=` to `wevolunteer-backup.service`.** The one alerting
      gap the application deliberately does not cover. A backup job that fails
      silently is indistinguishable from one that never ran.

- [ ] **6. Sign in as `super_admin` and open `/errors`.** The gate is
      `SUPER_ONLY`; if no super_admin exists, use `bin/make-admin.mjs`. Confirm
      the page loads and the day chart renders.

- [ ] **7. Read `/privacy` in a browser, signed out.** It must render without a
      session, and it must NOT show the "not finished" warning once item 1 is
      done. If it still does, one of the four values did not reach the build.

- [ ] **8. Confirm the intake works from a real browser.** Open the console on
      the deployed origin and run
      `fetch('/api/errors/report',{method:'POST',headers:{'Content-Type':'application/json'},body:'{"message":"deployment smoke test","route":"/"}'})`.
      Expect `202`, then find it in `/errors`. This exercises CSP, CORS and the
      proxy in a way no test can.

- [ ] **9. First commit after merge: `npm audit fix`** for brace-expansion
      (non-breaking, dev-only). **Do not** run `npm audit fix --force` — it
      downgrades react-router to remove a risk this app does not have.

- [ ] **10. Tag the release.** `v1.2.0`, annotated, on the merge commit, after
      the gates pass on it. §4.1 explains why the tag is created by hand rather
      than by `npm version`.

- [ ] **11. Run `bin/install-hooks.sh`** on any clone that has not.

**v1.3 — Operate it.** v1.2c built the instrument and this pass connected it to a
human. What is left is learning from it.

1. **Watch what alerting actually does in the pilot.** The one-hour throttle and

   production traffic. If the channel is noisy, narrow it; if a real problem
   went unnoticed, widen it. Both are one-line changes, and both should be made

2. **Add `OnFailure=` to the backup unit** (§7 item 5) if it was not done at

4. **Consider a boot guard on the version**, refusing to start if the two

## 11 — Recommendation

### Should WeVolunteer proceed to pilot deployment?

**Yes.** The code is ready. What remains is deployment configuration, and it is
listed, ordered, and small.

**Why yes.** The security model was tested adversarially rather than trusted, and
it held: authorization survived every attack including a `user_capabilities` row
for `error.read` inserted directly into the database; field injection through the
unauthenticated intake achieved nothing; the flood ceiling held at exactly its
documented value; and a genuine server error was still recorded *while* the
client table was being flooded. Four real defects were found and fixed, each
proven by reverting it. The restore procedure has evidence behind it. Four gates
pass on 2,407 tests.

And the three things that made the first verdict "with warnings" are closed. The
application now knows what version it is, tells users what it collects before
they hand it over, and tells an operator when it breaks. Those are not features;
they are the difference between software that works and software that can be
run by someone accountable for it.

**What is honestly still open.** Three deployment items, none of them code. The
most important is the privacy one, and it is worth being precise: **shipping
`/privacy` did not create a district privacy policy.** It built the mechanism and
stated truthfully what the software does. Retention, deletion contact and
under-13 consent remain decisions a district makes and answers for, and until
they are supplied the page says so in a banner rather than pretending otherwise.
That is the honest state — better than silence, not a substitute for adoption.

**The framing has not changed.** Before this release a crash on a student's phone
left no trace and the only diagnostic was someone saying "it didn't work". A
pilot without it would be flying blind. A pilot with it, with `ALERT_EMAIL` set
and a named owner, is a reasonable thing to do with real students' data.

**What I could not verify, stated plainly:**
- Production backups. Only running `verify-restore.sh` there proves those.
- Anything about the production host: TLS, nginx, systemd hardening, firewall.
- Real-browser behaviour of CSP, CORS and the intake against the deployed origin
  — hence §7 item 8.
- **Real alert delivery.** Alerting is tested end to end against a mocked mail
  layer and through the real sweep, but no email has actually been delivered by
  an SMTP server. §7 item 3 includes sending one.
- Email deliverability to school domains (SPF/DKIM/DMARC).
- The Playwright suite. `@playwright/test` is not in `package.json` and there is
  no script for it; it was not run.
